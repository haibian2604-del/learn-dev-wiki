## 第一部分：系统设计题（15题）

### 高并发 RAG 系统设计

**Q1: 设计一个支持日均 100 万查询的企业级 RAG 系统**

- 难度：⭐⭐⭐⭐⭐
- 公司：字节、阿里、腾讯（高频）
- 标签：#系统设计 #高并发 #RAG

**需求分析** ：

- 用户规模：10000+ 企业员工
- 查询量：日均 100万，峰值 QPS 3000
- 延迟要求：P99 < 500ms
- 可用性：99.9%
- 成本：API 调用成本 < 10万/月

**考察点** ：架构设计、检索优化、生成优化、缓存策略、成本控制、监控告警

**💡 参考答案**

**第一步：把需求翻译成容量数字（面试加分点）**
- 日均 100 万 → 平均 QPS ≈ 12；峰值 3000 → **峰均比 250×**，说明是办公场景的尖峰型负载
- 结论：**按峰值设计容量、按均值设计成本**，靠自动扩缩容吃掉峰谷差
- 成本：10 万元/月 ÷ 3000 万次/月 ≈ **0.0033 元/次**——预算极紧，**必须靠缓存和模型分层**，不能全靠大模型

**第二步：分层架构**
1. **接入层**：API 网关（鉴权、租户识别、限流、WAF）+ 优先级队列
2. **查询理解层**：意图识别 + 复杂度路由 + query 改写（小模型/缓存，50ms 内）
3. **检索层**：向量库分片 + BM25 集群，**并行双路 + RRF 融合** → rerank
4. **生成层**：LLM Router（按难度选模型）+ vLLM 推理集群（continuous batching）+ 流式输出
5. **存储层**：向量库 / ES / PG / Redis / 对象存储
6. **横切**：语义缓存、可观测（trace）、成本计量、权限过滤

**第三步：延迟预算（P99 500ms 分配）**

| 阶段       | 预算    | 手段                      |
| -------- | ----- | ----------------------- |
| 网关+鉴权    | 20ms  | 本地缓存 token 校验           |
| 意图/改写    | 50ms  | 小模型 + 结果缓存              |
| 检索（双路并行） | 100ms | HNSW + 分片副本 + 预过滤       |
| Rerank   | 80ms  | 小 cross-encoder，候选 ≤ 50 |
| 生成（TTFT） | 200ms | 小模型优先 + prefix cache    |
| 后处理/引用   | 50ms  | 异步回填                    |

**第四步：成本控制（0.0033 元/次的关键）**
- **语义缓存**：企业内问题重复率高，命中 30–50% 直接把成本砍半
- **模型分层路由**：简单 FAQ 走小模型/专用检索，只有复杂问题上大模型
- **Prompt 压缩**：只送 top-3~5 + 上下文压缩
- **批处理**：非实时任务走 batch API

**第五步：可用性 99.9%**
- 多副本 + 多可用区；向量库主从
- **降级链路**：LLM 超时 → 返回检索摘要；rerank 超时 → 用粗排结果；全链路失败 → 友好错误
- 依赖隔离：LLM 供应商多路由（故障自动切换）

**第六步：监控告警**
- 指标：QPS、P99、TTFT、缓存命中率、召回率、成本/次、错误率、工具失败率
- Trace：每次查询的 span 树，能定位"哪一段慢/哪一步错"
- 告警：P99 超阈、成本超预算、缓存命中率骤降

**Q2: 设计一个 Multi-Agent 协作系统（智能客服场景）**

- 难度：⭐⭐⭐⭐⭐
- 公司：字节、阿里（真题）
- 标签：#MultiAgent #系统设计 #协作

**需求** ：

- 场景：电商客服（订单查询、退款、售后）
- 3 个专业 Agent：订单 Agent、物流 Agent、售后 Agent
- 1 个 Supervisor：任务分发与结果汇总
- 要求：并发处理、状态管理、异常处理

**💡 参考答案**

**一、角色与职责边界**
- **Supervisor**：意图识别 → 任务分解 → 分派 → 汇总 → 决定是否问澄清/转人工。**不干具体活**
- **订单 Agent**：查订单、改地址、开发票（只读 + 低危写）
- **物流 Agent**：查物流、催单、改派（只读 + 通知）
- **售后 Agent**：退换货、退款（**高危写操作，需人工确认 + 幂等 key**）
- 边界原则：**每个 agent 的工具集互不重叠**，否则会出现"两个 agent 都能退款"的灾难

**二、协作机制**
- 编排：**Supervisor 中心调度**（不用自由群聊，客服场景要可控）
- 派发：独立子任务**并行**（`asyncio.gather`），有依赖的串行
- 汇总：Supervisor 合并结果 + 冲突消解（以高优先级/高置信度为准）

**三、状态管理**
- 会话级 state（Redis，key = `session_id`）：用户信息、已识别实体（订单号）、各 agent 结果、任务进度
- **会话级串行化**：同一 session 请求排队，避免并发写冲突
- 乐观锁 + 版本号防覆盖
- 长会话用滚动摘要压缩

**四、并发处理**
- Supervisor 本身无状态，水平扩展
- 子 agent 按类型拆 worker 池（退款接口慢，不要阻塞查询）
- 限流 + 背压；同 session 串行、跨 session 并行

**五、异常处理（重点）**
1. 子 agent 超时/失败 → 重试（指数退避）→ 换 agent/工具 → 降级（简化任务）→ **转人工**
2. **最大步数/重试次数上限**，防死循环
3. 退款类写操作：幂等 key 防重复扣款；失败必须**明确告知用户**而非静默
4. 误判导致策略冲突 → Supervisor 仲裁（优先级 + 置信度）；已执行的副作用走 **Saga 补偿**

**六、安全与合规**
- 用户身份注入上下文，退款金额上限，超限强制人工
- 全链路审计日志（谁、何时、基于什么、做了什么）
- 权限硬隔离：用户 A 的订单绝不出现在用户 B 的会话里

**Q3: 设计一个支持流式输出的 RAG 系统**

- 难度：⭐⭐⭐⭐
- 标签：#RAG #流式输出 #系统设计

**要求** ：

- 检索和生成并行
- 逐 token 返回
- 前端展示优化

**💡 参考答案**

**一、先澄清"检索和生成并行"的正确打开方式**
- 严格说 RAG 是"先检索后生成"，**生成必须以检索结果为输入**，不可能完全并行
- 真正可做的是并行化：
  1. **检索内部并行**：向量检索 ‖ BM25 ‖ 权限校验 ‖ 记忆读取，四路同时发起
  2. **预取（prefetch）**：首轮生成时，后台预测并预取下一轮可能需要的证据（适合多跳）
  3. **边检索边出提示**：立即推送"正在检索…"，用户感知延迟降为 0
- 面试时点出这一点，比盲目答"并行"更能体现理解

**二、逐 token 返回的实现**
- 传输选型：**SSE（Server-Sent Events）** 优先——单向、简单、HTTP 原生、自动重连；需要**双向打断/多模态**时才用 WebSocket
- 分片协议：定义 event 类型（`retrieval` / `token` / `citation` / `done` / `error`），前端按类型分别处理
- 后端：LLM 流式响应直接透传，**不要中间缓冲**（Nginx/网关要关 `proxy_buffering`）
- 引用策略：**先出正文后补引用**——不要让引用等检索校验阻塞首 token；生成结束后回填 `[1][2]` 锚点

**三、前端展示优化**
- 逐字渲染 + 打字机效果；Markdown **增量解析**（不要等全文再渲染）
- **引用角标实时出现**，点击可跳原文片段
- 支持**中断生成**（用户看到一半不满意直接停）+ 重新生成
- 检索阶段显示骨架屏/进度（"已找到 5 篇相关文档"）

**四、工程细节**
- 背压：客户端消费慢 → 缓冲上限 + 丢弃策略，防内存爆
- 断线续传：`event id` + `Last-Event-ID` 头
- 心跳保活（防反向代理 60s 超时断连）
- 首 token 延迟（TTFT）是关键指标，需单独监控

**Q4: 设计一个 Agent 工作流引擎（类似 LangGraph）**

- 难度：⭐⭐⭐⭐⭐
- 标签：#Agent #工作流 #状态机

**要求** ：

- 支持有向图定义
- 状态持久化
- 条件分支与循环
- 错误重试

**💡 参考答案**

**一、核心抽象（四件套）**
1. **State**：全局状态对象 + **reducer**（定义每个字段如何合并，如消息列表用 append、计数字段用覆盖）——reducer 设计决定了并发安全
2. **Node**：一个执行单元（可以是 LLM 调用、工具调用、确定性函数、子图）
3. **Edge**：普通边（固定跳转）+ **条件边**（路由函数决定下一个节点）
4. **Checkpointer**：状态快照存储

**二、有向图 + 循环**
- 用邻接表建模；**必须支持环**（Agent 的 ReAct 循环本质是环）
- 环必须有**退出条件**：最大迭代数、状态判定（达到目标）、预算耗尽
- 编译期做**图校验**：无出口的环、不可达节点要报错

**三、状态持久化（关键设计）**
- **checkpoint 粒度**：每节点执行后 / 每步之后写快照
- 存储：Redis（热，TTL）+ PG/对象存储（冷，审计）
- 能力：
  - **断点续跑**（进程崩溃后从最后 checkpoint 恢复）
  - **时间旅行**（回到任意历史状态重放——调试神器）
  - **人机中断（interrupt）**：暂停等人工审批后再继续
- 状态要**可序列化 + 版本兼容**（schema 演进不能读不了老快照）

**四、条件分支与循环**
- 条件边 = `fn(state) -> next_node`
- 支持 **fan-out / fan-in**：一个节点并行触发多个下游，用 **join（barrier）** 等齐再合并
- 并发写同一状态时靠 **reducer 保证幂等**

**五、错误重试**
- **节点级**重试策略（次数、退避、可重试异常类型），配置在节点上而非全局
- **兜底边**：重试耗尽后跳到降级节点（如"转人工"）
- 区分**可重试**（超时/限流）与**不可重试**（参数错）——后者重试无意义
- 幂等：有副作用的节点带 idempotency key

**六、与其他编排引擎的差别**
- 相比 Airflow/Temporal：面向**LLM 与不确定流程**，支持**运行时动态跳转**（下一跳由模型输出决定，而非编译期确定）
- 相比手写 while 循环：换来**可观测、可恢复、可中断、可视化**

**Q5: 设计一个分布式 Agent 调度系统**

- 难度：⭐⭐⭐⭐⭐
- 标签：#分布式 #调度 #Agent

**要求** ：

- 多台机器部署 Agent
- 负载均衡
- 任务队列管理
- 容错与重试

**💡 参考答案**

**一、组件划分**
- **API/网关层**：接请求、鉴权、限流、生成 task_id
- **调度器（Controller）**：任务分发、worker 管理、扩缩容决策
- **任务队列**：持久化消息队列（Kafka/Redis Stream/RabbitMQ），支持优先级
- **Worker 池**：按资源类型分组（CPU 密集组 / GPU 推理组 / 工具组）
- **状态存储**：任务状态机 + checkpoint（PG/Redis）
- **注册中心**：worker 心跳与能力上报

**二、负载均衡**
- **无状态任务**：加权轮询 / 最少连接
- **有状态会话**：**一致性哈希**把 session 固定到节点（粘性），避免反复拉取会话状态
- **资源感知**：按 worker 类型匹配（GPU 任务不派给 CPU 节点）
- **队列深度感知**：避免把任务推给已积压的 worker

**三、任务队列管理**
- **优先级队列 + 加权公平调度**：防大任务饿死小任务
- 队列深度作为**扩容信号**
- **背压**：队列满则拒绝新请求（返回 429），而不是堆积到超时

**四、容错与重试（核心）**
1. **心跳 + 租约（lease）**：worker 失活 → 租约过期 → 任务重新入队（防任务永久卡死）
2. **checkpoint 恢复**：长任务从最后快照续跑，而不是从头重来
3. **幂等**：任务带 `task_id` + 幂等 key，重复投递不产生副作用
4. **重试策略**：指数退避 + 最大次数 + 死信队列（DLQ）
5. **隔离舱（bulkhead）**：某类任务出问题不影响其他类型
6. **优雅停机**：worker 下线前完成手头任务或交还队列

**五、扩缩容**
- K8s HPA 依据：队列深度、worker 利用率、P95 时延（而非只看 CPU）
- GPU 任务用独立节点池 + 预热，避免冷启动拉长时延

**六、可观测**
- 任务级 trace（跨 worker 传播 trace_id）
- 指标：队列深度、任务时延分布、失败率、重试率、worker 利用率

**Q6: 设计一个 LLM Gateway（API 网关）**

- 难度：⭐⭐⭐⭐
- 标签：#网关 #限流 #负载均衡

**要求** ：

- 支持多个 LLM 供应商（OpenAI、Azure、国产）
- 限流与熔断
- 成本统计
- 缓存层

**💡 参考答案**

**一、核心价值**：把"多供应商、限流、成本、缓存、可观测"从业务代码里抽出来，业务只对接一个统一端点。

**二、多供应商适配**
- **适配器模式**：统一内部接口（`chat` / `embed` / `stream`），每家一个 adapters
- **参数映射**：`temperature`/`max_tokens`/工具调用格式各家不同，需归一
- **能力矩阵**：记录每家是否支持 Function Calling / 长上下文 / 多模态 / 流式
- **错误码统一**：把各家错误映射到统一分类（限流 / 超时 / 参数错 / 内容审核失败 / 余额不足）
- **自动降级**：主供应商故障 → 按能力矩阵切到备选（不支持 FC 的模型需回退到 prompt 解析）

**三、限流与熔断**
- 维度：**租户级 + 模型级 + 全局级**三层配额
- 算法：令牌桶（允许突发）/ 漏桶（平滑）；分布式用 Redis + Lua 保证原子
- 熔断：按供应商/模型统计错误率，连续失败快速失败，半开探测恢复
- 排队：超配额进优先级队列或直接 429（按 SLA 决定）

**四、成本统计**
- 计量：按 input/output token 分别计费（输出通常贵 3–4 倍）
- 归因：**按租户/业务线/场景维度聚合**，找到"20% 的调用占 80% 成本"的头部
- 预算：租户预算告警 + 硬上限
- 缓存命中要**从成本里扣除**（体现缓存收益）

**五、缓存层**
- **精确缓存**：同模型 + 同参数 + 同 prompt → 直接返回
- **语义缓存**：query embedding 相似度超阈值 → 复用答案（企业场景命中率高，**收益最大**）
- 注意：缓存要带**权限与租户维度**的 key，否则会跨租户泄露答案

**六、其他必备**
- 鉴权与配额、审计日志、幂等、超时控制、streaming 透传、重试（仅幂等请求）

**Q7: 设计一个 Memory 管理系统（长期记忆）**

- 难度：⭐⭐⭐⭐
- 标签：#Memory #存储 #检索

**要求** ：

- 对话历史存储（短期）
- 向量检索（长期）
- 自动遗忘机制
- 个性化记忆

**💡 参考答案**

**一、四层记忆架构**
| 层 | 存储 | 生命周期 |
|----|------|----------|
| 工作记忆 | 上下文窗口 | 单次调用，token 预算管理 |
| 短期（会话） | Redis，key=`user:session` | 会话期 + TTL |
| 长期·情节 | 向量库 | 跨会话 |
| 长期·语义 | 关系库 / 图库 | 跨会话（事实、偏好） |

**二、写入链路**
抽取显著信息 → **重要性打分**（LLM）→ 摘要 + **指代消解**（让条目自包含）→ embedding → 落库，带元数据（时间、user_id、类型、来源、importance）

**三、读取链路**
query 改写 → 混合检索（向量 + BM25，RRF）→ 元数据 pre-filter（user_id 硬过滤）→ rerank → 综合打分 `相关性 × 重要性 × 时间衰减` → top-k 注入 prompt

**四、自动遗忘机制**
1. **时间衰减**：指数衰减，旧记忆自然降权
2. **重要性加权**：高分记忆衰减慢
3. **访问频率**：LRU/LFU，长期不召回者淘汰
4. **容量上限 + TTL**
5. **冲突消解**：新事实覆盖旧事实，旧版本标记过期（不物理删，保留审计）
6. **作用域隔离**：任务级记忆仅本会话有效

**五、个性化**
- **画像**（静态偏好，存 PG）+ **行为**（动态兴趣，短期窗口）+ **会话上下文**
- 检索时按偏好加权，生成时适配语气
- 反馈闭环：显式（点赞/纠正）+ 隐式（采纳/跳过）
- **隐私边界**：可查看、可删除、可关闭

**六、工程要点**
- 海量历史优化三招：**减数据**（层级摘要）/ **缩空间**（分片 + pre-filter）/ **快索引**（HNSW + rerank）
- 多租户：`user_id` 前缀 + 强制过滤
- 合规：删除权、加密、留存策略、审计

**Q8: 设计一个 Function Calling 微调数据生成系统**

- 难度：⭐⭐⭐⭐
- 标签：#FunctionCalling #数据生成 #微调

**要求** ：

- 自动生成工具调用样本
- 数据质量验证
- 格式标准化

**💡 参考答案**

**一、数据来源（多路并行）**
1. **真实线上 trace**：用户 query + 工具调用链 + 结果 + 成功标记——分布最真实
2. **强模型合成**：让大模型在**沙盒环境**跑任务，生成多轮轨迹（ToolBench / ToolLLM 思路）
3. **模板 + 扰动**：基于工具 schema 程序化生成 query（覆盖参数组合、边界值）
4. **人工示范**：核心场景写 golden trajectory

**二、生成流水线**
1. **工具池构建**：真实 API 的 schema（含参数类型、枚举、必填），保证与线上一致
2. **任务生成**：按工具组合生成 query（单工具 / 多工具串行 / 并行 / 多轮追问）
3. **轨迹生成**：模型在沙盒中实际执行（不是"编"轨迹）
4. **结果验证**：真实执行 → 检查任务是否真完成（**这是最关键的一步，靠它做拒绝采样**）
5. **拒绝采样**：只保留成功轨迹做正样本；失败但能恢复的轨迹做纠错样本
6. **格式标准化**：统一 tool_call schema（名称/参数/非空校验）
7. **去重与配比**：指纹去重 + 工具覆盖度均衡 + 长度分布控制
8. **切分与隔离**：train/val/test 按**工具维度**隔离，防"背题"

**三、质量验证（四条硬标准）**
| 标准 | 检查方式 |
|------|----------|
| **可执行性** | 参数能通过 JSON Schema 校验，能真实调用成功 |
| **可完成性** | 环境反馈确认任务达成（而非模型自称完成） |
| **多样性** | 工具覆盖度、场景分布、参数取值分布 |
| **一致性** | 同一意图的调用格式统一，无矛盾样本 |

**四、常见坑**
- **分布过窄**：只会演示过的工具 → 必须用 held-out 工具做泛化评估
- **合成数据幻觉**：模型编造不存在的参数 → 强制经过 schema 校验
- **缺少负样本**：不含"调用失败→修正"的轨迹，模型不会纠错
- **数据泄露**：评测集与训练集重叠 → 严格隔离

**五、闭环**
线上 bad case 回流 → 归因（选错工具 / 参数错）→ 补进数据集 → 定期重训 → 回归验证

**Q11: 设计一个 Agent 调试与可观测性系统**

- 难度：⭐⭐⭐⭐
- 标签：#调试 #监控 #可观测性

**要求** ：

- 链路追踪（每一步 Agent 执行）
- 日志聚合
- 指标监控（延迟、成本、错误率）
- 告警规则

**💡 参考答案**

**一、三支柱（Trace / Metrics / Logs）**

**Trace（链路追踪）——最重要**
- 一次 run 生成一棵 **span 树**：根 span = 整个请求，子 span = LLM 调用 / 工具调用 / 检索 / rerank
- 每个 span 记录：输入、输出、耗时、token、成本、状态、错误
- 技术：OpenTelemetry 语义约定 + `trace_id` 跨服务传播
- 关键能力：
  - **回放（Replay）**：用相同输入重跑，定位是否随机性问题
  - **Diff**：两个版本同输入输出对比（调 prompt 必备）
  - **失败归因**：一眼看出是哪一步出的问题

**Metrics（指标）**
- 延迟：TTFT、端到端 P50/P95/P99、各阶段耗时占比
- 成本：每 run token 成本、按场景/租户聚合
- 质量：任务成功率、工具失败率、重试率、缓存命中率
- 系统：QPS、并发数、错误率

**Logs（日志）**
- 结构化日志（JSON）+ 强制带 `trace_id` / `run_id`，便于关联
- 分级：ERROR 进告警通道，DEBUG 采样存储（否则成本爆炸）

**二、告警规则**
- 基于指标阈值 + **变化率**（如 P99 环比涨 50%）
- 分层：P0 立即电话 / P1 邮件 / P2 日报
- 抑制与聚合：避免告警风暴，同根因合并
- 告警要有**可执行的 Runbook**，否则等于噪声

**三、工具选型**
- 自建：OpenTelemetry + ClickHouse/Jaeger + Prometheus + Grafana
- 开源：**LangFuse**（LLM 专用，可自部署）
- 商业：**LangSmith**（上手快，数据出域）
- 建议组合：**Prometheus 看系统指标 + LangFuse/LangSmith 看 LLM 链路**

**四、隐私（易被忽略）**
- trace 里含用户原文，**必须脱敏 + 设置留存期**
- 按租户隔离 trace 查询权限

**Q12: 设计一个支持语音交互的 Agent**

- 难度：⭐⭐⭐⭐
- 标签：#语音交互 #多模态 #Agent

**要求** ：

- 语音识别（ASR）
- Agent 推理
- 语音合成（TTS）
- 实时性优化

**💡 参考答案**

**一、三种架构范式（先选型）**
| 范式 | 结构 | 延迟 | 特点 |
|------|------|------|------|
| **Cascaded（流水线）** | ASR → LLM → TTS | 高（叠加） | 模块可替换、可观测、易调试 |
| **Omni（端到端）** | 单一语音大模型 | 中 | 保留语气情感，但可控性差 |
| **Full-duplex（全双工）** | 可同时听与说 | 最低 | 可打断，最自然，最难做 |

**二、延迟预算（体验生死线）**
- 人类对话的自然停顿约 **200–500ms**，端到端超过 **1s** 就会明显"卡"
- 分配示例：VAD 断句 100ms + ASR 300ms + LLM TTFT 300ms + TTS 首包 200ms ≈ 900ms

**三、实时性优化（核心考点）**
1. **流式 ASR**：边说边识别（不是等说完），配合 **VAD** 检测句尾
2. **流式 LLM → 分句流式 TTS**：LLM 吐出第一个句子就送去合成，**边生成边播**——这是降延迟最有效的一招
3. **预连接 / 预热**：提前建好 ASR/TTS 连接，省握手
4. **小模型 + 缓存**：常见寒暄、确认类回应走模板/缓存，跳过 LLM
5. **推测执行**：预测用户可能要问的追问，提前预生成（谨慎使用）

**四、打断（Barge-in）——全双工必备**
- 用户开口 → 立即**中止 TTS 播放** + **取消进行中的 LLM 生成**（省成本）
- 保留已播内容到上下文，避免答非所问
- 需要回声消除（AEC）区分"自己在说"和"用户在说"

**五、传输与工程**
- **WebSocket**（双向、低延迟、支持打断），不用 SSE
- 音频编解码（Opus）、采样率对齐、jitter buffer
- 移动端弱网处理：丢包补偿、降码率

**六、可观测**
- 分阶段埋点（VAD/ASR/LLM/TTS 各自耗时），否则不知道延迟卡在哪
- 指标：端到端延迟、打断成功率、ASR 字错率、TTS 首包时间

**Q13: 设计一个 Agent 知识库更新系统**

- 难度：⭐⭐⭐
- 标签：#知识库 #增量更新 #RAG

**要求** ：

- 增量索引
- 冷热数据分离
- 版本管理
- 回滚机制

**💡 参考答案**

**一、增量索引**
- **变更检测**三种手段：文件系统监听（inotify/FSEvents）、数据库 CDC、定时扫描 + 内容 hash 比对
- 变更分流：新增 / 修改 / 删除
- **只重算受影响 chunk 的向量**（不要全量重跑）
- **upsert** 语义：同 `doc_id` 覆盖旧向量，避免重复占位
- **删除必须真删**：文档下线要移除对应向量，否则"幽灵文档"会被召回
- 批量提交（减小索引小文件碎片），定期做段合并（compaction）

**二、冷热分离**
- **热层**：近 3 个月 / 高频访问文档 → 内存或 SSD，高副本数
- **冷层**：历史文档 → 对象存储 + 低副本
- 查询策略：**先查热层，不足再下探冷层**，兼顾延迟与召回
- 冷热迁移：按访问频率与时�效自动分层

**三、版本管理**
- `doc_id + version`，支持多版本共存
- **embedding 模型版本必须对齐**：换 embedding 模型 = 向量空间变了 → **必须全量重建**，不能新旧混用（这是最致命的坑）
- 元数据带 `valid_from` / `valid_to`，支持时序查询
- 索引本身版本化（index_v1 / index_v2）

**四、回滚机制**
- **别名切换**（类似 ES alias）：新索引建好、验证通过后**原子切换**别名，出问题立刻切回
- 零停机更新：双写/影子索引 → 校验 → 切换 → 清理旧索引
- 变更审计：谁在何时改了什么，可追溯

**五、一致性保障**
- 新旧文档**走同一套解析/切块/元数据管线**，防分布漂移
- 分桶监控：分别统计新/旧文档的召回率，发现偏斜立即告警
- 影子检索：新索引上线前用固定 query 集对比新旧召回分布

**Q15: 设计一个混合检索系统（向量 + BM25 + 图检索）**

**要求** ：

- 三种检索并行
- 结果融合算法
- 性能优化
- 召回率与精度平衡

**💡 参考答案**

**一、三路检索的分工（先讲清互补性，这是设计前提）**
| 通路 | 擅长 | 弱于 |

| **向量** | 语义相近、同义改写 | 精确词、编号、ID、长尾实体 |

| **图检索** | 多跳关系、全局性问题 | 描述性、非结构化内容 |

**二、并行执行**
- 三路**同时发起**（`asyncio.gather`），总耗时 ≈ 最慢那一路，而非三者之和
- **各自独立超时与降级**：某一路超时/失败不影响整体（`return_exceptions=True`）
- 元数据过滤（权限/时间/租户）在三路都要生效

**三、融合算法**
1. **RRF（倒数排名融合）——推荐首选**
   - `score(d) = Σ 1/(k + rank_i(d))`，k 常取 60
   - 优点：**只看排名、无需分数归一化**（三路分数量纲完全不同，归一化很难做对）
   - 缺点：丢弃了分数信息（可用加权 RRF 弥补：不同通路给不同权重）
2. **加权求和**：需要先把各路分数归一化（min-max / z-score），调参麻烦，易被某一路主导
3. **路由式（省成本）**：先判断问题类型，只跑必要通路
   - 事实型 → 向量 + BM25
   - 关系型 → 向量 + 图
   - 复杂型 → 三路全开
   - **这是控制成本的关键闸门**：三路全跑的代价是单路的 3 倍

**四、性能优化**
- 索引层：向量用 HNSW + 量化；BM25 用倒排 + 缓存；图用邻居预取
- 召回量控制：每路只取 top-50，融后 rerank
- 缓存：热点 query 的融合结果缓存
- 分片副本水平扩展

**五、召回率与精度的平衡（面试官最想听这个）**
- 思路：**召回端宁滥勿缺（多路并举提召回率），重排端宁缺勿滥（rerank 提精度）**
- 具体：
  1. 三路各取较大 top-k（提高召回上限）
  2. RRF 融合去重
  3. **cross-encoder rerank 精排**（把精度拉回来）
  4. 阈值过滤 + 控制在 3–8 条送生成
- 调参：用评测集的 **Recall@k（召回）与 NDCG（精度）双指标**联合优化，避免只优化一个

**Q1: 如何将 RAG 系统的 P99 延迟从 2s 降低到 300ms？**

- 难度：⭐⭐⭐⭐
- 公司：字节（真题）
- 标签：#性能优化 #延迟 #RAG

**优化方向** ：

- 检索优化（800ms → 200ms）
- 生成优化（1000ms → 100ms）
- 缓存策略
- 并行处理

**💡 参考答案**

**第零步：先测量，别猜（面试必答的第一步）**
- 拆解 P99 的耗时构成：网关 / query 改写 / 检索 / rerank / LLM TTFT / 生成总时长 / 后处理
- 没有这一步，优化就是盲人摸象；很多团队 2s 里 1s 是**串行的等待**而非算力不足

**一、检索 800ms → 200ms**
- **并行双路**：向量 ‖ BM25，而不是串行（直接省一半）
- **ANN 索引调优**：HNSW 调小 `efSearch`；IVF 调小 `nprobe`（精度换速度，用召回率兜底）
- **量化**：PQ/SQ 降内存、提速度
- **预过滤**：标量过滤先缩小候选集，避免全库扫描
- **减少召回量**：粗排取 50 而非 500，精度交给 rerank
- **分片 + 读副本**：水平扩展并发能力
- **缓存**：query embedding 缓存 + **语义缓存**（命中直接返回，跳过整条链路）

**二、生成 1000ms → 100ms（用户感知口径）**
- ⚠️ 关键认知：**1000ms→100ms 靠的是"感知延迟"，不是真的算完**
- **流式输出（SSE）**：TTFT 200ms 就开始吐字，用户体感从"等 2s"变成"立刻有反应"
- **小模型路由**：简单问题用小模型/蒸馏模型（延迟降 3–5 倍）
- **prompt 压缩**：只送 top-3 + 上下文压缩，**输入长度直接决定 prefill 耗时**
- **限制 max_tokens** + 要求简洁
- **推理引擎**：vLLM continuous batching + paged attention + prefix cache 复用
- **量化**：INT8/FP8

**三、缓存策略**
- 语义缓存（企业场景命中率 30–50%）
- 精确缓存（同 prompt）
- 分层：结果缓存 / embedding 缓存 / 检索结果缓存

**四、并行与架构**
- 权限校验 ‖ 记忆读取 ‖ 检索 全部并行
- 快慢双链路 + 难度路由
- 就近部署、连接复用（gRPC/HTTP2）、模型预热

**五、兜底**
- 降级：rerank 超时 → 用粗排；LLM 超时 → 返回检索摘要
- 目标：**P99 达标的同时，P50 也变好**，而不是把长尾藏起来

**Q2: 如何将 Agent 系统的 API 成本降低 70%？**

- 难度：⭐⭐⭐⭐
- 标签：#成本优化 #Agent #API

**优化策略** ：

- Semantic Cache
- Prompt 压缩
- 智能降级（GPT-4 → GPT-3.5）
- 批处理

**💡 参考答案**

**第零步：先做成本归因**
- 按租户 / 场景 / 调用类型聚合，验证**帕累托法则**（通常 20% 的调用吃掉 80% 成本）
- 区分 input token 成本与 output token 成本（output 通常贵 3–4 倍）——**优化 output 的杠杆更大**

**一、语义缓存（单项收益最大）**
- query embedding 相似度 > 阈值 → 复用答案
- 企业/客服场景命中率可达 **30–50%**，直接砍掉一半成本
- 注意：缓存 key 要含**租户 + 权限维度**，否则跨租户泄露

**二、模型分层路由（智能降级）**
- 简单任务（FAQ、意图分类、槽位抽取、改写）→ 小模型
- 复杂任务（多步推理、长文写作）→ 大模型
- 实现：难度分类器 + 能力矩阵；先按小模型答，**置信度低再升级**（cascade）
- 收益：把 70–80% 的流量从大模型挪走，成本降幅最大

**三、Prompt 压缩**
- 上下文裁剪：只送 top-3 而非 top-10
- **历史压缩**：滚动摘要替代全量历史（多轮场景省得最多）
- 工具 schema 精简：只注入当前可能用到的工具（Tool RAG）
- 去冗余：删掉重复的材料副本、模板化说明

**四、减少调用次数**
- 合并调用：一次抽取多个字段，而不是多次往返
- 避免无效循环：设最大步数与收敛条件，防"再搜一次"式空转
- 确定性逻辑用代码而非 LLM

**五、批处理**
- 离线任务（索引构建、批量标注、评测）用 **Batch API**，通常有 50% 折扣
- 实时请求用 continuous batching 提升吞吐摊薄成本

**六、输出侧控制**
- 限制 `max_tokens`、要求简洁、结构化输出（JSON 比散文短）
- 流式下可提前中止（用户已满足）

**七、自建/蒸馏（长期）**
- 高频场景蒸馏小模型自部署，边际成本趋近于算力成本
- 量化模型降低显存与推理成本

**八、监控闭环**
- 成本看板 + 预算告警；每次优化都要验证"质量没退化"（否则省了钱丢了体验）

**Q3: 如何优化向量检索的召回速度？**

- 难度：⭐⭐⭐
- 标签：#向量检索 #优化 #RAG

**优化方向** ：

- 索引选择（IVF、HNSW）
- 维度压缩
- 分片策略
- GPU 加速

**💡 参考答案**

**一、索引选型与调参（第一杠杆）**
- **HNSW**：图索引，高召回、低延迟，内存占用大 → 在线检索首选；调小 `efSearch` 可线性提速（精度换）
- **IVF**：聚类 + 倒排，内存友好 → 超大规模、可接受略低召回；调小 `nprobe` 提速
- **IVF-PQ / DiskANN**：极致省内存，适合冷数据或超大规模
- 实践：**先按召回率达标定位参数，再压延迟**

**二、量化与维度压缩**
- **标量量化 SQ**（FP32→INT8）：4× 内存压缩，召回损失小（推荐优先）
- **乘积量化 PQ**：压缩比更高，召回损失更大，需重排序补偿
- **维度压缩**：Matryoshka 截断（如 1024→256）、PCA 降维——维度减半，距离计算量减半

**三、分片与副本**
- 水平分片：数据切分到多节点，单节点搜索空间变小
- **读副本**：分摊 QPS，提升并发吞吐
- 分片键设计要避免热点（按 ID 哈希，不要按时间）

**四、GPU 加速**
- Milvus GPU / cuVS 等 GPU 版 ANN，构建与查询都大幅提速
- 适合高 QPS 或超大规模场景；成本较高，需算 ROI

**五、检索策略优化**
- **预过滤（pre-filter）**：先用标量条件（时间/租户/类型）缩小候选集，再向量检索——**收益常被低估**
- 减少 top-k：粗排取够用即可，精度交给 rerank
- 批量查询合并成一次请求（减少往返与固定开销）

**六、缓存与架构**
- query embedding 缓存（同 query 免重复编码）
- 热点查询结果缓存
- 异步/并行：向量检索与 BM25 并行，而非串行

**七、度量**
- 关注：QPS、P95/P99 检索延迟、**Recall@k（防止提速牺牲召回）**、内存占用
- 每次调参都要回归验证召回率，否则"变快了但找不到了"

**Q4: 如何处理 Agent 的长对话场景（> 10 轮）？**

- 难度：⭐⭐⭐⭐
- 标签：#Agent #长对话 #Memory

**优化策略** ：

- Memory 压缩
- 滑动窗口
- 摘要生成
- 重要信息提取

**💡 参考答案**

**一、上下文组装的三段式（核心框架）**
```
[系统 prompt] + [滚动摘要（旧）] + [最近 N 轮原文] + [相关长期记忆] + [当前工具结果]
```
- token 预算严格分配，超出时按优先级裁剪（先砍最老的历史）

**二、压缩手段**
1. **滑动窗口**：保留最近 N 轮**原文**（保证近期细节精确）
2. **滚动摘要**：更早的对话压缩成摘要，**增量更新**（不是每轮重算全量，省 token）
3. **结构化状态提取（最强的一招）**：把"任务进度、已确认约束、槽位值"抽成**独立 state 字段**
   - 例：`{目的地: 成都, 天数: 3, 预算: 5000, 偏好: 不吃辣}`
   - 好处：**约束不会因对话被压缩而丢失**——这是长对话最容易出的 bug（用户第 2 轮说的条件第 15 轮就"忘了"）
4. **长期记忆外部化**：不重要的细节写进向量库，**按需检索回注**，而不是常驻上下文

**三、重要信息提取**
- 用 LLM 判断每轮信息的重要性，只保留高价值内容进摘要
- 显式区分：**约束类（必须保留）** vs 闲聊类（可丢）

**四、工程手段**
- **KV Cache / Prompt Cache 复用**：system prompt 前缀不变 → 复用缓存，省时省钱
- 上下文压缩：对召回的旧内容做摘要而非原文塞入
- 分层存储：热会话在 Redis，冷会话归档

**五、质量保障**
- 定期做**约束回溯检查**（生成前校验 state 中的约束是否被满足）
- 评测集专门覆盖"长对话中的约束保持"场景
- **允许主动追问**：状态缺失时问用户，而不是猜

**Q5: 如何优化 LLM 的推理吞吐量？**

- 难度：⭐⭐⭐⭐
- 标签：#推理优化 #吞吐量 #LLM

**优化方向** ：

- Batch 推理
- KV Cache
- 量化（INT8）
- 模型并行

**💡 参考答案**

**一、批处理（第一杠杆）**
- **Continuous Batching（连续批处理）**：不等整批结束就插入新请求，GPU 利用率大幅提升 → 现代推理引擎（vLLM/TensorRT-LLM）标配
- **动态批处理**：按当前负载动态组批
- **Chunked Prefill**：把长 prompt 的 prefill 切块，与 decode 交错执行，避免长请求阻塞短请求

**二、KV Cache 优化**
- **Paged Attention**：分页管理 KV cache，消除内存碎片，显存利用率大幅提升
- **Prefix Caching**：相同 system prompt 前缀复用 KV，避免重复计算（RAG/Agent 场景收益极大）
- **KV cache 量化**：FP16 → INT8/FP8，显存减半

**三、量化**
- 权重 INT8/FP8/AWQ/GPTQ：显存降、吞吐升、精度损失可控
- KV cache 量化 + 激活量化
- 实践：**默认上 INT8**，精度敏感场景先做评测

**四、并行策略**
- **张量并行（TP）**：单层内切分，适合单机多卡
- **流水线并行（PP）**：按层切分，跨机
- **数据并行（DP）**：多副本分摊请求
- 组合：大模型用 TP+PP，小模型用 DP 扩副本

**五、调度与架构**
- 请求调度：优先级队列 + 公平调度，防大请求饿死小请求
- **Prefill / Decode 分离部署**：两类负载特性不同（prefill 算力密集、decode 访存密集），分开部署各取最优
- 多副本 + 负载均衡
- 投机解码（draft model）加速生成

**六、度量**
- 关注：**吞吐（tokens/s）**、**TTFT**、**TPOT（每 token 时间）**、GPU 利用率、显存占用
- 权衡：吞吐与延迟常矛盾——批越大吞吐越高但单请求延迟越长，需按 SLA 选点

**Q6: 如何实现 Agent 的异常重试机制？**

- 难度：⭐⭐⭐
- 标签：#异常处理 #重试 #Agent

**设计要点** ：

- 指数退避
- 最大重试次数
- 幂等性保证
- 降级策略

**💡 参考答案**

**一、先分类（最重要，很多人跳过）**
| 类型 | 例子 | 处理 |
|------|------|------|
| **可重试** | 超时、5xx、限流 429、连接失败 | 重试 |
| **不可重试** | 4xx 参数错、权限不足、内容审核拒绝 | **重试无意义**，改参数或升级 |
| **业务失败** | 工具返回空结果 | 换策略（改查询、换工具） |

**二、指数退避 + 抖动**
- 延迟 = `base × 2^n`，加**随机抖动**（避免惊群同步重试）
- 允许服务端返回的 `Retry-After` 覆盖本地策略

**三、次数与预算**
- **最大重试次数**（如 3 次）+ **总超时预算**（如 10s）——两个都要设
- 超预算立即走降级，避免拖死整条链路

**四、幂等性保证（写操作必做）**
- 幂等 key（`idempotency_key = task_id + step`），服务端去重
- 读操作天然幂等，可放心重试
- **副作用操作（退款、下单）重试前必须确认幂等**，否则会重复扣款

**五、熔断与降级**
- **熔断**：某工具/供应商连续失败 → 快速失败（半开探测恢复）
- **降级链**：备用工具 → 备用模型 → 缓存结果 → 默认值 → 转人工
- 降级要**对用户透明**（明确告知"当前使用备用方案"）

**六、跳出机制（防死循环）**
- 相同错误 hash 去重：重复同样错误直接跳出
- 收益递减检测：越改越差就停
- 全局最大步数上限

**七、错误反馈给模型**
- 把失败原因**结构化 + 自然语言化**回传（"参数 city 必填"），让 LLM 自我修正——这比单纯技术重试更能解决问题

**八、可观测**
- 记录重试次数分布、失败类型分布，用于优化工具与 prompt

**Q7: 如何实现 RAG 的增量索引更新？**

- 难度：⭐⭐⭐
- 标签：#增量更新 #索引 #RAG

**设计要点** ：

- 新文档自动检测
- 增量向量化
- 索引合并
- 热更新

**💡 参考答案**

**一、变更检测**
- 文件系统监听（inotify / FSEvents）——本地/网盘同步场景
- 数据库 **CDC**（binlog/WAL）——数据源是 DB 时最可靠
- 定时扫描 + **内容 hash 比对**——兜底方案，防监听漏事件
- 变更分类：新增 / 修改 / 删除

**二、增量向量化**
- 只对**变更文档的 chunk** 重算 embedding，不碰其他数据
- 按 manifest 比对（chunk_id → hash），跳过未变内容
- 批量提交（如 512 条/批）平衡吞吐与延迟
- **删除必须真删**：移除对应向量，否则"幽灵文档"持续被召回

**三、索引合并**
- 向量库：`upsert`（同 doc_id 覆盖）
- 全文索引：增量 commit + 定期段合并（避免小文件碎片）
- 图库：只更新受影响子图（→ GraphRAG 增量更新）
- 缓存：**失效相关查询缓存**（否则用户拿到旧答案）

**四、热更新（零停机）**
- **双索引 + 别名切换**（ES alias 思路）：
  1. 新索引写入并构建完成
  2. 用固定 query 集校验新旧召回差异
  3. **原子切换别名**指向新索引
  4. 清理旧索引
- 增量场景可直接 upsert（无需重建），但**换 embedding 模型必须全量重建**

**五、一致性与监控**
- 新旧文档走**同一套解析/切块管线**，防分布漂移
- 分桶监控：新/旧文档的召回率分别统计
- 延迟指标：从文档变更到可检索的**端到端时延**
- 失败重试：失败的文档进死信队列，人工介入

**Q8: 如何实现 Agent 的并发控制？**

- 难度：⭐⭐⭐⭐
- 标签：#并发控制 #Agent #分布式

**设计要点** ：

- 任务队列
- 限流策略
- 资源池管理
- 死锁避免

**💡 参考答案**

**一、任务队列**
- 持久化队列（Kafka / Redis Stream / RabbitMQ），防丢失
- **优先级 + 加权公平调度**：防大任务饿死小任务
- 队列深度作为扩容与背压信号；**队列满则拒绝（429）而非堆积**

**二、限流策略**
- 三层：**租户级 / 用户级 / 全局级**配额
- 算法：令牌桶（允许突发）或漏桶（平滑输出）
- 分布式限流用 **Redis + Lua** 保证原子性
- 按资源维度限：不只是 QPS，还有 **LLM 并发数**（GPU 是真实瓶颈）

**三、资源池管理**
- 连接池（HTTP/DB）、worker 池、GPU 批处理池
- **按任务类型分池**：LLM 密集 / IO 密集 / 工具密集分开，避免互相阻塞
- 池大小按下游承载能力设，不是越大越好

**四、Agent 特有的并发问题**
1. **会话级串行化**：同一 session 的请求**必须排队**（actor 模型），否则并发写状态会互相覆盖
2. **跨会话并行**：不同 session 完全并行
3. **状态并发写**：乐观锁（版本号 CAS）或分布式锁；冲突则重试
4. **多 Agent 并行**：fan-out 后需 **join（barrier）** 等齐再合并
5. **幂等**：并发重试不产生重复副作用

**五、死锁避免**
- 统一**加锁顺序**（按资源 ID 排序加锁）
- **超时释放**：锁带 TTL，防持有者崩溃导致永久锁
- 避免嵌套锁；能用无锁结构（原子操作/CAS）就不用锁
- 死锁检测：定期扫描等待图（复杂系统才需要）

**六、背压与隔离**
- 隔离舱：单租户/单任务类型故障不影响全局
- 熔断：下游异常时快速失败，防级联雪崩
- 优雅停机：完成手头任务再下线

**Q9: 如何实现 LLM 响应的流式处理？**

- 难度：⭐⭐⭐
- 标签：#流式处理 #WebSocket #SSE

**实现要点** ：

- Server-Sent Events
- WebSocket
- 背压处理
- 错误恢复

**💡 参考答案**

**一、协议选型**
| | SSE | WebSocket |
|---|---|---|
| 方向 | 单向（服务端→客户端） | 双向 |
| 复杂度 | 低，HTTP 原生 | 高，需握手与心跳 |
| 重连 | **自动**（`Last-Event-ID`） | 需自己实现 |
| 适用 | **LLM 输出（首选）** | 需打断 / 语音 / 多模态 |

- 结论：**纯 LLM 文本输出用 SSE**；语音对话、需要用户中途打断的场景用 WebSocket

**二、传输实现**
- LLM 响应**直接透传**，不要中间缓冲
- ⚠️ **必踩的坑**：Nginx / 网关默认 `proxy_buffering on` 会把流"攒"起来 → 必须关闭，并设 `X-Accel-Buffering: no`
- 定义结构化 event：`retrieval` / `token` / `citation` / `done` / `error`
- 心跳（注释行 `:ping`）保活，防反向代理超时断连

**三、背压处理**
- 客户端消费慢 → 服务端缓冲有上限，超限则**暂停上游生成**或丢弃低价值分片
- 不能无限缓冲（内存爆炸）；也不能无脑丢（内容不完整）
- 实践：设置`高水位/低水位`，水位以上暂停读取上游流

**四、错误恢复**
- SSE：`event id` + 客户端 `Last-Event-ID` 请求头 → 服务端从断点续传
- 断点续传需要服务端**缓存已生成内容**（或支持重新生成并跳过前缀）
- 无法续传时：明确告知用户 + 提供重试按钮
- 部分失败的中间态要能优雅收尾（已生成内容仍可用）

**五、前端配合**
- 逐字渲染 + Markdown **增量解析**（不要等全文）
- 可中断：用户点击停止 → 前端 abort + 服务端取消 LLM 请求（**省成本**）
- 引用角标随生成逐步出现，最后回填

**六、可观测**
- 单独监控 **TTFT（首 token 时间）**、分片间隔、流中断率

**Q10: 如何实现跨模型的统一 API？**

- 难度：⭐⭐⭐
- 标签：#API设计 #适配器模式 #统一接口

**设计要点** ：

- 适配器模式
- 参数映射
- 错误码统一
- 降级兼容

**💡 参考答案**

**一、适配器模式（核心）**
- 定义统一内部接口：`chat()` / `embed()` / `stream()` / `tool_call()`
- 每个供应商一个 adapter，把厂商格式 ↔ 内部格式互转
- 业务代码只依赖内部接口 → 换模型不改业务

**二、参数映射**
- 通用参数归一：`temperature` / `max_tokens` / `top_p` / `stop` / 超时
- **差异处理**：
  - 工具调用格式各家不同（`tools` vs `functions`，参数 JSON vs 字符串）
  - 有的模型不支持 system role（需拼进 user）
  - 有的不支持并行工具调用
- **能力矩阵**：显式声明每家支持什么，不支持时**自动降级**（如 FC 不支持 → 回退到 prompt 解析 JSON）

**三、错误码统一**
- 把各家错误映射到内部分类：`RATE_LIMIT` / `TIMEOUT` / `INVALID_PARAM` / `CONTENT_FILTER` / `INSUFFICIENT_QUOTA` / `SERVER_ERROR`
- 业务侧只处理内部错误码 → 逻辑稳定
- 保留原始错误详情用于排查（trace 里存）

**四、降级兼容**
- 主备路由：主供应商故障 → 按能力矩阵切备选
- 降级要保证**语义等价**（不支持长上下文时自动截断并告知）
- 灰度：新模型先小流量验证

**五、流式协议统一**
- 各家流式格式不同（OpenAI delta vs 其他）→ 统一转成内部 SSE 事件格式输出

**六、配套**
- 鉴权与配额、成本计量、幂等、重试、超时、审计
- **可观测**：trace 标注实际使用的供应商与模型版本

**Q11: 如何实现 Agent 的状态持久化？**

- 难度：⭐⭐⭐
- 标签：#状态管理 #持久化 #Agent

**设计要点** ：

- 状态序列化
- 数据库选择（Redis、MongoDB）
- 断点续传
- 状态恢复

**💡 参考答案**

**一、先明确"状态"包含什么**
- 消息列表（对话历史）
- **槽位与任务进度**（结构化字段，最关键）
- 工具调用结果与中间产物
- 循环计数、预算消耗
- 版本号（并发控制）

**二、状态序列化**
- 格式：JSON（可读易调试）或 MessagePack（紧凑高效）
- **版本兼容（易被忽略）**：状态加 `schema_version`，升级后要能读旧快照（做迁移或兼容读取），否则部署即丢会话
- 大产物（文件/图片）不放状态里，存对象存储只放引用

**三、存储选型**
| 存储 | 适合 | 说明 |
|------|------|------|
| **Redis** | 会话热态 | 快、TTL 自动过期；**持久性弱**，需 AOF/RDB |
| **PostgreSQL** | 权威存储 / 审计 | 事务强、可查询；配 JSONB 存状态 |
| **MongoDB** | 文档型状态 | schema 灵活，适合结构多变的会话 |
| **对象存储** | 大产物 / 归档 | 便宜 |

- 实践：**Redis 做热态加速 + PG 做权威持久化**（双写，Redis 挂了能回源）

**四、断点续传**
- **checkpoint 粒度**：每步（精确但写放大）vs 每节点（平衡）——按任务时长选
- 长任务（分钟级）必须支持：worker 崩溃/重启/部署时从最近 checkpoint 恢复
- 与人机中断（HITL）配合：暂停等审批 → 恢复继续

**五、状态恢复**
- 恢复 = 读快照 + **重放后续操作**（需操作可重放）
- 重放要幂等，否则会重复副作用
- 提供**时间旅行**能力（回到任意历史状态）用于调试

**六、隔离与一致性**
- key 设计：`session:{tenant}:{user}:{session_id}`，多租户强隔离
- 会话级串行化（同 session 排队），防并发写覆盖
- 乐观锁（版本号 CAS）或分布式锁
- TTL 与归档：会话结束转冷存储，避免无限增长

**Q12: 如何实现 RAG 的多语言支持？**

- 难度：⭐⭐⭐
- 标签：#多语言 #RAG #国际化

**实现要点** ：

- 多语言 Embedding 模型
- 语言检测
- 跨语言检索
- 生成语言控制

**💡 参考答案**

**一、Embedding 模型（决定跨语言能力）**
- 选**多语言/跨语言对齐**的模型：
  - 通用多语：`bge-m3`（中英+多语，支持长文本）、`multilingual-e5`、`text-embedding-3`
  - 中文优先：`bge-large-zh`
- 关键要求：**跨语言语义对齐**——中文 query 能召回英文文档（同一语义空间中距离近）

**二、语言检测**
- query 语言识别（fastText / langdetect，或直接用 LLM）
- 用途：决定检索语言、生成语言、分词方式
- 混合语言 query（中英夹杂）要单独处理（技术文档常见）

**三、跨语言检索（两条路线）**
1. **统一向量空间**（推荐）：多语 embedding 直接跨语言检索，无需翻译
2. **翻译桥接**：query 翻译成文档语言再检索
   - 优点：可用单语强模型（中文 bge-large-zh）
   - 缺点：翻译引入误差与延迟
3. **双路混合**：翻译路 + 多语向量路并行，RRF 融合——**最稳但最贵**
- 也支持"反向"：把文档离线翻译成统一语言入库

**四、生成语言控制**
- prompt 明确指定输出语言，**与用户 query 语言一致**
- 检索到英文材料、用户问中文 → 要求**用中文回答但保留专有名词原文**
- 多语言引用：引用原文 + 可选翻译

**五、分词与切块差异**
- CJK：需分词（jieba / IK），按字符或词切
- 西文：按空格/句子切，注意词形还原（stemming）
- **同一索引混多语言时，BM25 分词器要用多语方案**，否则某语言检索质量骤降

**六、评估（易被忽略）**
- **必须分语言统计指标**——只报平均值会掩盖某语言的严重问题
- 覆盖：单语检索、跨语检索、混合语言 query
- 关注"低资源语言"的表现短板

**Q1: LangChain vs LlamaIndex vs AutoGen，如何选择？**

- 难度：⭐⭐⭐
- 公司：所有公司（通用题）
- 标签：#框架选型 #对比分析

| 框架 | 定位 | 适合场景 |
|------|------|----------|
| **LangChain**（+LangGraph） | 通用**编排**框架 | 复杂业务流程、工具编排、单/多 Agent 状态图 |

  3. 核心是**多角色对话协作** → AutoGen

- **一句话**：**不是选最强的，是选最贴合场景的**；先明确"我的核心难点是检索、编排还是协作"。

**Q2: 向量数据库选型：Milvus vs Weaviate vs Pinecone vs Chroma**

- 难度：⭐⭐⭐
- 标签：#向量数据库 #选型

**对比维度** ：

- 性能（QPS、延迟）
- 功能（混合检索、过滤）
- 部署（自建 vs 云服务）
- 成本

**💡 参考答案**

| 库 | 部署 | 特点 | 适合 |
|----|------|------|------|
| **Milvus** | 自建（云原生） | 分布式、索引类型全（HNSW/IVF/DiskANN）、GPU 支持、功能最强 | 大规模生产，有运维能力 |
| **Weaviate** | 自建/云 | Go 编写、**混合搜索内置**、模块化（向量化模块） | 要开箱混合检索 |
| **Pinecone** | 全托管 SaaS | 零运维、稳定、生态好 | 快速上线、无运维团队（数据出域需评估） |
| **Chroma** | 嵌入式 | 极轻、pip 即用、开发体验好 | PoC / 本地开发 / 小规模 |
| *补充* **pgvector** | PG 扩展 | 零新组件、事务一致、SQL 过滤强 | 中小规模、已有 PG 栈 |
| *补充* **Qdrant** | 自建/云 | Rust、性能好、过滤能力强 | 性价比之选 |

- **决策维度（面试按这四个答）**：
  1. **规模与性能**：亿级 → Milvus/Qdrant；百万级 → pgvector 够用
  2. **功能需求**：要混合检索 → Weaviate/Milvus；要复杂标量过滤 → Qdrant/pgvector
  3. **部署与运维**：无运维 → Pinecone；要私有化 → Milvus/Qdrant
  4. **成本**：SaaS 按量贵但省人力；自建便宜但需人力
- **关键提醒**：先看**过滤能力（pre-filter）与混合检索**是否够用，再看性能——很多项目败在过滤支持弱，而不是 QPS 不够。

**Q3: Memory 框架选型：Mem0 vs Zep vs LangChain Memory**

- 难度：⭐⭐⭐
- 标签：#Memory #框架选型

**💡 参考答案**

| 方案 | 定位 | 优点 | 缺点 |
|------|------|------|------|
| **LangChain Memory** | 基础记忆组件 | 轻量、灵活、与 LangChain 生态一体 | **需自己接存储**；并发隔离要自己做（易踩坑）；无自动抽取/衰减 |
| **Mem0** | 记忆层（开源+托管） | **自动抽取/更新/去重/衰减**，支持图记忆，接入简单 | 抽象较重，深度定制受限 |
| **Zep** | 生产级记忆服务 | 会话记忆 + 事实抽取 + **时间知识图谱**，低延迟 | 需部署依赖（图库），学习成本 |

- **选型建议**：
  1. **快速原型 / 已有 LangChain 栈** → LangChain Memory（+ Redis 持久化）
  2. **要开箱的记忆管理能力**（自动抽取、去重、衰减）→ Mem0 / Zep

- **选型时必查的四点**：
  1. **多租户隔离**是否原生支持（别自己补）
  2. **可删除性**（合规要求"被遗忘权"）
  3. **延迟**（记忆检索在关键路径上）
  4. **成本**（记忆写入本身也消耗 LLM 调用）
- **提醒**：框架能省事，但**"写什么/读什么/何时忘"的策略仍要自己定**——这才是记忆系统的难点，不是框架能替代的。

  4. 成本（API 费用 vs GPU 成本）与数据合规
- **关键提醒**：
  - **MTEB/C-MTEB 榜单只作初筛**，必须用自有标注集验证
  - 垂直领域（医疗/金融/代码）**微调 embedding 的收益常大于换模型**

**Q5: LLM 选型：GPT-4 vs Claude vs Llama vs 国产大模型**

- 难度：⭐⭐⭐
- 标签：#LLM #模型选型

**选型决策树** ：

- 任务类型（推理、代码、创作）
- 成本预算
- 部署方式（API vs 私有化）
- 合规要求

**💡 参考答案**

| 模型 | 优势 | 短板 | 部署 |
|------|------|------|------|
| **GPT-4 系** | 综合能力最强、生态最全 | 贵、数据出域 | API |
| **Claude** | 长上下文、代码、写作、Agent 能力强 | 贵、数据出域 | API |
| **Llama 系** | 开源可私有化、可微调、成本可控 | 需自运维、能力略逊 | 自部署 |
| **国产（Qwen / DeepSeek / GLM 等）** | 中文好、**合规友好**、性价比高、可私有化 | 生态略弱 | API + 自部署 |

**决策树（按顺序问）**：
1. **合规/数据能否出域**？不能 → 只能私有化（Llama / 国产开源）
2. **任务是什么**？代码/复杂 Agent → Claude/GPT；中文业务 → 国产；长上下文 → Claude/国产长上下文模型
3. **成本预算**？紧 → 国产/小模型；松 → 顶级模型
4. **是否需要微调**？需要 → 开源模型

**实践原则（关键）**：
- **不要选一个模型，要建"模型分层"**：简单任务小模型、复杂任务大模型，配**难度路由**
- 建**能力矩阵 + 成本台账**，按场景分配
- **多供应商冗余**：单一供应商故障会直接宕机（用 Gateway 统一接入）
- **持续评测**：模型迭代快，定期用自有评测集复评，别吃"发布时的印象"
- 警惕**锁定**：抽象出统一接口，换模型成本才可控

**Q6: Agent 框架选型：LangGraph vs CrewAI vs AutoGen**

- 难度：⭐⭐⭐
- 标签：#Agent #框架选型

**💡 参考答案**

| 框架 | 核心抽象 | 优势 | 适合 |
|------|----------|------|------|
| **LangGraph** | **状态图**（节点+边+reducer） | 精细控制、支持循环/条件跳转/持久化/人机中断 | 复杂可控的工作流、生产级 Agent |
| **CrewAI** | **角色团队**（Crews + Flows） | 抽象简洁、上手快、贴近人类分工 | 内容生成、研究类协作，快速搭多 Agent |
| **AutoGen**（/AG2） | **对话**（多 Agent 群聊） | 代码执行强、灵活的多轮研讨 | 研究型任务、自动化探索 |

- **选型判据**：
  1. **要精细控制状态与流程** → LangGraph（可观测、可恢复、可中断是生产刚需）
  2. **要快速搭多角色协作** → CrewAI
  3. **要多个 Agent 自由研讨** → AutoGen
- **注意**：
  - CrewAI/AutoGen 的"自由协作"在**生产环境难控**——容易出现无限对话、成本失控
  - LangGraph 的图结构虽然学习曲线陡，但**可控性和可运维性最好**
  - 与底层框架解耦：业务能力（工具/记忆）尽量做成框架无关的模块
- **一句话**：**Demo 阶段选上手快的，生产阶段选可控的**。

**Q7: 文档解析框架选型：LlamaParse vs Unstructured vs PyMuPDF**

- 难度：⭐⭐
- 标签：#文档解析 #RAG

**💡 参考答案**

| 方案 | 原理 | 质量 | 速度/成本 | 适合 |
|------|------|------|-----------|------|
| **LlamaParse** | LLM 驱动解析 | **复杂 PDF 最好**（表格、多栏、图表） | 慢、收费（云端，数据出域） | 版式复杂且预算充足 |
| **Unstructured** | 规则 + 模型混合，可自部署 | 中等偏上，格式覆盖广 | 中等 | 要私有化 + 多格式支持 |
| **PyMuPDF** | 规则式（文本层直接抽取） | 简单 PDF 好，**复杂版式/表格弱** | **最快、免费** | 文本型 PDF、批量预处理 |

- **决策**：
  1. **复杂 PDF（扫描件/多栏/表格）且能接受成本** → LlamaParse
  2. **要私有化 + 格式种类多** → Unstructured
  3. **文本型 PDF / 大批量快速分流** → PyMuPDF
- **生产推荐组合（性价比最高）**：
  - **PyMuPDF 先做快速分流**：能干净抽取的直接用
  - 判定为"复杂页"（无文本层、表格密集、多栏）→ 送 LlamaParse / **OCR（PaddleOCR 等）**
  - 既省成本又保质量
- **关键提醒**：**文档解析质量是 RAG 的上限**——解析错乱（表格串行、页眉页脚混入）后面怎么调检索都救不回来。宁可在这里多花时间。

**Q8: 异步任务队列选型：Celery vs RQ vs Dramatiq**

- 难度：⭐⭐
- 标签：#任务队列 #异步处理

**💡 参考答案**

| 队列 | 依赖 | 优势 | 短板 |
|------|------|------|------|
| **Celery** | Broker（Redis/RabbitMQ） | **生态最成熟**、功能全（定时/路由/重试/多队列）、社区大 | 配置复杂、坑多、调试难 |
| **RQ** | Redis | **极简直观**、代码少、易上手 | 功能相对少、依赖 Redis |
| **Dramatiq** | Redis/RabbitMQ | 轻量、**可靠（默认重试+死信）**、API 简洁、性能好 | 生态较小 |

- **决策**：
  1. **需要复杂编排 / 定时任务 / 多队列路由** → Celery
  2. **要简单快速、任务模型简单** → RQ
  3. **要高可靠 + 简洁 API** → Dramatiq
- **选型时真正该看的（比 star 数重要）**：
  1. **可靠性**：任务会不会丢？确认机制（ack）是自动还是手动？
  2. **重试与死信队列**：内置还是自己写
  3. **可观测**：有没有现成的监控（Flower / 自建）
  4. **幂等支持**：能否配合幂等 key 防重复执行
  5. **并发模型**：prefork / gevent / asyncio——LLM 场景是 IO 密集，**用 asyncio/gevent 而非 prefork**
- **RAG/Agent 场景特别提醒**：任务体是"调 LLM + 检索"，属**长 IO 等待型**，队列并发模型要选协程型；同时要设**任务级超时**，防卡死占满 worker。
- 若只需"延迟执行"而非"任务编排"，也可考虑云厂商的 Serverless 队列（省运维）。

**Q9: API 框架选型：FastAPI vs Flask vs Django**

- 难度：⭐⭐
- 标签：#API框架 #后端开发

**💡 参考答案**

| 框架 | 定位 | 优势 | 短板 |
|------|------|------|------|
| **FastAPI** | 现代异步 API | **异步原生**、Pydantic 校验、**自动 OpenAPI 文档**、性能好、类型友好 | 生态比 Django 小、全功能需自己拼 |
| **Flask** | 轻量微框架 | 极简灵活、生态成熟、学习成本低 | 同步为主、无内置校验与文档、大项目需自行架构 |
| **Django** | 全栈框架 | ORM/Admin/认证/迁移**全家桶**、适合业务系统 | 重、异步支持后加、对纯 API 服务偏重 |

- **决策**：
  1. **AI/LLM 服务、高并发、IO 密集** → **FastAPI**（LLM 调用是典型 IO 等待，异步收益极大）
  2. **小型工具 / 简单接口** → Flask
  3. **要 Admin 后台 + 复杂业务模型 + 完整权限体系** → Django（或用 Django REST Framework 只做 API 层）
- **为什么 AI 服务首选 FastAPI**：
  - `async/await` 天然适配 LLM 流式与并发调用
  - **Pydantic 校验**：工具参数、请求体校验开箱即用（与 Function Calling 的 schema 理念一致）
  - **自动生成 OpenAPI**：便于内部对接与调试
  - 类型提示友好，配合 IDE 开发体验好
- **提醒**：框架选择不是关键，**服务分层、可观测、限流、超时与幂等**这些工程能力才是；换框架不会解决架构问题。

**Q10: 监控方案选型：Prometheus + Grafana vs LangSmith vs LangFuse**

- 难度：⭐⭐⭐
- 标签：#监控 #可观测性

**💡 参考答案**

| 方案 | 监控对象 | 部署 | 特点 |
|------|----------|------|------|
| **Prometheus + Grafana** | **系统与业务指标**（QPS/延迟/资源/错误率） | 自建 | 通用标准、灵活、**不懂 LLM 语义** |
| **LangSmith** | **LLM 链路**（trace/评测/数据集） | SaaS | 上手最快、功能全、**数据出域**、收费 |
| **LangFuse** | **LLM 链路** | **开源自部署** | trace + 评测 + 成本统计，可私有化 |

- **结论：不是三选一，而是组合使用**
  - **Prometheus + Grafana** 看**系统层**：QPS、P95/P99、GPU 利用率、错误率
  - **LangFuse / LangSmith** 看**LLM 层**：每次 run 的 span 树、prompt/response、token 成本、工具调用链
  - 两者用 `trace_id` 关联，才能从"指标异常"下钻到"具体哪条请求哪一步出错"
- **LangSmith vs LangFuse 怎么选**：
  - **数据不能出域 / 有私有化要求** → **LangFuse**（开源可自部署）
  - **追求快速上手 / 团队无运维** → LangSmith
  - 成本敏感 → LangFuse 自部署
- **补充**：底层用 **OpenTelemetry** 做统一埋点标准，避免绑定某一家；日志用 Loki/ELK。
- **选型时必查**：
  1. trace 能否关联**业务指标**（否则两个系统割裂）
  2. **成本统计**是否按租户/场景维度
  3. 是否支持**评测与数据集**（LLM 应用需要回归能力）
  4. **隐私与留存**（trace 里有用户原文，需脱敏）

## 第四部分：业务落地题（8题）

**Q1: 如何证明 Agent 比人工客服更好？设计评估方案**

- 难度：⭐⭐⭐⭐
- 公司：字节、阿里（真题）
- 标签：#评估 #ROI #业务价值

**评估维度** ：

- 准确性
- 效率
- 成本
- 满意度
- 覆盖率

**💡 参考答案**

**一、先定指标（可量化、可对比）**
| 维度 | 指标 |
|------|------|
| 质量 | 解决率（首解率）、准确率、幻觉率、错误率 |
| 效率 | 平均处理时长 AHT、首响时间、并发承载 |
| 成本 | 单工单成本（token + 运维）、人力成本对比 |
| 体验 | CSAT / NPS、转人工率、投诉率 |
| 覆盖 | 可自动处理的问题占比、意图覆盖度 |

**二、实验设计（关键，不能只跑"感觉"）**
1. **影子模式先行**：Agent 生成答案但**不直接发给用户**，人工复核并记录差异 → 低风险验证质量
2. **A/B 分流**：同批次工单随机分配（Agent / 人工），**对比同质人群**
3. **分层分析**：按问题类型分层（FAQ / 查询 / 复杂投诉 / 情绪化）——**找出 Agent 的真实优势区间**
4. **统计严谨**：先算样本量，给置信区间，避免"跑了 50 单就下结论"

**三、成本与 ROI**
- 成本侧：token + 基础设施 + 研发运维 + 人工兜底
- 收益侧：人力替代 × 人力成本 + AHT 缩短 × 处理量
- 算**回本周期**；注意边际成本随规模递减（试点阶段 ROI 天然差）

**四、诚实的结论（面试加分）**
- 通常结论是：**Agent 在高频简单问题上显著优于人工（成本降 X%、响应快 Y 倍），在复杂/情绪化问题上不如人**——正确表述是"**在 X 类问题上替代 Y% 的人工工作量**"，而不是笼统的"比人工好"
- 明确**不可替代的兜底**：投诉、法律风险、情绪安抚保留人工
- 给出**演进路径**：先覆盖 60% 简单问题 → 逐步扩边界

**五、持续监控**
- 上线后持续跟踪，防止"上线即巅峰"（流量分布变化会拉低效果）

**Q2: 如何设计 Agent 的灰度发布策略？**

- 难度：⭐⭐⭐
- 标签：#灰度发布 #上线策略

**💡 参考答案**

**一、分层放量（阶梯式）**
```
影子模式 → 内部员工 → 白名单用户 → 1% → 5% → 20% → 50% → 100%
```
- 每档设**观察期**（至少覆盖一个完整业务周期，如日活低谷+高峰）
- 新版本与旧版本**并行存在**（可随时切回）

**二、分流维度**
- 用户维度（按 user_id 哈希，**同一用户体验稳定**，避免抖动）
- 流量维度（按比例）
- 场景维度（先在低频场景试）
- 租户维度（SaaS 场景）

**三、门禁指标（自动回滚的触发条件）**
- 质量：任务成功率、幻觉率、人工接管率
- 性能：P95/P99 延迟
- 成本：单次成本
- 稳定：错误率、超时率、工具失败率
- **任一超阈值 → 自动回滚**（不要靠人盯）

**四、可回滚基础（前提条件）**
- 版本化一切：**prompt / 模型 / 索引 / 配置**都能独立切版本
- 别名切换（秒级生效），而不是"重新部署"
- 数据兼容：新旧版本共存不冲突

**五、灰度 vs A/B 的区别（常被混淆）**
- **灰度**：验证**稳定性**（会不会坏）——发现问题就回滚
- **A/B**：验证**效果**（哪个更好）——需要统计显著性
- 实践中先灰度保稳定，再 A/B 比效果

**六、配套**
- 变更公告与回滚预案（Runbook）
- 全链路 trace 标注版本号（出问题能定位是哪个版本）
- 用户反馈通道（灰度期重点收集）

**Q3: 如何设计 RAG 系统的 A/B 测试？**

- 难度：⭐⭐⭐
- 标签：#ABTest #RAG #实验

**实验设计** ：

- 对照组与实验组
- 评估指标
- 流量分配
- 统计显著性

**💡 参考答案**

**一、变量选择（一次只改一个）**
- 可测变量：切块策略、embedding 模型、top-k、rerank 开关、prompt 模板、混合检索权重
- **单变量原则**：同时改多个，赢了也不知道是哪个起的作用

**二、对照组与实验组**
- 唯一差异 = 被测变量，其余配置完全相同（同一索引快照、同一模型版本）
- 分流：按 **user_id / session_id 哈希**，保证**同一用户体验一致**（否则体验抖动会污染指标）

**三、指标设计（分主次）**
| 类型 | 指标 | 说明 |
|------|------|------|
| **主指标** | 答案准确率 / 采纳率 / 任务成功率 | 决定成败 |
| **护栏指标** | P95 延迟、单次成本、错误率 | 不能退化 |
| **辅助指标** | 检索 Recall@k、rerank NDCG | 用于归因 |
- ⚠️ **不要只看主指标**——常见坑是"准确率涨了但延迟翻倍"，要用护栏指标拦下

**四、流程（离线先行，省钱）**
1. **离线评测集**筛掉明显差的版本（此时淘汰成本最低）
2. 小流量线上 A/B（如 5%）
3. 达显著后扩量验证
4. 全量

**五、统计显著性（面试常考）**
- **先算样本量**（power analysis）：效应量、显著性水平 α=0.05、power=0.8
- 用置信区间而非只看均值
- **多重比较**要校正（同时测 5 个变体，假阳性概率会上升）
- 避免**偷看数据提前下结论**（peeking problem）

**六、常见陷阱**
- 指标漂移（外部事件干扰）→ 加时间对照
- 样本污染（用户跨组）→ 分流要稳定
- 季节/周期性 → 实验周期覆盖完整周期
- 只测"平均"忽略分层 → 按场景/问题类型分层看

**Q4: 如何处理 Agent 的幻觉问题？**

- 难度：⭐⭐⭐⭐
- 标签：#幻觉 #Agent #可靠性

**缓解策略** ：

- RAG 增强
- 引用来源
- 置信度评分
- 人工审核

**💡 参考答案**

**核心认知（面试先亮这个）**：**幻觉不能根除，只能降低 + 让用户可识别**。设计目标是"**可发现的幻觉**"而非"零幻觉"。

**一、检索侧（幻觉常源于"没检索到"）**
- 提高召回质量：混合检索 + rerank，避免材料缺失导致模型脑补
- 材料不足时**明确降级**，而不是"尽力回答"

**二、生成侧约束**
- **Prompt 硬约束**："仅依据以下材料回答；材料未提及则明确说无法回答"
- **强制引用**：每个论断标注来源编号
- **上下文组织**：材料编号清晰、最相关的放首尾（防 lost-in-the-middle）

**三、验证侧（关键，很多人不做）**
- **答案-证据一致性校验**：用 LLM 或 NLI 模型判断每句话是否有材料支撑 → 无支撑的句子标红/剔除
- **引用准确性检查**：引用编号是否真的支持该论断（防"引用对了但内容无关"）
- **多路交叉验证**：同一问题多次采样，答案不一致则提示不确定

**四、交互侧**
- **展示来源**：让用户能一键核对原文（最实用的手段）
- **标注不确定性**：置信度低时显式提示
- 高风险场景（医疗/法律/金额）**强制人工确认**

**五、训练侧**
- SFT 加入"材料不足时拒答"的样本
- DPO 惩罚编造行为

**六、度量**
- faithfulness / groundedness 指标（可用 RAGAS 类框架）
- 人工抽检幻觉率，建 bad case 库
- 指标进 CI，防版本退化

**七、兜底**
- **拒绝回答也是一种正确**：宁可说"我不确定"，也不要编

**Q5: 如何设计 Agent 的权限控制？**

- 难度：⭐⭐⭐
- 标签：#权限 #安全 #Agent

**设计要点** ：

**💡 参考答案**

**一、身份与上下文**
- **双身份**：用户身份（谁在用）+ 服务身份（Agent 自己）
- 把用户身份与权限**注入上下文**，模型只应请求被授权的操作
- 注意：**注入上下文不等于安全**——真正的校验必须在系统层（模型可能被诱导）

**二、权限模型**
- **RBAC**（基于角色）+ **ABAC**（基于属性：部门、数据密级、时间）
- **工具级 ACL**：每个工具声明所需权限，只授予必要的最小权限集
- 数据级：文档级 ACL，检索时**强制过滤**用户无权访问的内容

**三、读写分级（Agent 特有关键设计）**
| 级别 | 示例 | 控制 |
|------|------|------|
| 只读 | 查询订单 | 自由 |
| 低危写 | 改地址、发通知 | 记录审计 |
| **高危写** | 退款、删除、支付 | **人工确认 + 二次验证 + 金额/频次上限** |
| 禁止 | 修改权限、导出全量数据 | 直接拒绝 |

**四、强制约束（不依赖模型自觉）**
- 金额上限、单日频次上限、白名单（只能操作自己名下的订单）
- 沙箱执行代码、网络出口白名单
- **幂等 key** 防重复副作用

**五、审计与检测**
- 全量操作日志（谁、何时、依据什么、做了什么）——可溯源、可追责
- 越权检测与异常告警（短时间大量敏感操作）
- 定期权限复核（回收不用的权限）

**六、兜底**
- 越权请求：拒绝 + 明确告知 + 记录
- 模型被注入诱导时，系统层仍能拦住（深度防御）

**Q6: 如何处理用户数据隐私？**

- 难度：⭐⭐⭐
- 标签：#隐私 #安全 #合规

**保护措施** ：

**💡 参考答案**

**按数据生命周期逐段施策：**

**一、采集（最小必要）**
- 只收集实现功能必需的数据；明确告知用途与范围，取得同意
- 敏感字段（身份证/银行卡）**能不收就不收**，非收不可的加密存储

**二、存储（加密与隔离）**
- 传输 TLS，存储 AES 加密；密钥独立管理（KMS），不与数据同库
- 多租户/多用户**逻辑或物理隔离**；检索必须带 `user_id`/`tenant_id` 硬过滤
- 分环境隔离：生产数据不进测试环境

**三、使用（脱敏与最小权限）**
- **PII 脱敏后再进模型与日志**（trace 里存用户原文是常见泄露点）
- 训练数据需**明确授权**，不得把用户对话直接用于训练
- 访问最小权限 + 访问审计

**四、传输（数据出域评估）**
- 用第三方 API 意味着**数据出境/出域** → 隐私敏感场景优先**私有化部署**
- 出域前脱敏，评估供应商的数据留存政策

**五、留存与删除（合规硬要求）**
- 明确**留存期限**（TTL），到期自动清理
- 支持**用户删除权 / 被遗忘权**（GDPR、个人信息保护法）——包括向量库、缓存、备份里的数据
- 支持数据导出（可携带权）

**六、治理**
- 合规框架：个保法 / 等保 / GDPR（按业务地域）
- 定期隐私影响评估（PIA）
- 数据分类分级，按级别定策略
- 事故响应预案（泄露上报流程）

**Q7: 如何设计 Agent 的个性化能力？**

**实现方式** ：

**💡 参考答案**

**一、三层结构**
| 层 | 内容 | 存储 | 更新频率 |
|----|------|------|----------|
| **画像**（静态偏好） | 长期偏好、禁忌、风格 | 关系库 / KV | 低 |
| **行为**（动态兴趣） | 近期点击/浏览/购买序列 | 行为日志 + 实时特征 | 高 |
| **会话上下文** | 本次对话的即时需求 | Redis | 实时 |

**二、个性化手段**
1. **检索加权**：偏好匹配的候选提权（如"不吃辣"→ 川菜馆降权）
2. **生成适配**：语气、详略、术语深度按用户画像调整（专家 vs 新手）
3. **推荐重排**：在候选集上按个人偏好 rerank
4. **Prompt 注入**：把画像摘要注入系统提示（注意 token 成本）

**三、反馈闭环**
- **显式**：点赞/点踩、纠正（"我不喜欢这个"）→ 写入画像，importance 打高
- **隐式**：采纳/跳过/修改 → 弱信号，累积后生效
- 定期用 LLM 从交互历史中抽取/更新画像

**四、冷启动**
- 默认画像 + 快速试探（少量轮次内快速学习）
- 引导式提问（首次使用问偏好）
- 群体画像兜底（相似用户的行为）

**五、隐私与边界（必须讲，否则减分）**
- 用户**可查看、可修改、可删除**自己的画像
- 个性化可关闭（《个保法》要求）
- **避免信息茧房**：保留一定探索（多样性），不要完全按偏好收窄

**六、评估**
- 个性化 vs 非个性化的 A/B（采纳率、满意度、留存）
- 注意**过度个性化**会降低发现新内容的能力

**Q8: 如何量化 Agent 的业务价值（ROI 计算）？**

- 难度：⭐⭐⭐⭐
- 标签：#ROI #业务价值 #成本收益

**计算维度** ：

- 成本节省（人力替代）
- 效率提升（响应时间）
- 收入增长（转化率）
- 用户满意度

**💡 参考答案**

**一、成本侧（要算全，别只算 API 费）**
- 直接：LLM token、向量库、算力、存储
- 间接：**研发与运维人力**（常被低估）、标注与评测、人工兜底成本
- 一次性：建设期投入（数据治理、系统开发）

**二、收益侧（四类，归因难度递增）**
| 类别 | 计算方式 | 归因难度 |
|------|----------|----------|
| **人力替代** | 自动化处理量 × 单工单人力成本 | 低（可直接测） |
| **效率提升** | AHT 缩短 × 处理量 | 低 |
| **收入增长** | 转化率/留存提升 × 客单价 | **高（需 A/B 对照）** |
| **体验价值** | CSAT/NPS 提升 → 留存/复购 | 高 |

**三、方法（严谨性决定结论可信度）**
1. **Baseline 对照**：与"纯人工"或"旧系统"对比
2. **A/B 或影子模式**：证明增量来自 Agent，而非外部因素
3. **分层归因**：按场景/问题类型拆，避免平均值掩盖（可能某些场景是负收益）
4. **敏感性分析**：关键假设（如人力成本、采纳率）变动时 ROI 怎么变

**四、输出形式**
- **回本周期（Payback Period）**——管理层最关心
- **净现值 / 3 年 TCO 对比**
- **分阶段 ROI**：试点期（可能为负，含建设投入）→ 规模化期（边际成本递减，ROI 上升）
- 单位经济模型：单次会话成本 vs 单次人工成本

**五、常见坑（面试可讲）**
- 只算显性 API 成本，忽略运维与兜底人力 → ROI 虚高
- 把**相关性当因果**（"上线后 GMV 涨了"未必是 Agent 的功劳）→ 必须有对照组
- 忽略**质量成本**（答错造成的赔付/流失）
- 静态测算：流量规模变化会改变单位成本（LLM 批量与规模效应）

**六、一句话结论**
**ROI 的可信度取决于对照组设计**——没有对照的 ROI 数字，只是故事。
