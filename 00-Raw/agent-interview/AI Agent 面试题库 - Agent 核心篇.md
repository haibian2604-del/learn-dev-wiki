## AI Agent 面试题库 - Agent 核心篇

> 本文档为题目原文 + 逐题参考答案。答案按「面试口述」标准组织：先给结论，再给要点，最后给权衡与工程细节。

## 📚 适用对象

- ✅ Agent 算法工程师（必学，优化策略）
- ✅ Agent 开发工程师（必学，系统搭建）
- ⏱️ 建议学习时间：算法岗5天，开发岗4天

## 第一部分：Agent 基础概念

**Q1: 你如何定义一个基于 LLM 的智能体（Agent）？它通常由哪些核心组件构成？**

- 难度：⭐⭐
- 岗位：通用
- 标签：#Agent #定义 #架构
- 公司：所有公司（必考）

**💡 参考答案**

- **定义**：以 LLM 为推理内核，能自主感知环境、拆解目标、调用工具、执行动作并根据反馈迭代的智能系统。一句话公式：`Agent = LLM（大脑） + 规划 + 记忆 + 工具 + 反馈闭环`。
- **与 Chatbot 的本质区别**：Chatbot 是单轮「问-答」；Agent 有**自主性**（自己拆任务）、**行动力**（调用工具改变外部状态）、**闭环性**（观察结果后修正），追求的是"完成任务"而非"生成文本"。
- **核心组件**：
  1. **大脑 / LLM**：推理、决策、意图理解、工具选择
  2. **规划 Planning**：任务分解、路径选择、反思与重规划
  3. **记忆 Memory**：短期（上下文窗口）/ 长期（向量库、关系库、知识图谱）
  4. **工具 Tools**：Function Calling、检索、代码执行、外部 API
  5. **感知 Perception**：多模态输入解析（文本/图/音/结构化）
  6. **执行与编排**：状态机、调度、并发、重试、护栏
- **一句话收尾**：组件好搭，难的是让它们**可靠地协同**——所以工程上还要加可观测、评估、安全护栏三个横切模块。

**Q2: 请详细解释 ReAct 框架。它是如何将思维链和行动结合起来，以完成复杂任务的？**

- 难度：⭐⭐⭐
- 岗位：通用
- 标签：#Agent #ReAct #核心范式
- 公司：字节、阿里、腾讯（高频）

**💡 参考答案**

- **是什么**：ReAct（Reasoning + Acting，Yao et al. 2022）把**推理轨迹**和**动作**交错在一个循环里，三者轮转：
  - `Thought`（想：我该做什么、为什么）
  - `Action`（做：调用某个工具，带参数）
  - `Observation`（看：工具返回的真实结果）
  然后带着 Observation 进入下一轮 Thought，直到给出 `Final Answer`。
- **为什么有效**：
  - Thought 承担**分解与追踪**（类似 CoT），让多步任务不迷路；
  - Action 把推理**锚定到外部真实信息**（检索、API），显著降低幻觉——这是它优于纯 CoT 的关键；
  - Observation 提供**纠错信号**：工具返回与预期不符时可以改计划。
- **一个例子**：问"某公司最新财报营收多少？" → Thought：需要查财务数据 → Action：`search("公司 2025 Q3 营收")` → Observation：返回数字 → Thought：已足够 → Final Answer。若检索为空，下一轮 Thought 会改查询词。
- **工程实现**：在 system prompt 里放 few-shot 示范；用 stop token（如 `Observation:`）截断模型输出以解析 Action；解析出工具名与参数 → 执行 → 把结果拼回上下文。
- **局限与对策**：错误会沿链路累积（**误差级联**）、步数不可控易死循环、token 成本高。生产上要配：**最大步数上限、失败重试与反思、结果校验、收敛判定**。常见演进：ReAct + Reflexion（失败后带批评重试）、Plan-and-Execute（先规划再执行）。

---

**Q3: 在 Agent 的设计中，"规划能力"至关重要。请谈谈目前有哪些主流方法可以赋予 LLM 规划能力？（例如 CoT, ToT, GoT等）**

- 难度：⭐⭐⭐
- 岗位：通用
- 标签：#Agent #规划 #思维链
- 公司：字节、阿里（高频）

**💡 参考答案**

按"搜索空间大小 / 是否回溯"递进讲：

| 方法 | 核心 | 特点与代价 |
|------|------|-----------|
| **CoT**（思维链） | 逐步线性推理 | 便宜、单路径、错了不回头 |
| **Self-Consistency** | 采样多条 CoT 后投票 | 提准确率，成本 ×N |
| **Least-to-Most / Plan-and-Solve** | 先分解子问题再逐个解 | 适合有层次的任务 |
| **ToT**（思维树） | 把 thought 当节点，做 BFS/DFS + 自评 + 回溯 | 强搜索能力，成本高 |
| **GoT**（思维图） | 图上允许**合并/聚合**多个 thought，边表达依赖 | 比 ToT 更灵活，工程复杂、昂贵 |
| **Reflexion / Self-Refine** | 自我批评 → 重试 | 靠反馈迭代，需外部信号 |
| **LLM+P / PDDL** | LLM 翻译成形式化规划，交给经典规划器 | 有保证但需建模 |
| **MCTS / RAP** | 用搜索 + 价值估计规划 | 成本最高，研究为主 |

- **选型逻辑**：简单任务用 CoT；需要高准确用 Self-Consistency；需要探索/回溯用 ToT；**生产系统通常是组合**——LLM 做高层规划（Plan-and-Execute），底层用 ReAct 执行，配 Reflexion 兜错。
- **现实约束**：精度提升与 token 成本近似线性正相关，所以要做**难度路由**——简单 query 直答，难 query 才上重搜索。

## 第二部分：Memory 系统设计

**Q4: Memory 是 Agent 的一个关键模块。请问如何为 Agent 设计短期记忆和长期记忆系统？可以借助哪些外部工具或技术？**

- 难度：⭐⭐⭐
- 岗位：通用
- 标签：#Agent #Memory #系统设计
- 公司：字节、阿里、腾讯（高频）

**💡 参考答案**

先分层，再谈读写，最后谈工具。

- **记忆分层（类比认知科学）**：
  - **工作记忆**：当前上下文窗口，**token 预算管理**是核心（给系统提示/历史/工具结果分配配额）
  - **短期/会话记忆**：最近 N 轮原文 + 增量摘要
  - **长期/情节+语义记忆**：跨会话的事实、偏好、经历
  - **程序性记忆**：可复用的技能/工具/SOP（常以 skill 形式沉淀）
- **短期记忆设计**：滑动窗口保最近原文；更早的用**滚动摘要**压缩；结构化状态（槽位、任务进度）单独维护，不靠原始对话。
- **长期记忆设计（读写两条链路）**：
  - **写**：抽取显著信息 → 判重要性打分 → 摘要 + 做指代消解（自包含）→ embedding → 落库，带元数据（时间、用户、类型、来源）
  - **读**：查询改写 → 混合检索（向量 + BM25）→ 过滤（user_id/时间/类型）→ rerank → 按「相关性 × 重要性 × 时间衰减」综合排序 → top-k 注入 prompt
- **可借助的技术**：
  - 存储：**向量库**（Milvus / pgvector / Faiss / Weaviate）存语义记忆；**关系库**（Postgres）存画像与事实；**Redis** 存会话态；**图库**（Neo4j）存实体关系；对象存储放原文
  - 框架：LangChain / LlamaIndex 的 memory 模块、**Mem0 / Letta(MemGPT) / Zep**、LangGraph 的 checkpointer
- **易错点**：记忆不是"全都存"——**写什么、读什么、什么时候忘**才是设计难点；不做去重和冲突消解会越用越脏。

## 第三部分：Tool Use 工具调用

**Q5: Tool Use 是扩展 Agent 能力的有效途径。请解释 LLM 是如何学会调用外部 API 或工具的？（可以从 Function Calling 的角度解释）**

- 难度：⭐⭐⭐
- 岗位：通用
- 标签：#Agent #ToolUse #FunctionCalling
- 公司：所有公司（高频）

**💡 参考答案**

分"模型怎么学会"和"运行时怎么跑"两层讲。

- **运行时机制（Function Calling 闭环）**：
  1. 应用把工具的 **JSON Schema**（名称、描述、参数类型/必填/枚举）随请求发给模型；
  2. 模型输出结构化调用 `{name, arguments}`（而不是纯文本）；
  3. 宿主运行时解析 → **实际执行**工具；
  4. 结果作为 `tool` 角色消息回填上下文；
  5. 模型根据结果继续推理或再调用，直到给出最终答案。
- **模型是怎么"会"的**：
  - **训练侧**：在 `(指令, 工具 schema, 正确调用)` 数据上做 **SFT**（典型数据集 ToolLLM/ToolBench、API-Bank、Glaive）；进一步用 **RL**（reward = 任务成功 + 格式合法 + 步数惩罚）优化多步选择能力。
  - **推理侧（不改权重）**：靠 prompt + few-shot 示范教会格式；用 **约束解码**（grammar/JSON schema）保证输出合法。
- **两种实现流派对比**：
  - **文本解析式**（ReAct）：模型输出 `Action: search[...]`，正则解析——兼容任何模型，但脆弱；
  - **原生 Function Calling**：模型直接产出 `tool_calls` 字段——稳定、可并行，但有厂商绑定。
- **工程要点**：工具描述要精确（含**何时用/不用**与副作用说明）；参数用枚举与 schema 约束；执行前校验、写操作要幂等；工具返回的错误要转成模型能懂的自然语言，让它能自我修正。

**Q6: 有微调过 Agent 能力吗？数据集如何收集？**

- 难度：⭐⭐⭐
- 岗位：算法岗重点
- 标签：#Agent #微调 #数据集

**💡 参考答案**

> 没做过就诚实说"没做过端到端微调，但设计过数据方案"——然后讲透方案，比硬编强。

- **数据来源（四条主线，按性价比排序）**：
  1. **线上真实轨迹**：记录完整 trace（用户 query + 工具调用链 + 结果 + 成功/失败标记），过滤出**成功轨迹**做正样本、失败轨迹做负样本或纠错样本。最贴合分布。
  2. **强模型蒸馏 / 合成**：让 GPT-4 级模型在沙盒环境中跑任务（ReAct/ToolBench 思路），**用结果校验（任务是否真完成）做拒绝采样**，只保留成功的。
  3. **人工标注 / 专家示范**：写 golden trajectory，质量最高但最贵，适合核心场景与冷启动。
  4. **环境自动反馈**：代码执行通过、单元测试通过、API 返回 success → 自动打标，可规模化。
- **数据形态**：
  - **SFT**：`(system+tools, user, assistant tool_call, tool result, assistant final)` 的多轮样本
  - **DPO/RL**：`(prompt, chosen, rejected)` 偏好对，或 `(prompt, reward)` 交互样本
- **清洗与构造**：去重、长度过滤、**格式规范化**（工具调用必须合法）、负样本要包含"失败→恢复"的轨迹（教纠错）、控制步数分布不要过长。
- **训练策略**：先 **LoRA SFT** 教格式与调用规范（稳、便宜），再用 **DPO / GRPO** 提升任务成功率与效率；用 held-out 任务集验证泛化。
- **关键坑**：合成数据容易**分布过窄**（只会示范过的工具）；要用 held-out 工具/场景做泛化评估，防止"背题"。

## 第四部分：框架选型

**Q7: 请比较一下两个流行的 Agent 开发框架，如 LangChain 和 LlamaIndex。它们的核心应用场景有何不同？**

- 难度：⭐⭐
- 岗位：开发岗重点
- 标签：#Agent #框架 #选型
- 公司：所有公司（通用）

**💡 参考答案**

一句话：**LangChain 是"编排框架"，LlamaIndex 是"数据/RAG 框架"**。

| 维度 | LangChain（+LangGraph） | LlamaIndex |
|------|------------------------|-----------|
| 定位 | 通用编排、Agent 工程 | 数据接入 + RAG 检索 |
| 强项 | chain/agent 抽象、工具集成广、**LangGraph 状态图**做有环/多 agent | **Ingestion 管线**（加载器、节点切分）、多种索引、Query Engine、retriever/reranker、RAG 评估 |
| 核心场景 | 复杂业务流程、tool-calling agent、多智能体编排 | 知识库问答、文档检索、结构化数据查询、GraphRAG / agentic RAG |
| 状态与并发 | LangGraph 原生支持持久化状态、断点续跑 | 相对弱，偏无状态检索 |

- **重叠与现状**：两者现在都能做 RAG 和 agent，边界在模糊。但**基因不同**：LangChain 从"LLM 应用编排"长出来，LlamaIndex 从"把私有数据喂给 LLM"长出来。
- **选型口诀**：**以检索为核心 → LlamaIndex；以流程编排为核心 → LangChain/LangGraph**。实际项目常**组合**：LlamaIndex 做检索层，LangChain 做编排与工具层。

**Q8: 你用过哪些 Agent 框架？选型是如何选的？你最终场景的评价指标是什么？**

- 难度：⭐⭐⭐
- 岗位：开发岗重点
- 标签：#Agent #框架选型 #评估

**💡 参考答案**

- **框架清单**：
  - 编排类：**LangChain / LangGraph**（状态图、多 agent）、**LlamaIndex**（RAG）
  - 多智能体：**AutoGen/AG2**（群聊式）、**CrewAI**（角色分工）、Swarm
  - 工程/企业：**Semantic Kernel**、Google ADK、Claude Agent SDK、OpenAI Agents SDK
  - 低代码：**Dify / Coze**（快速验证）
- **选型维度（我的决策框架）**：
  1. **场景形态**：单 agent / 多 agent / 固定工作流 → 决定要不要状态图
  2. **可控 vs 效率**：要精细控制状态与并发 → 代码框架；要快速出 Demo → 低代码
  3. **生态与集成**：模型/向量库/工具适配广度
  4. **可观测与调试**：trace 能力是否完善
  5. **部署与成本**、**团队熟悉度**、**是否厂商锁定**
- **评价指标（分三层）**：
  - **结果层**：任务成功率 / 端到端通过率、用户满意度、人工接管率
  - **过程层**：工具选择准确率、参数正确率、平均步数、幻觉率、格式合规率
  - **系统层**：P50/P95 时延、单任务 token 成本、错误率/超时率
- **方法**：离线 golden set 回归 + 线上 A/B + 人工评审；LLM-as-Judge 做规模化打分，但要人工抽检校准。

## 第五部分：Multi-Agent 协作

**Q9: 什么是多智能体系统？让多个 LLM Agent 协同工作相比于单个 Agent 有什么优势？又会引入哪些新的复杂性？**

- 难度：⭐⭐⭐⭐
- 岗位：通用
- 标签：#MultiAgent #协作 #系统设计
- 公司：字节、阿里（高频）

**💡 参考答案**

- **定义**：多个具有不同角色/职责的 LLM Agent，通过某种通信协议协作（或竞争）来完成任务，能力上限超过单个 agent。
- **优势**：
  1. **专业化**：每个 agent 的 prompt/工具集更聚焦，单点能力更强、更稳定
  2. **上下文解耦**：避免一个 agent 背上所有信息导致上下文爆炸
  3. **并行加速**：独立子任务并行执行
  4. **多视角校验**：generator + critic/verifier 提升正确率、降幻觉
  5. **可维护可扩展**：加一个角色就扩展一种能力
  6. **贴近人类组织**：分工明确，便于归因与审计
- **新引入的复杂性**：
  1. **误差级联**：上游错了下游全错，且难定位
  2. **协调成本**：谁说、说什么、何时结束——调度逻辑本身很复杂
  3. **token 与时间成本上升**：通信即成本，常是单 agent 的数倍
  4. **死锁 / 无限对话 / 循环**：缺乏收敛机制就会空转
  5. **状态一致性**：共享状态并发读写冲突
  6. **信用分配难**：RL 训练时不知道奖励该给谁
  7. **评测与调试难**：多步多主体，归因困难
- **一句话收尾**：多 agent 不是"越多越好"——**只在单 agent 确实因为上下文或角色冲突做不好时才上**，简单任务用单 agent 更快更便宜。

**Q10: 了解 A2A 框架吗？它和普通 Agent 框架的区别在哪，挑一个最关键的不同点说明。**

- 难度：⭐⭐⭐
- 岗位：算法岗重点
- 标签：#Agent #A2A #前沿技术

**💡 参考答案**

- **是什么**：A2A（Agent2Agent）是 Google 2025 年提出的**跨厂商、跨框架的 Agent 互操作协议**，目标是让不同团队/公司用不同技术栈做的 agent 能**互相发现与协作**。
- **核心概念**：**Agent Card**（能力名片，供发现）、**Task**（任务生命周期）、**Message / Part**（消息与多模态片段）、**Artifact**（产物）；基于 HTTP/JSON-RPC + SSE 传输。
- **最关键的不同点（挑这个说）**：
  > **普通 Agent 框架解决"一个 agent 内部怎么干活"（LLM + 工具 + 记忆的编排）；A2A 解决"agent 与 agent 之间怎么说话"（跨边界的通信协议）。**
  普通框架是"单体应用内部架构"，A2A 是"分布式系统间的接口标准"——类比：LangChain 是类内部方法，A2A 是 HTTP/RPC 契约。
- **与 MCP 的分工**：**MCP** 解决 `Agent ↔ 工具/资源`（纵向接入）；**A2A** 解决 `Agent ↔ Agent`（横向协作）。两者互补。
- **价值**：避免每个 agent 都要为对方写适配器（N×N → N+N），让多 agent 从"公司内玩具"走向"跨组织生态"。

## 第六部分：挑战与优化

**Q11: 在构建一个复杂的 Agent 时，你认为最主要的挑战是什么？**

- 难度：⭐⭐⭐
- 岗位：通用
- 标签：#Agent #挑战 #优化

**💡 参考答案**

一句话：**把"能跑通的 Demo"变成"可靠、可控、可负担的生产系统"。** 展开为：

1. **长链路误差累积**：多步之后一个小错被放大，且难定位（可靠性）
2. **非确定性**：LLM 输出波动，同一输入结果不稳，难复现难测试
3. **规划质量**：复杂任务拆解不当，后面全废
4. **工具调用准确率**：选错工具、参数错、该调不调
5. **上下文管理**：窗口限制、长对话"遗忘"与注意力稀释
6. **记忆设计**：写什么、读什么、何时忘——很容易越用越脏
7. **评测困难**：没有标准 benchmark，多步任务归因难
8. **成本与时延**：多轮 token 消耗大、P95 延迟不可接受
9. **安全可控**：越权、prompt 注入、隐私、不可逆操作
10. **工程化**：状态管理、并发隔离、可观测、灰度与回滚

- **收尾金句**：技术挑战都可解，**最本质的张力是"能力（自主性）"与"可控性"之间的平衡**——自主性越高越强，但也越难保证安全与可预测。

**Q12: 当一个 Agent 需要在真实或模拟环境中（如机器人、游戏）执行任务时，它与纯粹基于软件工具的 Agent 有什么本质区别？**

- 难度：⭐⭐⭐
- 岗位：算法岗重点
- 标签：#Agent #具身智能 #机器人

**💡 参考答案**

| 维度 | 软件工具 Agent | 真实/模拟环境 Agent（具身） |
|------|---------------|--------------------------|
| **动作空间** | 离散、语义化的 API 调用 | 连续 + 离散的低层控制（关节角、速度），需策略网络/VLA |
| **观测** | 结构化文本返回 | 高维连续感知（RGB-D、点云、力觉），**部分可观测、含噪声** |
| **环境动力学** | 确定/近确定，可复现、可重置 | 连续、随机、**不可逆**（打翻杯子无法撤销），有物理代价 |
| **时间约束** | 请求-响应，秒级可接受 | **实时闭环控制**，毫秒级 |
| **数据来源** | 语言数据 + SFT 轨迹即可 | 遥操作数据、RL 交互、仿真数据；**样本效率极低**（sim-to-real gap） |
| **主要学习范式** | Prompting + SFT/RL 微调 | 模仿学习 + RL + VLA 微调 |
| **安全要求** | 逻辑安全（越权/隐私） | **物理安全**（撞人、损坏），硬约束 |

- **本质区别一句话**：软件 agent 的"世界"由 API 定义、可逆、可重放；具身 agent 的"世界"是**连续的物理过程**，动作有真实代价、不可回滚，因此必须实时、必须安全、必须处理感知噪声。
- **共性**：都仍需"规划 + 记忆 + 技能库 + 安全约束"，只是实现层从"调 API"变成"出策略"。

**Q13: 如何确保一个 Agent 的行为是安全、可控且符合人类意图的？在 Agent 的设计中，有哪些保障对齐方法？**

- 难度：⭐⭐⭐⭐
- 岗位：通用
- 标签：#Agent #安全性 #对齐
- 公司：字节、阿里、腾讯（重要）

**💡 参考答案**

核心原则：**不信任 LLM 本身，把安全放在系统层——纵深防御 + 最小权限 + 人在回路。**

按阶段分层：

- **目标/规划层**：约束与禁止项显式写进 system prompt；高风险任务先做 **plan review**；人机协同（HITL）审批关键步骤。
- **输入层**：prompt 注入检测、内容审核、PII 识别与脱敏、意图风险分级。
- **执行层**：
  - **最小权限**：工具级 ACL / RBAC，只授予必要权限
  - **沙箱隔离**：代码执行、网络出口白名单
  - **限额与熔断**：金额/频次/步数上限、超时、kill switch
  - **可撤销**：写操作幂等、支持回滚/补偿事务、**高风险操作二次确认**
- **监督层**：guardrail 模型（如 Llama Guard）审核输入输出、规则引擎、异常检测、自我批判/verifier agent。
- **训练/对齐层**：RLHF / DPO 对齐价值、Constitutional AI、学会**拒答与表达不确定性**（uncertainty-aware refusal）。
- **验证层**：结果校验（dry-run、模拟执行、形式化约束）。
- **治理层**：红队测试、越权/注入基准（如 AgentHarm）、全链路审计日志、持续监控与回滚。

- **一句话收尾**：**自主性越高，越要往"能拦住、能看见、能撤销"上投资**——这三条是安全 Agent 的底线。

## 第七部分：Agent 系统设计与优化（真题补充）

**Q14: 在 RAG+知识图谱的 Agent 系统中，知识图谱更新的机制是怎样的？是怎样保证实时性的？**

- 难度：⭐⭐⭐
- 岗位：算法岗重点
- 标签：#知识图谱 #实时更新
- 公司：字节(真题)

**💡 参考答案**

- **更新机制（增量为主，重建为辅）**：
  1. **抽取**：新文档 → LLM/规则抽取实体与关系（含属性）
  2. **对齐消歧**：实体对齐到已有节点（否则同一个"苹果"变成两个）
  3. **合并（upsert）**：并行写入节点/边，**带上元数据**（来源、置信度、`valid_from/valid_to`）
  4. **冲突消解**：多来源矛盾时按置信度/来源权重/时间新旧裁决；矛盾的旧事实标记过期而非删除（保留可审计）
  5. **索引同步**：图索引 + 向量索引一起更新，**失效相关缓存**
- **实时性保证**：
  - **事件驱动**：CDC / 消息队列（Kafka）监听文档变更，只更新**受影响子图**，不做全量重建
  - **读写分离**：查询走只读副本，写入走主图，互不阻塞
  - **分层**：实时层（近期/热点）+ 历史层，查询时合并
  - **缓存**：热点查询结果短 TTL 缓存，更新时精准失效
  - **异步 + 优先队列**：高频实体优先更新
- **一致性权衡**：强一致代价高，生产多用**最终一致 + 版本号**，保证可追溯与可回滚。
- **技术栈举例**：Neo4j / NebulaGraph 存图，pgvector / Milvus 存向量，LangChain/LlamaIndex 的 GraphRAG 管线调度。

**Q15: 训练 LoRA 模型时，你是如何选择冻结层的？依据是什么？**

- 难度：⭐⭐⭐
- 岗位：算法岗重点
- 标签：#LoRA #层选择
- 公司：字节(真题)

**💡 参考答案**

先纠正一个常见误解：**LoRA 默认就是冻结原权重**（只训低秩矩阵 A/B）。所以真正的问题是"**注入哪些层、用什么 rank**"。

- **经验规律**：
  - **底层（embedding、最浅几层）**：学通用/语法特征，任务无关 → **通常不注入或给小 rank**
  - **中高层（后几层 attention + FFN）**：承载任务语义 → **重点适配**
  - **广而薄 > 窄而厚**：全层注入低 rank，通常优于只选少数层用大 rank
  - **模块选择**：一般注入 `q_proj/k_proj/v_proj/o_proj` + FFN 的 `up/down/gate`；多模态常只调 cross-attn 或投影层
- **选择依据（五条）**：
  1. **任务与预训练分布差异**：差异大 → 覆盖更多层、更大 rank
  2. **数据量与过拟合风险**：数据少 → 少层 / 低 rank
  3. **参数与显存预算**：决定 rank 上限
  4. **消融实验**：逐层/逐模块 ablation 看下游指标——**最终依据**
  5. **训练稳定性 / 梯度敏感性**：用梯度或重要性分析定位关键层
- **实践路径**：先按社区基线（qkv+o+ffn，rank 8–64，`alpha = 2r`）跑通，再做 injection target + rank 的小规模网格消融搜索。

**Q16: 大规模 Agent 系统在多线程/多进程场景下的资源调度策略如何设计？**

- 难度：⭐⭐⭐⭐
- 岗位：开发岗重点
- 标签：#资源调度 #并发
- 公司：字节(真题)

**💡 参考答案**

分五层设计：

1. **接入层**：网关限流（令牌桶/漏桶）、优先级队列（按 SLA 分级）、**背压**削峰。
2. **任务编排层**：DAG 编排（Temporal / Airflow / Ray / Celery）、异步队列 + worker pool，按 agent 类型拆分 worker 池（避免长任务饿死短任务 → 加权公平队列）。
3. **资源层**：
   - K8s 容器化，**HPA 按 QPS / 队列深度自动扩缩**
   - **CPU/IO 密集与 GPU 密集隔离部署**
   - 有状态（会话）用一致性哈希/粘性会话 + Redis 共享状态；无状态服务随意水平扩展
4. **GPU 层**：vLLM / TensorRT-LLM 做 **continuous batching**，把并发请求聚合成批提升吞吐。
5. **隔离与韧性**：多租户 cgroup 配额、超时/熔断/隔离舱（bulkhead），防止单任务拖垮全局。

- **观测闭环**：QPS、队列长度、P95、GPU 利用率 → 动态调参/扩缩。
- **一句话**：**异步解耦 + 队列 + 自动扩缩 + 批处理 + 隔离**，这五件事做到位，调度问题就解决八成。

**Q17: 如果你要在 GPU 资源有限的条件下同时提供推理和微调服务，如何做资源分配和任务调度以保证时延和吞吐？**

- 难度：⭐⭐⭐⭐
- 岗位：开发岗重点
- 标签：#资源管理 #调度策略
- 公司：字节(真题)

**💡 参考答案**

核心思路：**推理保时延（高优、不可中断），微调保吞吐（低优、可抢占）。**

- **资源切分**：
  - 物理隔离：**推理池 / 训练池**分开，而非均分，按实时负载动态调配
  - 单卡切分：**MIG**（NVIDIA 硬件分区）或时间片/显存配额
- **调度策略**：
  - **优先级 + 抢占**：在线推理高优；微调作为 **preemptible**，被抢占时 checkpoint 后让出
  - **时间窗**：微调排低谷时段（夜间），白天资源让给推理
  - K8s 上用 **Volcano / Kueue** 做 gang scheduling 与配额管理
- **各自优化手段**：
  - 推理：**量化**（INT8/FP8/AWQ）、continuous batching、**prefix KV cache 复用**
  - 微调：**LoRA/QLoRA** 降显存、梯度检查点、ZeRO、CPU offload
- **弹性**：微调用 spot/抢占式实例降成本，推理用稳定资源
- **隔离**：不同容器/进程，防显存 OOM 互相影响
- **动态调节**：监控实时负载，推理高峰自动压缩微调配额
- **权衡本质**：**时延（推理）与吞吐（训练）此消彼长**，用"优先级 + 抢占 + 批处理"在两者间取平衡点。

**Q18: 如何让多个agent协同工作的？举个具体的协同机制例子。**

- 难度：⭐⭐⭐
- 岗位：通用
- 标签：#Multi-Agent #协作机制
- 公司：字节、阿里(高频)

**💡 参考答案**

- **常见协同机制**：
  - **编排式（Supervisor / Orchestrator）**：主 agent 分解—分派—汇总（LangGraph Supervisor、CrewAI 层级模式）
  - **流水线**：检索 → 分析 → 写作 → 审校，阶段传递
  - **辩论 / 投票**：多 agent 独立作答后互评或投票，提升正确率
  - **黑板（Blackboard）**：共享内存，各 agent 读写协作
  - **群聊（Group Chat）**：AutoGen 式共享会话轮转发言
  - **协商/招标**：Contract Net 式任务招标-投标
- **具体例子（行程规划）**：
  1. 用户说"下周去成都 3 天"
  2. **Supervisor** 拆解为查信息 / 排行程 / 算预算 / 校验四个子任务
  3. 并行派发：【信息 Agent】调天气与景点 API → 【规划 Agent】据结果排日程 → 【预算 Agent】核算花费
  4. 【审校 Agent】检查时间冲突、闭馆日、超预算 → **不通过则带 critique 回退给规划 Agent 重排**
  5. Supervisor 汇总输出行程表
- **工程实现**：共享状态用 **task board / message bus**（如 Redis + LangGraph state），每步留 trace；用**终止条件**（一致性达成 / 最大轮次 / 预算耗尽）防死循环。

**Q19: 如果一个agent误判导致策略冲突，如何处理？**

- 难度：⭐⭐⭐
- 岗位：通用
- 标签：#错误处理 #容错机制
- 公司：字节(真题)

**💡 参考答案**

闭环五步：**检测 → 仲裁 → 回滚 → 溯源 → 学习**。

1. **检测**：策略一致性校验器 / 规则检查 / verifier agent 发现冲突即触发。
2. **仲裁**：引入更高优先级的 Supervisor 或仲裁器，按**优先级规则、置信度、时间戳、多数表决**裁决。
3. **止损**：暂停可疑 agent；**回滚**其副作用——用事务化检查点或 **Saga 补偿事务**撤销已执行的动作。
4. **降级**：无法自动裁决时降级为人工接管或安全默认策略（fail safe）。
5. **溯源**：全链路 trace 定位是哪个 agent 在哪一步、基于什么证据误判。
6. **学习**：bad case 进评测集与训练数据，更新 prompt / 规则 / 微调模型，形成闭环。
- **预防优于补救**：明确各 agent 的**职责边界与优先级**、给 agent 加自检、设**置信度门控**（不确定时上报而非硬决策）。

**Q20: 你是怎么设计agent的记忆系统？长期记忆如何存储？如果历史记录量非常大，怎么优化查询效率？**

- 难度：⭐⭐⭐
- 岗位：通用
- 标签：#记忆系统 #存储优化
- 公司：字节、阿里(高频)

**💡 参考答案**

- **分层设计**：工作记忆（上下文窗口）/ 短期（最近 N 轮 + 摘要，Redis）/ 长期（向量库 + 关系库 + 图库 + 对象存储）/ 程序性记忆（技能）。
- **长期存储选型**：
  - **向量库**（Milvus / pgvector / Faiss）存 embedding，用于语义召回
  - **关系库**（Postgres）存结构化事实/画像/偏好
  - **图库**（Neo4j）存实体关系
  - **对象存储**存原始对话/文档
- **海量历史的查询优化（重点，面试官想听这个）**：
  1. **冷热分离**：热数据放内存/缓存，冷数据落盘
  2. **索引优化**：ANN 索引（**HNSW / IVF-PQ**）+ **标量 pre-filter**（先按 user_id/时间/类型过滤再向量检索）；混合检索 BM25 + 向量
  3. **分片分区**：按 `user_id` / 时间分片，多租户隔离，缩小单次搜索空间
  4. **层级摘要**：原始对话 → 会话摘要 → 用户画像（L0/L1/L2），检索时先命中上层再下钻，**大幅减少数据量与检索量**
  5. **检索优化**：查询改写 → 粗筛（时间/重要性）→ rerank 精排 → 控制 top-k
  6. **写入优化**：异步 + 批量 embedding；热点查询结果缓存
  7. **淘汰**：TTL + 重要性衰减，剔除不再相关的记忆
- **一句话**：优化 = **减数据（摘要/淘汰）+ 缩空间（分片/过滤）+ 快索引（ANN/rerank）**。

**Q21: 有没有做记忆衰退，避免旧数据干扰新任务？**

- 难度：⭐⭐⭐
- 岗位：算法岗重点
- 标签：#记忆管理 #遗忘机制
- 公司：字节(真题)

**💡 参考答案**

- **为什么需要**：全量保留会让旧偏好/过时事实持续污染检索结果，噪声随使用时间单调增长。
- **机制设计**：
  1. **时间衰减**：检索得分 = `相关性 × 时间衰减因子`（指数衰减，参考艾宾浩斯曲线），旧记忆自然降权
  2. **重要性加权**：写入时用 LLM 打 importance 分，重要记忆衰减更慢
  3. **访问频率**：LRU/LFU + recency，长期不被召回的逐步淘汰
  4. **TTL 与容量上限**：会话记忆设过期时间；长期记忆按容量淘汰最低分条目
  5. **冲突消解**：新事实覆盖旧事实（如偏好改变），旧版本**标记过期而非删除**（保留可审计）
  6. **固化与升华**：反复出现的信息升华为长期画像，一次性噪声直接丢弃
  7. **作用域隔离**：任务级记忆只在本会话有效，防跨任务污染
- **工程实现参考**：Letta(MemGPT) 的分层记忆管理、Mem0 的 update/delete 接口、生成式 Agent 的 `importance + recency + relevance` 综合打分。
- **关键权衡**：**忘太多丢信息，忘太少噪声大**——用评测集调衰减参数，不要拍脑袋定。

**Q22: 你们这种模块堆叠的架构是怎么设计视觉问答模块和动作模块的协同逻辑的？**

- 难度：⭐⭐⭐⭐
- 岗位：算法岗重点
- 标签：#模块设计 #多模态Agent
- 公司：字节(真题)

**💡 参考答案**

关键设计原则：**模块间传"结构化语义结果"，而不是原始像素。**

- **接口设计**：VQA 模块输出结构化结果——场景描述、检测框、空间关系、**可操作对象列表 + affordance + 置信度**；动作模块消费该结构（而非原始图像），实现模块解耦。
- **时序协同（闭环）**：`观测 → VQA → 动作 → 环境变化 → 新观测` 循环执行。
  - VQA 低频运行（关键帧触发 / 缓存复用），动作模块高频实时控制，两者**频率解耦**
- **通信协议**：定义 schema（JSON / tensor）+ 时间戳同步；共享状态可用黑板模式。
- **信息注入**：视觉特征通过 **cross-attention / 条件注入**传给动作网络（VLA 做法）；或 VQA 提供目标候选与 affordance，动作网络做策略选择。
- **冲突与主动感知**：VQA 置信度低时，动作模块可**反查 VQA**（active perception：换个视角再看）或请求人工。
- **一致性 vs 延迟**：管道式（pipeline）模块清晰易调试但累积延迟；端到端（VLA）快但可解释差——按场景选，常用"端到端出粗动作 + 模块化做安全校验"。
- **训练与评估**：可联合微调或分别训练后对齐接口；仿真环境做 sim-to-real；评估用任务成功率 + 各模块独立指标（检测 mAP、动作准确率）。

**Q24: 你怎么处理响应速度与推理精度之间的tradeoff？是先召回再精排，还是单次生成？**

- 难度：⭐⭐⭐
- 岗位：通用
- 标签：#性能优化 #权衡
- 公司：字节(真题)

**💡 参考答案**

核心答案：**默认走"快路径 + 难例升级"的级联（cascade）架构，而不是二选一。**

- **链路设计**：
  1. **快路径**：语义缓存命中直接返回；否则小模型 / 单次生成
  2. **级联检索**：向量/BM25 快速**召回**（便宜） → cross-encoder / LLM **精排**（贵而准） → 只对难例走大模型多步推理
  3. **难度路由**：query 复杂度分类 → 简单直答，复杂走多步
- **提精度手段**：rerank、多路召回融合（RRF）、self-consistency、反思校验、RAG grounding。
- **提速度手段**：语义缓存、投机解码、量化、蒸馏、**流式输出**（降低感知延迟）、并行工具调用、KV cache。
- **动态权衡**：按 SLA 分级（低时延走 light 链路，高价值走 heavy 链路）；**置信度门控**——只有低置信才触发重推理。
- **结论**：密集知识任务用「先召回再精排」；简单/高频问题用「单次生成 + 缓存」。**不做全局二选一，而是按 query 分级路由。**

**Q27: 构建 Agent 的时候，遇到过哪些瓶颈？LangChain 的 memory 默认机制在多用户并发中怎么做隔离？你是如何保证线程安全的？**

- 难度：⭐⭐⭐
- 岗位：开发岗重点
- 标签：#工程实践 #并发安全
- 公司：字节(真题)

**💡 参考答案**

- **常见瓶颈**：上下文爆炸与长对话遗忘、工具调用不稳定、多 agent 死循环、**并发隔离**、成本时延、评测难。
- **LangChain memory 默认机制的问题（面试关键）**：
  - 早期 `ConversationBufferMemory` 等**不是线程安全的**，且默认按实例持有状态
  - 多用户共享同一实例会**串数据**；存在进程内存里则**重启即丢**
- **隔离做法**：
  1. **会话级独立**：以 `user_id + session_id` 作 namespace，每人独立 memory 实例或独立 key，**绝不共享**
  2. **外部持久化**：`RedisChatMessageHistory` / Postgres / DynamoDB 存历史，key 带前缀；服务保持**无状态**可水平扩展
  3. **LangGraph checkpointer**：用 `thread_id` 天然做会话隔离与断点续跑
- **线程安全保证**：
  - **asyncio 单事件循环 + 每会话独立对象**（避免共享可变状态）
  - 多线程/多进程下用锁或进程隔离；会话级**串行队列**（actor 模型）
  - **乐观锁（版本号 CAS）** 防并发写覆盖；请求带 `request_id` 做幂等
  - 多租户加资源配额与数据隔离

**Q28: 你做的 Agent 使用了多少个外部工具，在调用链条上如何保障故障容错和超时机制？**

- 难度：⭐⭐⭐
- 岗位：开发岗重点
- 标签：#工具调用 #容错设计
- 公司：字节(真题)

**💡 参考答案**

先给数量（按实际，如 10+ 个：检索 / 数据库 / HTTP API / 代码执行 / 邮件等），再讲机制。

- **超时**：每个工具独立设 **连接超时 + 读超时**；并设整条调用链的总超时，避免单工具拖垮全局。
- **重试**：**指数退避 + 抖动**；区分可重试（5xx / 超时）与不可重试（4xx 参数错），限定次数（如 3 次）。
- **熔断与降级**：连续失败触发熔断 → 降级到缓存 / 默认值 / 备用工具 / 人工。
- **参数校验**：调用前用 JSON Schema 校验，非法参数不发出，直接回给模型修正。
- **幂等**：写操作带 `idempotency key`，防止重试造成重复下单。
- **隔离**：并行调用用 `asyncio.gather(return_exceptions=True)`，单工具失败不影响其他。
- **错误反馈**：把失败原因转成**自然语言**返回给 LLM，让它反思、换工具或换参数。
- **兜底**：**最大步数限制**，超限终止并返回已完成部分。
- **可观测**：全链路 trace（OpenTelemetry / LangSmith），记录每次调用的入参、出参、耗时、状态。

  - 用**显式状态机/图**（LangGraph state）维护槽位、任务进度、工具结果

  6. **缓存一致**：写后失效 / 双删
  7. **幂等**：请求带 `request_id` 去重

**Q33: 你做Prompt优化时，是如何判断优化后的Prompt在Agent推理链路中性能提升的？用什么指标来衡量？**

- **结果一致性**：
  - **单一事实来源**：共享状态存储 + 版本号
  - **协调协议**：两阶段提交 / **Saga 补偿事务**处理跨 agent 写
  - **乐观并发控制**（CAS / 版本号）或悲观锁；冲突检测与合并
  - **Barrier / join**：等所有必需子任务完成再聚合，保证确定性汇总
  - **幂等去重**（dedup key）+ 消息去重
  - **按依赖 DAG 调度**，保证因果顺序
- **可观测**：全链路 trace + 审计日志，便于回溯与补偿。
- **设计取舍**：分布式**强一致代价高**，生产多用**最终一致 + 补偿事务**。

**Q35: Agent整体流程是怎么做的？包括哪些模块？**

- 难度：⭐⭐
- 岗位：通用
- 标签：#Agent架构 #模块设计
- 公司：字节、阿里

**💡 参考答案**

- **端到端流程**：
  接收输入 → 意图理解（+ 澄清）→ **规划**（任务分解/选策略）→ **记忆检索**（长期）→ **循环执行**（ReAct：Thought → 选工具 → 调用 → Observation → 更新状态）→ **反思/校验**（verifier，不通过则重试）→ 汇总生成 → 输出 + **记忆写入**
- **模块清单**：
  1. **输入/感知层**：多模态解析、意图识别、澄清
  2. **大脑**：LLM 推理 + 规划器
  3. **记忆模块**：工作 / 短期 / 长期

  7. **观测/评估层**：trace、指标、日志
  8. **交互层**：会话管理、输出渲染、人在回路

**Q36: 如果子agent回复不对怎么办？反思？跳不出去怎么办？限制次数？**

- 难度：⭐⭐⭐
- 岗位：通用
- 标签：#错误处理 #反思机制
- 公司：字节(真题)

**💡 参考答案**

- **检测**：校验器（格式/事实/约束检查）+ 置信度阈值 + 父 agent 评审。
- **反思重试**：把「子 agent 答案 + 具体批评（错在哪、期望什么）」回传，让它带反馈重做（Reflexion / Self-Refine）；可换策略或补检索。
- **升级**：多次失败 → 上报父 agent **重新分派 / 换子 agent / 换工具** → 仍不行则降级（简化任务）或转人工。
- **跳出机制（防死循环，重点）**：
  - **最大重试次数**（如 2–3 次）
  - **最大总步数 / 超时预算**
  - **相同错误重复检测**（hash 去重，重复即停）
  - **收益递减检测**：越改越差就停
- **兜底**：输出**当前最佳结果 + 明确的不确定性说明**，而不是无限循环或静默失败。
- **学习**：失败 case 进 bad case 库，优化 prompt / 工具 / 微调。

**Q39: 大模型生成工具调用时，如何避免参数格式错误？有哪些后处理或约束解码方法？**

- 难度：⭐⭐⭐
- 岗位：算法岗重点
- 标签：#工具调用 #格式约束
- 公司：字节(真题)

**💡 参考答案**

从"事前约束 → 事后修复"两手抓：

- **事前（预防）**：
  1. **严格 JSON Schema**：类型、必填、枚举、字段说明都给全
  2. **约束解码**：grammar-constrained decoding（**outlines / XGrammar / llama.cpp GBNF**），在 token 级屏蔽非法结构；或用 provider 的 **structured outputs**（json_schema）
  3. **Prompt / few-shot**：给正确调用示例，明确"只输出合法 JSON"
  4. **训练**：SFT 大量 function-call 样例，DPO 惩罚格式错误
- **事后（修复）**：
  1. **容错解析**：`json_repair`、去 markdown 代码块、正则截取、截断补全
  2. **Schema 校验**：pydantic / jsonschema，不合规则**带错误重试**
  3. **归一化**：类型转换、单位统一、枚举映射、空值补默认
- **运行时校验**：必填校验、ID 有效性检查、参数范围检查
- **架构优化**：复杂参数**拆成多步小调用**；参数名语义化
- **兜底链**：解析失败 → 重试（带错误）→ 降级到更强模型或模板填充
- **监控**：统计格式失败率，作为迭代指标。

**Q40: 当多个工具都能完成子任务时，你的Agent如何做选择？有没有引入打分或排序模块？**

**Q41: 在Agent中引入"记忆"机制时，为什么常用向量数据库？如何设计embedding和检索策略？**

- 难度：⭐⭐⭐
- 岗位：通用
- 标签：#记忆系统 #向量数据库
- 公司：字节、阿里(高频)

**💡 参考答案**

- **为什么用向量库**：记忆检索的本质是**按语义相关性**取回内容，而非精确键匹配。向量库支持语义相似检索、ANN 加速、可扩展，天然适配非结构化的对话与事实。
- **embedding 设计**：
  - **选模型**：中英文用 bge-m3 / text-embedding-3 / gte / jina；领域数据可做对比学习**微调 embedding**
  - **切块策略**：按语义/句子切 chunk 并加 overlap；记忆条目要**短且自包含**（做指代消解与重写）
  - **多向量**：内容向量 + 元数据；重要记忆附 importance 权重
- **检索策略**：
  1. **混合检索**：向量（语义）+ BM25（关键词/实体），用 **RRF 融合**——补足向量对精确词/ID 的弱项
  2. **先过滤再检索**：按 `user_id` / 时间 / 类型做 pre-filter，再向量检索
  3. **召回 → rerank**（cross-encoder / LLM rerank）→ top-k（3–8 条）
  4. **综合打分**：相关性 × 重要性 × 时间衰减
  5. **查询改写**：多轮指代消解、HyDE
  6. **分层检索**：先命中摘要层，再下钻原文
  7. 去重与多样性控制
- **评估**：recall@k、MRR、最终答案准确率。

**Q43: Function Calling 和 Toolformer 的本质区别是什么？各自在训练/推理阶段如何工作？**

- 难度：⭐⭐⭐
- 岗位：算法岗重点
- 标签：#Function Calling #Toolformer
- 公司：字节(真题)

**💡 参考答案**

一句话：**Function Calling 是"推理时的接口协议"，Toolformer 是"训练时把工具内化进权重"。**

| 维度 | Function Calling | Toolformer |
|------|-----------------|-----------|
| 发生阶段 | **推理时** | **训练时** |
| 谁提供工具 | 宿主应用提供 schema | 模型自己从 API 文档学何时调 |
| 输出 | 结构化 `tool_calls` | 文本中插入 `[API(...) → result]` 标记 |
| 工具执行 | **外部系统执行后回填** | 模型生成调用标记，可端到端 |
| 数据来源 | 人工/合成的 (schema, call) 数据；或 native 支持 | 无标注语料 + API 文档**自监督**构造 |
| 是否改权重 | 不必（prompt 即可）；可训练增强 | **必须**，工具使用内化进参数 |
| 学习信号 | SFT/RL 教格式与选择 | **只保留能降低语言建模 loss 的调用**（有用才学） |

- **推理阶段对比**：
  - FC：需要 agent loop 反复「模型输出调用 → 执行 → 回填 → 继续」
  - Toolformer：模型在生成时直接产出调用标记，更偏单次端到端
- **关系**：现代 native function calling 可看作 **Toolformer 思想的工程化**——用 SFT/RL 把"何时调用、调哪个"内化，再用显式 schema 标准化接口。

**Q45: 你的Agent如何处理工具调用失败(如API超时、返回空)？有设计重试、降级或用户澄清机制吗？**

**Q46: 在真实场景中，如何防止Agent泄露用户隐私或越权操作？从算法和系统层面谈谈你的设计。**

- 难度：⭐⭐⭐⭐
- 岗位：通用
- 标签：#安全性 #隐私保护
- 公司：字节、阿里(重要)

**💡 参考答案**

**核心原则：不信任 LLM 本身，安全要落在系统层——纵深防御 + 最小权限 + 人在回路。**

- **算法层**：
  - 训练/对齐：RLHF 拒绝敏感操作、注入防护训练、PII 识别与脱敏模型
  - 推理输入：**prompt 注入检测**（工具返回内容视为**不可信数据**，与指令严格隔离）、敏感信息过滤、意图风险分级
  - 推理输出：PII/敏感内容审核（DLP + guardrail 模型）、结果脱敏
  - 权限感知：把用户身份与权限注入上下文，模型只应请求被授权的操作
- **系统层**：
  - **认证鉴权**：用户级 + 服务级身份，**最小权限（RBAC/ABAC）**，工具级 ACL
  - **数据隔离**：多租户隔离；检索时按 `user_id` 强制过滤（**防跨用户召回**）；传输/存储加密 + 密钥管理
  - **执行管控**：代码沙箱、出口白名单、只读优先；**高风险操作（支付/删除）强制人工确认 + 二次验证**
  - **审计**：全链路操作日志，可溯源、可回滚
  - **防护**：限流/频次/金额上限、越权检测、异常检测
- **治理**：数据最小化与留存策略、红队测试、持续监控。

**Q47: 如果用户连续追问"为什么选这家酒店？"，Agent如何回溯决策链并给出可解释理由？**

- 难度：⭐⭐⭐
- 岗位：算法岗重点
- 标签：#可解释性 #决策追溯
- 公司：字节(真题)

**💡 参考答案**

- **前提（关键）**：**决策时就要落库"理由链"**，而不是事后重建——否则只能编造。
- **记录内容**：每步的候选集、过滤条件、**打分因子与权重**、工具返回的证据、最终选择，全量写入结构化决策日志（trace）。
- **回溯与解释四步**：
  1. 按 `session + 实体` 从记忆/日志检索该决策记录
  2. 把打分因子 + 证据（价格、评分、距离、**与用户偏好的匹配度**、评论摘要）组织成理由
  3. **引用来源**（可点击跳转），让解释可核验
  4. **反事实对比**：说明为什么没选其他候选（更贵 / 更远 / 不符偏好）
- **防幻觉**：理由必须**锚定已记录的客观证据**，加校验避免事后编造原因（hallucinated rationale）。
- **结构化呈现**：给出打分表 + 权重，用户可调（"我更看重位置" → 即时重排）。
- **一句话**：**可解释性不是解释能力，而是记录能力**——决策时没埋点，事后就只能编。

**Q48: 如何评估一个Agent系统的鲁棒性？除了准确率，还会测试哪些对抗性或边缘case？**

- 难度：⭐⭐⭐
- 岗位：通用
- 标签：#鲁棒性评估 #压力测试
- 公司：字节、阿里

**💡 参考答案**

- **对抗性 case**：
  - **Prompt 注入**（直接注入 / 间接注入，如在工具返回或网页内容里埋指令）
  - 越狱、恶意与有害指令、越权请求、隐私套取
- **边缘 case**：
  - 输入扰动：错别字、口语、多语言、超长/超短、空输入、乱码、**自相矛盾的需求**
  - 工具异常：超时、报错、**返回空 / 返回脏数据 / 返回超长**
  - 环境异常：高并发、部分服务宕机、网络抖动
  - 边界任务：**超出能力范围**（应拒答或转人工）、模糊歧义、多任务混合
  - 长链路：多步后误差累积、上下文超限
- **指标（不止准确率）**：
  - **鲁棒性 gap**：扰动下成功率相对基线的下降幅度
  - 失败恢复率、幻觉率
  - **越权 / 注入拦截率**
  - 错误率、超时率
  - **降级行为**：失败时是否优雅降级（fail safe），而不是崩溃或静默错误
  - **一致性**：同输入多次运行的稳定度
- **方法**：压力测试、模糊测试（fuzzing）、红队、混沌工程、线上 A/B 与监控、回归评测集。
- **目标**：**失败也要安全**——明确告知 + 保留已完成的正确部分。

**Q50: 问数据的输入输出格式如何保证大模型输出稳定的json做了哪些工作？**

- 难度：⭐⭐⭐
- 岗位：开发岗重点
- 标签：#格式化输出 #稳定性
- 公司：字节(真题)

**💡 参考答案**

从"约束生成 → 容错解析 → 校验重试"三层做：

- **事前约束**：
  1. **明确 schema**：给 JSON Schema / 示例，标明字段类型、枚举、必填，并在指令中强调输出格式
  2. **结构化输出能力**：使用 provider 的 **json mode / structured outputs**（如 `response_format: json_schema`），底层即约束解码
  3. **约束解码**：outlines / XGrammar / GBNF，在 **token 级屏蔽非法结构**
  4. **Prompt 技巧**：few-shot 正确示例、**先 CoT 再输出 JSON**（思维与格式分离）、明确"只输出 JSON，不要解释"
  5. **训练**：必要时 SFT 强化格式能力
- **事后修复**：
  1. **容错解析**：`json_repair`、剥离 markdown 代码块、正则截取、截断补全
  2. **Schema 校验**：pydantic / jsonschema，不合规则**带错误重试**（自修复），限次数
  3. **归一化**：类型转换、默认值补齐、枚举纠正
- **架构**：复杂结构**拆成多次简单调用**分别生成，降低单次出错概率。
- **参数**：温度调低（甚至 0），选结构化输出强的模型。
- **工程**：把格式失败率纳入监控，写契约测试防退化。

**Q51: 问Agent的工具tool的设计，是否是workflow形式？**

- 难度：⭐⭐
- 岗位：开发岗重点
- 标签：#工具设计 #Workflow
- 公司：字节(真题)

**💡 参考答案**

- **先澄清概念**：**工具（tool）** 是原子能力（单一职责、schema 明确、幂等）；**workflow** 是工具的**编排方式**。两者是不同层面的东西。
- **两种编排形态并存**：
  - **Workflow（确定性编排）**：固定步骤 / DAG，适合流程稳定、可预测的场景（审批流、报表生成）——**可控、可测、便宜、低延迟**
  - **Agentic（LLM 自主决定工具与顺序）**：适合路径不固定、需动态决策的场景——**灵活但不可控、贵**
- **生产主流是混合**：
  - **外层 workflow 骨架**（固定阶段 + 护栏 + 状态机）
  - **内层节点内 agent 自主**选工具（ReAct）
  - 或先用 **router** 判断走哪条 workflow
- **LangGraph 统一二者**：节点 = 步骤/agent，边 = 确定性或条件跳转。
- **选择依据**：任务确定性、可接受失败率、成本时延、可解释与合规要求。
- **结论**：**不是非此即彼**——我的实践是"workflow 骨架 + 局部 agent 自主"，把确定的部分固化、不确定的部分交给模型。

**Q52: agent调用工具不正确怎么办，采用sft或者强化学习怎么来解决？**

- 难度：⭐⭐⭐
- 岗位：算法岗重点
- 标签：#错误修正 #微调策略
- 公司：字节(真题)

**💡 参考答案**

**先诊断，再决定要不要训练——多数问题不需要动权重。**

- **现象分类**：选错工具 / 参数错 / 该调不调 / 不该调乱调 / 调用顺序错。
- **低成本手段优先（能解决八成问题）**：
  - 完善**工具描述与命名**（说清何时用/不用）
  - 补 **few-shot** 正反例、明确**决策规则**
  - 加 **schema 约束 + 运行时校验 + 失败反馈重试**
  - 加 **router 小模型**先做工具路由
  - 检索相似历史样例动态注入
- **SFT（解决"会不会 / 格式对不对"）**：
  - 构造高质量 `(任务 → 正确工具调用)` 轨迹，教工具选择、参数格式、调用时机
  - 数据：专家标注、强模型合成、**成功轨迹过滤 + 拒绝采样**
  - 优点：稳定、样本效率较高、格式易控；缺点：**易过拟合示范、泛化弱**
- **RL（解决"选得好不好 / 多步决策"）**：
  - reward 设计：任务成功率 + 工具选择正确 + 格式合法 − 步数/成本惩罚 − 安全违规
  - 算法：PPO / **GRPO** / DPO
  - 优点：结果导向，能超越示范；缺点：**reward 设计难、训练不稳、成本高、易 reward hacking**
- **推荐组合**：**先 SFT 打基础（格式与基本调用）→ 再 RL 精调（成功率与效率）**；小模型可蒸馏。
- **工程兜底（与训练并重）**：验证器 + 重试 + 降级，保证即使模型出错系统也不崩。
- **一句话**：**能用 prompt 和工具设计解决的，就不训练；要提升固有能力，SFT 优先、RL 进阶。**
