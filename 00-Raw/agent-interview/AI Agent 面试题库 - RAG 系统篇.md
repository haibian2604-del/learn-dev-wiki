## AI Agent 面试题库 - RAG 系统篇

> 本文档为题目原文 + 逐题参考答案（22 题）。答案按「面试口述」标准组织：先结论，再要点，最后权衡与工程细节。

## 📚 适用对象

- ✅ RAG 算法工程师（必学，优化检索策略）
- ✅ RAG 开发工程师（必学，系统搭建）
- ⏱️ 建议学习时间：算法岗4天，开发岗3天

## 第一部分：RAG 核心原理（必考）

**Q1: 请解释 RAG 的工作原理。与直接对 LLM 进行微调相比，RAG 主要解决了什么问题？有哪些优势？**

- 难度：⭐⭐
- 岗位：通用
- 标签：#RAG #检索增强 #核心概念
- 公司：字节、阿里、腾讯（高频）

**💡 参考答案**

- **原理**：先检索、后生成。离线阶段把文档切块后向量化入库；在线阶段把用户 query 也向量化，检索出最相关的 top-k 片段，**拼进 prompt 让 LLM 基于给定材料作答**并给出引用。
- **解决的核心问题**：
  1. **知识时效性**——微调把知识烧进权重，更新一次要重训；RAG 换文档即生效
  2. **幻觉**——给模型事实依据，把"自由发挥"变成"据材料回答"
  3. **私有数据**——企业文档不必进训练集，规避数据外泄与成本
  4. **可溯源**——答案能链回原文，可核验、可审计
- **对比微调**：

| 维度 | RAG | 微调 |
|------|-----|------|
| 知识更新 | 换文档，分钟级 | 重训，天级 |
| 成本 | 低（无训练） | 高（算力+数据） |
| 可解释 | 强（引用来源） | 弱（知识在权重里） |
| 擅长 | **知识**（事实、时效、私域） | **能力**（格式、风格、推理模式、工具调用） |
| 幻觉 | 降低但不消除 | 不适用 |

- **结论**：二者**互补而非替代**。问题是"模型不知道"→ 用 RAG；问题是"模型不会做/格式不对"→ 用微调。生产上通常是 **RAG 打底 + 轻量微调补能力**（如 Function Call 格式微调）。

**Q2: 一个完整的 RAG 流水线包含哪些关键步骤？请从数据准备到最终生成，详细描述整个过程。**

- 难度：⭐⭐
- 岗位：通用
- 标签：#RAG #流程 #系统设计

**💡 参考答案**

分**离线索引**与**在线查询**两条链路，中间夹一层评估监控。

**离线（索引期）**：
1. **数据接入**：多源 connector（网盘/数据库/网页），增量采集
2. **文档解析**：PDF/HTML/DOCX → 结构化文本，保留标题层级与表格（→ 文档解析是质量天花板）
3. **切块 chunking**：按结构/语义切分，加 overlap
4. **元数据附加**：标题路径、来源、时间、权限标签（后面做过滤和引用要用）
5. **向量化**：embedding 模型编码
6. **入库**：向量索引（ANN）+ 标量索引（过滤）+ 全文索引（BM25），三套并存

**在线（查询期）**：
7. **Query 理解**：改写（多轮指代消解）、意图识别、**查询路由**（该走向量还是图还是直接答）
8. **检索**：向量 / BM25 / **混合检索**，多路召回
9. **重排 rerank**：cross-encoder 精排，top-50 → top-5
10. **上下文组装**：去重、按相关性排序、token 预算裁剪、防"lost in middle"
11. **生成**：带引用的答案合成
12. **后处理**：引用校验、格式规整

**横切能力**：评估（检索层+生成层指标）、监控与 trace、语义缓存、**权限过滤**（多租户必做）。

- **一句话**：**索引期决定上限，检索期决定能不能碰到，生成期决定答得好不好。**

**Q3: 在构建知识库时，文本切块策略至关重要。你会如何选择合适的切块大小和重叠长度？这背后有什么权衡？**

- 难度：⭐⭐
- 岗位：通用
- 标签：#RAG #文档处理 #切块策略

**💡 参考答案**

- **核心权衡**：
  - **块太大** → 噪声多、检索命中但答案被稀释、精度下降、token 成本高
  - **块太小** → 语义不完整（"它"指代不明）、上下文断裂、召回后拼不回完整意思
- **参数经验值**：size 常见 **256–1024 token**，overlap **10–20%**（如 512 + 64）。起点用 512/64，再按评测调。
- **决策依据**：
  1. **内容形态**——结构化文档（条款、FAQ）用小块；叙事长文用大块或段落级
  2. **embedding 模型最大输入长度**（超长会被截断，等于白切）
  3. **问题粒度**——事实型问答小块好；总结/对比类大块好
  4. **下游有没有 rerank**——有精排可以召回多一点、块小一点
- **主流策略**：
  - 固定长度 / 递归字符切分（默认方案）
  - **语义切分**（按句子 embedding 相似度断裂）——质量高但慢
  - **结构化切分**（按标题层级、代码函数、Markdown 标题）——工程上最划算
  - **父子块 Parent-Child**：小块做检索（精准命中），大块（父块）送生成（上下文完整）——强烈推荐
  - 句子窗口 / 元数据拼接（把标题路径拼进 chunk 头，显著提升可检索性）
- **落地建议**：不要追求最优切块，**用自有评测集看 recall@k 与最终答案准确率**，A/B 几组参数即可收敛。

**Q4: 如何选择一个合适的嵌入模型？评估一个 Embedding 模型的好坏有哪些指标？**

- 难度：⭐⭐
- 岗位：通用
- 标签：#RAG #Embedding #模型选择

**💡 参考答案**

- **选型六个维度**：
  1. **语言覆盖**：中文场景优先 **bge-m3 / bge-large-zh / gte**；英文/多语可用 text-embedding-3、jina
  2. **维度与成本**：维度越高存储与检索越贵（768/1024/1536）；支持 Matryoshka 截断的模型更灵活
  3. **最大输入长度**：512 还是 8k，直接约束切块策略
  4. **公开榜单**：MTEB / C-MTEB 做初筛（**只作参考**，不自作结论）
  5. **部署形态**：API（省事、数据出域）vs 本地（私有化、可控成本）
  6. **领域适配**：金融/医疗/代码等垂直领域，往往需要**在自己的数据上微调 embedding**
- **评估指标（分层）**：
  - **检索层**：Recall@k、Precision@k、MRR、NDCG、Hit Rate——最直接
  - **语义层**：STS 相关性（Spearman 相关）
  - **下游任务**：分类/聚类表现
  - **业务层**：**端到端答案准确率与忠实度**——最终准绳
- **关键认知**：
  - **榜单分数 ≠ 你的业务效果**，必须用**自有标注集**评测
  - 非对称检索（短 query 查长文档）要用支持 query/passage 双编码的模型
  - 领域微调（对比学习 + 难负样本挖掘）常带来比换模型更大的提升

## 第二部分：检索优化（算法岗重点）

**Q5: 除了基础的向量检索，你还知道哪些可以提升 RAG 检索质量的技术？**

- 难度：⭐⭐⭐
- 岗位：算法岗、开发岗通用
- 标签：#RAG #检索优化 #混合检索
- 公司：字节、阿里（高频）

**💡 参考答案**

按"查询侧 → 检索侧 → 排序侧"三层归类：

- **查询侧（改写问题本身）**：
  - **Query 改写**：多轮指代消解、口语补全、纠错
  - **HyDE**：先让 LLM 生成假设答案，再用假设答案去检索
  - **多查询扩展 / Query2Doc**：生成多个视角的查询，扩大召回
  - **子问题分解**：复杂问题拆成多个简单问题分别检索（→ 见 Q18）
- **检索侧（扩大与融合）**：
  - **混合检索**：向量（语义）+ BM25（关键词/实体/ID）双路，**RRF 融合**——互补性最强的一招
  - **多向量 / 多字段**：同一 chunk 存多个向量（标题向量、摘要向量）
  - **元数据过滤**：时间、来源、权限做 pre-filter，先缩小空间
  - **图检索**：多跳、关系型问题走 **GraphRAG**
  - **层级检索**：先命中摘要层，再下钻原文（RAPTOR 思路）
- **排序侧（精排与去噪）**：
  - **Rerank**：cross-encoder / LLM rerank，top-50 → top-5，**性价比最高的一招**
  - **上下文压缩**：只保留与问题相关的句子，降噪声降 token
  - 去重与多样性（避免 top-k 全是同一段的复制品）
- **兜底**：检索置信度低时**拒答或澄清**，而不是硬答。
- **一句话**：**混合检索扩召回，rerank 提精度，查询改写提上限**——三招组合能覆盖大部分场景。

**Q6: 请解释"Lost in the Middle"问题。它描述了 RAG 中的什么现象？有什么方法可以缓解这个问题？**

- 难度：⭐⭐⭐
- 岗位：算法岗重点
- 标签：#RAG #长文本 #优化

**💡 参考答案**

- **现象**：LLM 对长上下文中的信息利用呈 **U 型曲线**——**开头的和结尾的信息记得牢，中间的被忽略**。即使上下文窗口够长，塞在中间的关键证据也可能被漏掉。
- **对 RAG 的直接影响**：如果 top-k 检索结果按相关性从高到低排进 prompt，**最相关的那条恰好落在中间位置**时被忽略，表现为"材料里明明有，模型却说没有"。
- **缓解方法**：
  1. **控制 top-k**：不是越多越好，3–5 条常优于 20 条（少而准）
  2. **重排位置**：把**最相关的放首尾**，次相关放中间（reorder by importance）
  3. **降噪**：rerank 后过滤低分项，压缩上下文长度
  4. **上下文压缩**：只留相关句子，缩短总长度
  5. **结构化组织**：用标题、编号、分隔符显式切分材料，降低混淆
  6. **分块喂入 / 迭代检索**：不一次给完，按需再检索（agentic RAG）
  7. **换更强的长上下文模型**或在 prompt 里明确"请逐条核对材料 1..N"
- **本质**：这不是"窗口不够"问题，而是**注意力分配问题**——加长窗口不解决，**减少噪声 + 优化位置**才解决。

**Q7: 在什么场景下，你会选择使用图数据库或知识图谱来增强或替代传统的向量数据库检索？**

- 难度：⭐⭐⭐
- 岗位：算法岗重点
- 标签：#GraphRAG #知识图谱 #检索策略

**💡 参考答案**

- **选图的判据（满足越多越该上）**：
  1. **多跳推理**——"A 的供应商的竞争对手是谁"，向量检索一次只能拿到一跳的碎片
  2. **关系型/结构化问题**——实体间显式关系是答案主体（股权、供应链、组织架构）
  3. **需要全局性问题**——"这个数据集的主要主题是什么"，向量 top-k 天生答不了
  4. **要求可解释**——答案能沿着图的路径解释，审计友好
  5. **强 schema 领域**——医疗、法律、金融有明确本体
- **不适合的场景**：
  - 纯事实查证、单跳问答——**向量更快更便宜**，上图谱是过度设计
  - 描述性/叙事性问题——图谱结构化不了，仍需文本证据
  - 数据频繁变更、实体消歧成本极高的场景
- **生产主流是"图 + 向量"混合**，不是替代：
  - **查询路由**先判断问题类型 → 事实型走向量，关系型走图，混合型两路并行后融合
  - 图负责"关系骨架"，向量负责"文本细节支撑"
- **代价**：图谱构建与维护成本高（抽取、对齐消歧、增量更新）、冷启动慢、schema 演进难。
- **一句话**：**问题里有"关系/多跳/全局"，选图；问题只是"找一段话"，选向量。**

## 第三部分：评估与优化（通用）

**Q8: 如何全面地评估一个 RAG 系统的性能？请分别从检索和生成两个阶段提出评估指标。**

- 难度：⭐⭐⭐
- 岗位：通用
- 标签：#RAG #评估 #指标设计

**💡 参考答案**

RAG 评估必须**分阶段拆解**，否则出了错不知道该修检索还是修生成。

- **检索阶段**：
  - **Recall@k / Hit Rate**：正确证据有没有被召回——**最关键**，召不回后面全废
  - **Precision@k / MRR / NDCG**：排序质量，正确证据排第几
  - **上下文相关性 Context Relevance**：召回内容与问题是否真的相关
- **生成阶段**：
  - **忠实度 Faithfulness / Groundedness**：答案是否**只依据**给定材料，有没有编（**幻觉率的直接度量**）
  - **答案相关性 Answer Relevance**：有没有答非所问
  - **答案正确性 Correctness**：与标准答案比对（有标注时）
  - **引用准确率**：引用是否真的支持该句论断
- **端到端**：任务成功率、人工采纳率、用户满意度、P95 时延、单次查询成本
- **评估方法**：
  1. **有标注集**：人工标注 (query, 正确文档, 标准答案)，自动化计算指标
  2. **LLM-as-Judge**：用强模型按 rubric 打分（RAGAS / TruLens / DeepEval 等框架已内置 faithfulness、context relevance 等指标）——需人工抽检校准
  3. **A/B 测试**：线上分流对比
  4. **人工评审**：盲评 + 评分卡
- **实践建议**：
  - **先分层定位瓶颈**：Recall@k 低 → 修检索；召回高但 faithfulness 低 → 修 prompt 或生成模型
  - 指标要**接 CI 回归**，防版本退化
  - 没有标注集时，先用 LLM-as-Judge 建基线，再逐步人工标注补齐

**Q9: 传统的 RAG 流程是"先检索后生成"，你是否了解一些更复杂的 RAG 范式，比如在生成过程中进行多次检索或自适应检索？**

- 难度：⭐⭐⭐⭐
- 岗位：算法岗重点
- 标签：#RAG #高级技术 #自适应检索

**💡 参考答案**

按"多检索几次 / 自己决定要不要检索 / 会自我批判"三条演进线：

- **迭代式检索（Iterative / Multi-hop Retrieval）**：
  - **IRCoT**：检索→推理→再检索，用中间推理结果驱动下一轮查询
  - 适合多跳问题（"A 的创始人在哪所大学读的书"）
- **自适应检索（Adaptive Retrieval）**：
  - **Self-RAG**：模型输出**反思 token**（是否需要检索 / 材料是否相关 / 答案是否有支撑），自己决定要不要检索、要不要重写
  - **Adaptive-RAG**：先用分类器判断问题难度，简单问题**直接答**（不检索）、中等问题单次检索、复杂问题多步检索——**省成本的关键**
- **检索质量纠偏**：
  - **CRAG（Corrective RAG）**：对召回结果做质量评估（正确/模糊/错误），错误就换源（如转向 Web 搜索），模糊就补充检索
  - **查询重写循环**：检索结果差 → 改写 query 再试，设最大轮次
- **结构增强**：
  - **GraphRAG**：图层做全局与多跳
  - **RAPTOR**：递归聚类建摘要树，层级检索
- **工程权衡（关键）**：
  - 多轮检索 = 多次 LLM 调用，**成本与延迟成倍上升**
  - 所以生产上一定配**难度路由**：简单问题走单次，复杂问题才上多步
  - 必须设**最大轮次 / 预算上限 / 收敛条件**，否则会空转
- **一句话**：高级 RAG 的本质是**把"固定两步"变成"按需多次的控制器"**——收益是准确率，代价是延迟与成本。

## 第四部分：工程实践（开发岗重点）

**Q10: RAG 系统在实际部署中可能面临哪些挑战？**

- 难度：⭐⭐⭐
- 岗位：开发岗重点
- 标签：#RAG #部署 #工程实践
- 公司：字节、阿里（高频）

**💡 参考答案**

按"数据 → 性能 → 稳定 → 安全"四类：

- **数据侧**：
  1. **文档解析质量**——PDF 表格错乱、扫描件需 OCR，直接决定上限
  2. **知识库增量更新与分布漂移**——新老文档风格/术语不一致导致检索偏差（→ Q14）
  3. **数据噪声**——模板页眉页脚、广告、乱码进入索引（→ Q15）
  4. **多租户权限隔离**——检索必须按 user/tenant 硬过滤，否则跨租户泄密
- **性能侧**：
  5. **延迟**——检索+重排+生成串行，P99 容易超 1s；需缓存、并行、批处理
  6. **成本**——embedding 调用、rerank、LLM token 三重开销，规模上来很快
  7. **高并发**——峰值 QPS 与向量库容量/LLM 配额不匹配
- **稳定侧**：
  8. **检索质量波动**——召回差时模型会**脑补**，必须做置信度门控与拒答
  9. **模型/依赖升级**——换 embedding 模型 = 全量重索引，要有版本与回滚方案
  10. **可观测性**——链路长，没有 trace 无法定位"到底哪一步错了"
- **安全合规侧**：
  11. **Prompt 注入**——文档内容里藏指令可劫持模型（间接注入）
  12. **数据泄露与合规**——敏感信息脱敏、留存策略、审计日志
- **应对总纲**：**分层可观测 + 逐层评估 + 缓存与并行 + 权限硬过滤 + 降级兜底**。

**Q11: 了解搜索系统吗？和 RAG 有什么区别？**

- 难度：⭐⭐
- 岗位：开发岗重点
- 标签：#RAG #搜索系统 #对比分析

**💡 参考答案**

- **本质差异**：**搜索交付的是"文档列表"，RAG 交付的是"答案"**。
- **对比表**：

| 维度 | 传统搜索 | RAG |
|------|---------|-----|
| 输出 | 排序文档列表 + 摘要 | 自然语言答案 + 引用 |
| 核心任务 | 相关性排序（Ranking） | 检索 + 阅读理解 + 生成 |
| 目标指标 | Recall / NDCG / CTR | 答案正确率 / 忠实度 |
| 技术栈 | 倒排索引 + BM25 + 学习排序 | 向量库 + 混合检索 + LLM |
| 用户行为 | 自己点开筛选 | 直接拿到结论 |
| 容错 | 给错链接用户能自己判断 | 给错答案用户**难以察觉** |

- **继承关系**：RAG 的检索层**大量复用搜索技术**——BM25、倒排索引、混合检索的 RRF 融合、query 改写、rerank，都是搜索领域沉淀的。**RAG ≈ 搜索 + LLM 阅读理解**。
- **搜索业界的经验可直接迁移**：分词与同义词、字段权重、点击反馈做训练数据、NDCG 评估。
- **RAG 新增的难点**：LLM 的忠实度（搜到但读错/编造）、上下文长度与位置效应、多轮对话中的指代消解。
- **一句话**：**搜索解决"找到"，RAG 解决"读懂并回答"**；评估标准也因此从"排序质量"升级为"答案正确性"。

**Q13: 构建向量检索库时如何处理时间衰减对召回的影响？**

- 难度：⭐⭐⭐
- 岗位：算法岗重点
- 标签：#时间衰减 #召回优化
- 公司：字节(真题)

**💡 参考答案**

- **为什么要处理**：语料时间跨度大时，**旧文档大量存在且语义相似**，会挤占新内容的召回位；但"最新"不等于"最正确"，全按时间排序又会牺牲相关性。
- **做法一：打分融合（主流）**
  - 最终分 = `语义相似度 × 时间衰减因子`，衰减用**指数衰减** `exp(-λ·Δt)`
  - 或线性加权：`score = α·similarity + (1-α)·freshness`，α 用评测调
  - λ 按业务定：新闻/价格类衰减快（半衰期天级），制度文档衰减慢（年级）
- **做法二：分层/分片**
  - 按时间分层（近 3 月 / 1 年 / 历史），查询时**优先检索热层**，不足再下探冷层
  - 冷热分离同时解决存储与检索效率
- **做法三：检索后重排**
  - 先按纯语义召回 top-N，再在 rerank 阶段把时间作为特征之一（更可控，便于 A/B）
- **做法四：软删除与版本**
  - 被新版本文档取代的旧版本**标记失效而非物理删除**，检索时过滤（保留可审计）
- **关键权衡与坑**：
  - **衰减过强** → 高价值的历史经典内容被埋没（如技术文档、法条）
  - **衰减过弱** → 过时信息持续误导
  - 解决：**按文档类型设置不同衰减曲线**，别全局一刀切；重要/权威来源给权重加成
  - 时间衰减要和**用户意图**结合——问"最新政策"要强衰减，问"原理"无需衰减

**Q14: RAG中知识库搭建，对知识库的文件文档进行动态增量更新，怎么来避免新旧文档的分布不一致导致的检索偏差问题？**

- 难度：⭐⭐⭐
- 岗位：算法岗重点
- 标签：#增量更新 #分布一致性
- 公司：美团(真题)

**💡 参考答案**

问题的本质：新旧文档在**术语、格式、切块粒度、信息密度**上不一致，导致 embedding 空间与检索打分系统性偏向某一批。

- **一、统一处理管线（治本）**
  - 新旧文档**走同一套解析+切块+元数据规范**，不要新老两套脚本
  - 换 embedding 模型/切块策略时**必须全量重建**，不能只增量——否则新旧向量不在同一空间，是致命偏差
- **二、元数据对齐**
  - 统一附加：来源、版本、生效时间、文档类型、层级路径
  - 用元数据做**过滤与加权**，把"新旧差异"显式化，而不是让模型隐式承担
- **三、分布对齐手段**
  1. **术语归一**：建同义词/别名表，新旧术语映射到同一表述（"用户"vs"客户"）
  2. **查询侧扩展**：query 改写时同时生成新旧术语版本，多路检索
  3. **版本感知检索**：默认只召回"现行有效"版本，历史版本按需显式查询
  4. **分桶评估**：**分别统计新文档/旧文档的召回率与命中率**，发现偏斜立即暴露（这是检测偏差的关键动作）
- **四、更新机制**
  - **增量为主**：CDC/消息队列监听变更 → 只重算受影响 chunk 的向量 → **upsert**（同 doc_id 覆盖）
  - **删除处理**：文档下线要真正移除对应向量，否则"幽灵文档"会被召回
  - **冲突与去重**：同内容多副本做指纹去重，避免重复占位
  - **版本与回滚**：保留版本号，出问题能回滚到上一版索引
- **五、灰度与验证**
  - 新文档入库后**影子检索**对比新旧召回分布，指标无异常再放量
  - 定期跑一致性 lint：同一问题在新旧文档集上答案是否一致

**Q15: RAG如果有噪声怎么办？**

- 难度：⭐⭐
- 岗位：通用
- 标签：#噪声处理 #数据质量
- 公司：字节、阿里

**💡 参考答案**

先分类噪声来源，再分环节处理。

- **噪声来源**：
  1. **文档级**：模板页眉页脚、导航栏、广告、评论区、版权声明
  2. **切块级**：块内混入无关段落、表格错乱、切断了句子
  3. **召回级**：语义相近但实际不相关的块（假阳性）
  4. **输入级**：用户 query 本身有错别字/歧义
- **处理手段（按流水线顺序）**：
  - **索引前（最划算）**：
    - 模板去噪：正则/规则剥离页眉页脚、导航、广告
    - 质量过滤：太短、乱码率高、重复率高的块直接丢弃
    - 结构化解析：保留标题层级，避免表格串行
    - 去重：文档指纹 + 段落级 SimHash 去重
  - **检索时**：
    - **混合检索 + rerank**：cross-encoder 精排能滤掉大量语义假阳性（**最有效的一招**）
    - 元数据过滤：按来源可信度、时间、类型过滤
    - **相关性阈值**：低于阈值直接丢弃，宁可少给
  - **生成时**：
    - **上下文压缩**：只保留与问题相关的句子
    - Prompt 约束："仅依据材料回答，材料不足则说明无法回答"
    - **引用标注**：强制标出每句依据，暴露噪声
- **兜底机制**：
  - **置信度门控**：召回质量差时**拒答或澄清**，而不是硬答
  - 提供"我查到的相关材料"让用户自己判断
- **一句话**：**噪声治理的重点在索引前和重排，不在生成后**；生成阶段只能缓解，不能治愈。

**Q16: 讲一下BM25算法原理**

- 难度：⭐⭐
- 岗位：通用
- 标签：#BM25 #稀疏检索
- 公司：字节、阿里(高频)

**💡 参考答案**

- **定位**：**稀疏检索**的概率排序模型，是 TF-IDF 的改进版，至今仍是关键词检索的工业标准（Elasticsearch/Lucene 默认）。
- **核心公式（概念版）**：

```
score(D, Q) = Σ  IDF(qi) · [ f(qi,D)·(k1+1) ] / [ f(qi,D) + k1·(1 - b + b·|D|/avgdl) ]
```

- **三个组成部分**：
  1. **IDF（逆文档频率）**：词越稀有越有区分度 → 权重越高。BM25 的 IDF 做**饱和处理并取对数**，避免极端值
  2. **TF 饱和**：词频越高分越高，但**增长边际递减**（受 `k1` 控制，通常 1.2–2.0）。出现 10 次和 100 次的差距远小于线性
  3. **文档长度归一化**：长文档天然含更多词，需要**惩罚长度**（受 `b` 控制，0–1，通常 0.75）。`b=1` 完全归一化，`b=0` 不归一化
- **与 TF-IDF 的关键区别**：TF-IDF 的 TF 无上界（长文刷分），BM25 加了**饱和 + 长度归一化**两个修正，效果显著更好。
- **优缺点**：
  - 优点：无需训练、可解释、对**精确词/术语/编号/ID**（如型号"XPS-9370"、人名）召回极强、快
  - 缺点：**不懂语义**——同义词（"手机"vs"移动电话"）召不回；无法处理未登录词
- **在 RAG 中的角色**：补齐向量检索的短板，与向量做**混合检索**，用 **RRF 融合**——这是目前最稳的召回配置。
- **中文适配**：需先分词（jieba / IK），分词质量直接影响效果。

**Q17: 是否做过意图识别？如果要做意图识别，可以怎么实现？**

**💡 参考答案**

- **定位**：意图识别决定**走哪条链路**——是直接答、走 RAG、调工具、还是澄清/转人工。是 Agent 的"路由器"。
- **实现方案（按成本从低到高）**：

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **规则/关键词** | 正则、词典匹配 | 快、可解释、零成本 | 泛化差、维护累 |
| **小模型分类** | BERT/TextCNN 做多分类 | 快、稳、便宜、可解释 | 需标注数据、类别固定 |
| **LLM + Few-shot** | prompt 给定意图清单 + 示例，输出 JSON | 零标注冷启动、易扩展、能处理长尾 | 慢、贵、有波动 |
| **LLM Function Calling** | 把每个意图封装成工具让模型选 | 天然支持多意图与参数抽取 | 同 LLM 方案 |
| **向量语义匹配** | query embedding 与意图描述向量比对 | 无需训练、易加新意图 | 边界模糊时易混 |
| **Embedding 微调** | 对比学习微调句向量做意图聚类 | 领域适配好 | 工程量大 |

- **工程最佳实践（推荐混合）**：
  1. **规则兜底**：明显意图（含订单号、明确指令）直接命中
  2. **小模型路由**：高频意图用轻量分类模型，快且省
  3. **LLM 兜长尾**：低置信度或未命中交给 LLM 判断
  4. **置信度门控**：低于阈值 → **澄清提问**而不是硬猜
- **关键设计点**：
  - 意图体系要**支持多标签 + 未知类（OOS）**，现实里用户会问没定义过的意图
  - 与**槽位填充（slot filling）**配套：识别意图后还要判断参数齐不齐
  - **数据闭环**：线上低置信样本回流标注，模型持续迭代
  - **分层**：先粗分领域（客服/购买/售后），再细分具体意图，降低单模型压力
- **冷启动路径**：先用 LLM few-shot 上线积累数据 → 蒸馏成小模型降本增速。

**Q18: 介绍检索做的优化，具体追问子问题分解怎么做，有没有做意图识别？**

- 难度：⭐⭐⭐
- 岗位：算法岗重点
- 标签：#检索优化 #子问题分解
- 公司：字节(真题)

**💡 参考答案**

分三块答：检索优化全景 → 子问题分解的具体做法 → 与意图识别的关系。

**一、检索优化的层次**
1. **查询侧**：改写、多查询扩展、HyDE、**子问题分解**
2. **检索侧**：混合检索（向量+BM25+RRF）、元数据预过滤、图检索、层级检索
3. **排序侧**：cross-encoder rerank、上下文压缩、去重与多样性
4. **控制侧**：难度路由（简单直答/中等单次/复杂多步）、置信度门控与拒答

**二、子问题分解怎么做（重点）**

- **触发条件**：检测 query 含多实体、多个问号、并列关系、"和/以及/分别"等连接词，或首轮检索结果分散/低分
- **具体流程**：
  1. **分解**：用 LLM 把复杂问题拆成 N 个自包含的子问题（few-shot 引导）
     - 例："A 公司和 B 公司的 RAG 方案有什么不同" → ① A 的方案是什么 ② B 的方案是什么 ③ 对比维度
  2. **改写自包含**：每个子问题必须**消解指代**，能独立检索（否则检索不到）
  3. **并行检索**：子问题各自检索，互不干扰（可并行降低延迟）
  4. **按需递归**：若子问题仍答不出，再拆一层（限制最大深度，防爆炸）
  5. **聚合**：合并证据 → 判断是否齐备 → 齐备则生成，缺失则补检索或标注"无法回答"
- **两种实现方式**：
  - **Plan-then-Execute**：先一次性规划所有子问题（简单、延迟低，但计划可能不优）
  - **Interleaved（IRCoT 式）**：边推理边发问下一步（更准但轮次多、成本高）
- **关键工程约束**：
  - 必须设 **子问题数量上限 + 最大递归深度 + 总预算**，否则成本和延迟失控
  - 子问题结果要**保留来源**，最终答案需能追溯到原始证据
  - 聚合阶段要有**冲突消解**：不同子问题证据矛盾时如何取舍

**三、与意图识别的关系**
- 意图识别是**前置路由**：先判断"这是不是需要多跳分解的问题"，避免所有 query 都走重链路
- 二者组合成**难度分级**：单跳事实 → 直接检索；多实体对比 → 子问题分解；关系型 → 图检索
- 实践中：**意图识别 + 复杂度分类**共同决定走哪条检索链路，这是控制成本的关键闸门

**Q19: 在RAG里的"召回-过滤-生成"三段式 pipeline能细讲一下吗？**

- 难度：⭐⭐⭐
- 岗位：通用
- 标签：#Pipeline设计 #三段式
- 公司：字节(真题)

**💡 参考答案**

三段式是把 RAG 在线链路拆成职责清晰的三段——**负责召回广度、过滤精度、生成质量**。

**第一段：召回（Recall）——目标是把正确的找进来**
- **设计原则**：**宁滥勿缺**，这一段的 KPI 是 Recall，不是 Precision
- 手段：向量检索 + BM25 并行 → **RRF 融合**；多查询扩展；元数据预过滤（权限/时间/类型）
- 参数：top-k 取大（如 50–100）
- 常见坑：只走向量导致精确词/编号召不回；预过滤条件写错导致正确文档被挡

**第二段：过滤（Filter / Rerank）——目标是把无关的踢出去**
- **设计原则**：**宁缺勿滥**，这一段决定送进 prompt 的质量与 token 成本
- 手段：
  - **Rerank**：cross-encoder / LLM rerank 对候选精排（**核心**）
  - **相关性阈值**过滤低分项
  - **去重**（同文档相邻块、多源重复内容）
  - **上下文压缩**：抽取块内真正相关的句子
  - 多样性控制：避免 top-k 全来自同一段
- 参数：最终留 3–8 条
- 常见坑：不做 rerank 直接生成（噪声进入、幻觉上升）；过滤过狠导致证据不足

**第三段：生成（Generation）——目标是答得对、有依据、不编**
- 手段：
  - **结构化 prompt**：材料编号 + 明确"仅依据材料回答"
  - **位置优化**：最相关的放首尾，防 lost-in-the-middle
  - **强制引用**：每句标注来源，便于核查与追责
  - **不确定性表达**：材料不足时明确说"无法回答"，而不是脑补
  - **后处理**：引用校验（引用是否真的支持该论断）
- 常见坑：不约束就自由发挥；材料堆太多导致中间信息被忽略

**三段之间的关键契约**
- 每段的**输入输出标准要显式定义**（如召回段输出带 score/来源的候选列表），否则无法定位问题出在哪一段
- **各段独立可评估**：Recall@k（召回段）、NDCG/精度（过滤段）、faithfulness（生成段）——**分层定位瓶颈**是这套设计的最大价值
- **降级思路**：召回不足 → 放宽过滤；过滤后证据太少 → 触发补充检索或直接澄清

**Q20: 介绍一下function calling和MCP**

**💡 参考答案**

- **Function Calling（工具调用）**——**模型侧能力**
  - 定义：把工具的 JSON Schema 随请求发给模型，模型输出结构化的调用请求 `{name, arguments}`，由宿主运行时执行后把结果回填，模型继续推理。
  - 关键点：它是**模型输出格式能力 + 应用侧执行闭环**；模型只负责"决定调什么、参数是什么"，**执行永远在应用侧**。
  - 训练：SFT 在 (指令, 工具 schema, 正确调用) 数据上学格式与选择；RL 提升多步成功率。
  - 局限：每个应用要自己接一堆工具，**N 个应用 × M 个工具 = N×M 个适配器**。

- **MCP（Model Context Protocol）**——**协议层标准**
  - 定义：统一"模型应用 ↔ 外部能力"的接入协议，把工具/资源/提示标准化，**一次实现，处处可用**。
  - 架构：**Host / Client / Server** 三角色；Server 提供 Tools / Resources / Prompts；传输支持 stdio 与 Streamable HTTP。
  - 价值：把 N×M 降为 **N+M**——工具方写一次 Server，应用方接一次 Client。

- **二者关系（关键）**：

| | Function Calling | MCP |
|---|---|---|
| 层次 | 模型能力 / 调用格式 | 通信协议 / 接入标准 |
| 解决 | 模型怎么"表达"要调工具 | 工具怎么被"发现与接入" |
| 类比 | 函数签名 | 驱动接口规范（如 USB） |
| 关系 | **MCP 的 Tools 最终仍通过 Function Calling 呈现给模型** | MCP 是对 FC 的工程化封装 |

- **一句话**：**Function Calling 解决"怎么调"，MCP 解决"去哪找、怎么接"**；两者是层次关系，不是替代关系。
- 延伸：MCP 管 `Agent ↔ 工具`，**A2A** 管 `Agent ↔ Agent`（→ [[01-Wiki/concepts/A2A 协议]]）。

**Q21: 在高并发查询 Agent 系统中，你会如何优化召回和生成阶段的延迟？**

- 难度：⭐⭐⭐
- 岗位：开发岗重点
- 标签：#高并发 #延迟优化
- 公司：字节(真题)

**💡 参考答案**

按阶段拆解，每段给可落地手段。

**一、召回阶段**
1. **缓存**：**语义缓存**（query embedding 命中相似问题直接返回）、热点 query 结果缓存
2. **索引优化**：ANN 索引选型（HNSW 高召回低延迟）、**量化**（PQ/SQ）降内存提速度、维度压缩
3. **分片与副本**：向量库水平分片 + 读副本，分摊 QPS
4. **预过滤**：标量过滤先缩小搜索空间，避免全库扫描
5. **减少召回量**：先粗排少量候选，别一上来就 top-1000
6. **并行**：向量检索与 BM25 检索并行发起，而非串行
7. **embedding 加速**：query 侧 embedding 用小模型/本地 GPU/缓存

**二、生成阶段**
1. **首 token 优化**：**流式输出（SSE）**——用户感知延迟大幅下降（体感从"等 2s"变成"200ms 就开始出字"）
2. **模型侧**：小模型/蒸馏模型处理简单问题、**量化**（INT8/FP8）、投机解码
3. **推理引擎**：vLLM/TensorRT-LLM 的 **continuous batching** + paged attention 提升吞吐
4. **KV Cache 复用**：相同 system prompt 前缀做 prefix caching
5. **缩短上下文**：rerank 后只送 3–5 条 + 上下文压缩，**prompt 越短生成越快**
6. **控制输出长度**：限制 max_tokens，明确要求简洁

**三、链路与架构层**
1. **难度路由**：简单问题走轻量链路（小模型直答/缓存），复杂问题才走重链路
2. **并行化**：检索、权限校验、记忆读取并行；多工具调用并行
3. **异步与队列**：网关限流 + 优先级队列（SLA 分级），避免高峰雪崩
4. **减少串行步数**：合并 prompt、一次生成多个字段
5. **多副本 + 就近部署 + 连接复用**（gRPC/HTTP2）
6. **预热**：模型与索引预热，避免冷启动尖刺

**四、度量与治理**
- **拆指标定位瓶颈**：TTFT（首 token）、检索耗时、rerank 耗时、TPOT（每 token）——**不拆开就不知道优化哪里**
- 目标：P95/P99 时延、缓存命中率、单查询成本
- **降级预案**：LLM 超时 → 返回检索结果摘要；rerank 超时 → 直接用粗排

**Q22: 如果让 agent 调用搜索引擎，如何避免无关结果影响回答？**

- 难度：⭐⭐
- 岗位：通用
- 标签：#结果过滤 #相关性
- 公司：字节(真题)

**💡 参考答案**

- **一、查询侧（源头提质）**
  - **查询改写**：口语转关键词、加上时间/地域限定，搜索引擎对关键词敏感
  - **多查询生成**：一次生成 2–3 个角度不同的查询，扩大有效召回
  - 明确站点/语言/时间范围（site:、since:），缩小搜索空间
- **二、结果筛选（核心）**
  - **相关性重排**：对返回结果做 cross-encoder/LLM rerank，只保留高分项
  - **来源可信度加权**：白名单域名 > 一般站点 > 论坛/UGC > 广告位（搜索引擎结果里**广告和 SEO 垃圾是最主要的噪声**）
  - **去重**：同一内容的多站点转载，做指纹去重
  - **时效过滤**：丢弃过期页面
  - **抽取正文**：只取页面正文段落，剥掉导航、广告、推荐位
- **三、内容层面**
  - **上下文压缩**：只保留与问题直接相关的句子（而非整篇塞入）
  - **篇幅控制**：每条结果限长，避免一条长文挤占全部上下文
- **四、生成侧约束**
  - Prompt 明确：**"仅依据以下材料回答；材料不足则明确说明无法回答"**
  - **强制引用**：每个论断标注来源链接，倒逼模型不编造
  - **置信度门控**：材料相关性整体偏低时，**拒答或反问澄清**，而不是硬凑答案
- **五、对抗性风险（必须防）**
  - **间接 Prompt 注入**：网页内容里可能藏"忽略之前的指令"这类指令——**把检索结果当作不可信数据**，与指令严格隔离（→ [[01-Wiki/concepts/Agent 安全与对齐]]）
  - 来源审计：记录每次引用了哪些页面，便于追责与回溯
- **一句话**：**搜索引擎负责召回，重排与来源过滤负责降噪，prompt 约束负责防止脑补**——三层缺一不可。
