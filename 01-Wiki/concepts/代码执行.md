# 代码执行（Code Execution）

## 定义

让 LLM **编写并运行代码**来解决任务——既是工具的一种，也是"行动（action）"的一种形式。与"为每个功能手造工具"相比，它用代码的通用性换掉了工具集的枚举需求。

## 为什么强

- **强大**：LLM 生成的代码方案常常出人意料地聪明有效
- **灵活可扩展**：科学计算器有大量功能按钮，不可能为每个按钮造一个工具；而"让模型自己写代码"一次覆盖所有功能
- **被专门优化**：许多模型训练者会专门优化模型，确保代码执行功能在应用中表现良好

## 机制/原理：四次交互

1. **设计系统提示词**：指令模型"编写代码解决问题"，要求以 Python 返回并用 `<execute_python>` `</execute_python>`（或 ``` 围栏）标签包裹
2. **模型输出**：如 `import math` + `print(math.sqrt(2))`
3. **提取与执行**：用正则等模式匹配提取标签内代码 → **在安全沙盒中执行** → 得 `1.4142135623730951`
4. **反馈与格式化**：数值结果传回 LLM → 生成格式良好的最终答案

执行载体：Python 内置 `exec()`（可执行任意字符串代码，强大但有安全风险）或专用沙盒工具。

## 例子

- **预定义工具集 vs 代码执行**：为数学题建 `add` / `subtract` / `multiply` / `divide`，遇到"2 的平方根"就得再加 `sqrt`——工具集永远追不上需求
- **结合外部反馈的反思**：执行初稿代码捕获 `SyntaxError` → 连同任务发回模型 → 模型反思并产出 V2
- **code-as-action 规划**：处理"哪个月份热巧克力销量最高"这类查询，若只给 `获取最大值`/`过滤行` 等基础工具会得到极其冗长的调用序列；直接写代码则可利用 **Pandas 数百个内置函数**，简洁表达"解析日期 → 排序 → 过滤 → 去重 → 计数"。论文普遍表明**同样的工具与参数下，写代码的评估分数明显高于写 JSON 再解析**（→ [[01-Wiki/entities/smolagents]] 的 CodeAgent）

## 安全：本主题的核心风险

- **真实事故**：某团队成员使用的高度 agentic 化代码执行器**错误执行了 `rm *.py`，删除了项目目录中所有 Python 文件**；因该成员有备份习惯才未造成实质损失
- **最佳实践**：**必须使用沙盒环境**；推荐 **Docker** 或 **E2B** 这类轻量级沙盒，隔离代码、降低损坏系统或环境的风险
- **现实**：仍有不少开发者直接执行模型生成的代码而不做检查——这是系统性风险

## 边界与常见误区

- 代码执行 ≠ 沙盒执行：把"能跑"当成"安全"是最大的误区
- 提示词要求必须明确（要求返回代码 + 指定围栏标签），否则提取步骤不稳定
- 与 [[01-Wiki/concepts/Tool Calling]] 的分工：简单、语义明确的动作做成工具；需要组合计算/数据处理的复杂动作交给代码执行
