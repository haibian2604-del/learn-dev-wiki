# 反思模式（Reflection）

## 定义

让模型**对自己的输出进行检查、评估、改进**的设计模式。类比人类写作：写完初稿回读，发现模糊、拼写、遗漏，再修改。是"经常使用且实现起来出奇地简单"的优化手段——**不保证 100% 正确，但性价比极高**。

## 机制/原理：四步循环

1. **初始生成**：模型按任务要求产出初稿（邮件/代码/图表）
2. **自我或外部评估**：把结果作为输入，再次提示同一模型或另一个模型做批判性分析（检查正确性、风格、效率，给改进建议）
3. **迭代优化**：把评估反馈（"第 5 行有 bug""单元测试失败"）交给模型生成更好的版本
4. **循环往复**：可多次迭代直到满意

关键点：

- **流程通常是硬编码的**——工程师预先设计"生成 → 反思"两步，而不是让模型自主决定何时反思。这是可靠且易实现的工程化方法
- 反思可由同一模型完成，也可引入专门扮演"审查者"的独立模型——**这就是多智能体协作的雏形**（双 Agent 对话模式，→ [[01-Wiki/concepts/单 Agent 与多 Agent]]）
- 评估标准可客观（代码能否运行）也可主观（代码风格）

## 三个能力层次

| 层次 | 做法 | 增益来源 |
|------|------|----------|
| 内省 | 初稿 → "检查错误并写改进版" | 模型自身的一致性检查 |
| 模型分工 | 快模型写初稿 + **思考模型（Reasoning Model）** 做反思 | 发挥不同模型优势，1+1>2 |
| **外部反馈** | 沙盒执行代码 → 捕获 Output/Errors → 连同初稿一起反思重写 | **引入模型之外的新信息，质的飞跃** |

## 例子

- **写邮件**：V1 存在"next month 太模糊 / fre 拼写错 / 无署名" → 反思后 V2 明确日期、修拼写、加署名
- **写代码**：把 code V1 与 `SyntaxError: unterminated string literal` 一起反馈 → V2 功能正确
- **多模态图表**：V1 生成的堆叠柱状图不直观 → 把代码 + plot.png 交给**多模态模型**扮演"专家数据分析师"，评估可读性/清晰度/完整性 → V2 代码产出新图

## 反思提示词的两条黄金法则

1. **明确指示反思动作**：不说"请改进"，说"请审查 / 请检查 / 请验证"
2. **具体指定检查标准**：不说"让它更好"，列出评判维度（域名的"易发音 + 无负面含义"；邮件的"语气专业 + 事实准确"）

## 外部反馈：为什么它最重要

提示词工程存在**收益递减规律**——初期快速提升后进入平台期。三层台阶：

- 调提示词 → 到平台期
- **+ 反思** → 曲线上扬到更高平台
- **+ 外部反馈** → 再次跃升到远超两者的平台

外部反馈的三种来源：**模式匹配**（正则扫描是否提及竞争对手）、**网络搜索**（核实"泰姬陵 1631 年下令建造、1648 年完工"）、**统计工具**（字数是否超限）。

## 如何判断值不值得保留

反思会略微拖慢 Agent，必须用评估决定去留（→ [[01-Wiki/concepts/Agent 评估]]）：

- **客观任务**（如 SQL 查询）：建"提示词 + 真实答案"数据集，用代码自动判分。实测"哪个月份销量最高"类任务，**+8%** 准确率提升 → 值得保留
- **主观任务**（如图表美观度）：用 **Rubric 评分量表**引导 LLM 逐维度打分（是否有标题/轴标签/图型是否合适/数值范围是否恰当），**不要让它直接比较两张图**——已知 LLM 存在**位置偏见（position bias）**，倾向选第一个选项

## 边界与常见误区

- **反思不是魔法**：不保证每次正确，只带来"适度的性能提升"；且效果**因场景而异**，有些任务提升显著、有些微乎其微
- 误区：把反思当成"免费午餐"——增加 token 成本、执行时间与系统复杂度
- 误区：只让模型"内省"就期待大幅提升——**真正的突破来自外部反馈**
