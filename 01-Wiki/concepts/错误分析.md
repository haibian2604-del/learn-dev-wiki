# 错误分析（Error Analysis）

## 定义

通过**观察与量化**找出工作流中表现最差的组件的系统性方法。回答的问题是"**到底哪个环节拖低了最终效果**"，从而把有限的构建精力投到收益最大的地方。它是"评估"的归因层，与 [[01-Wiki/concepts/Agent 评估]] 的指标层互补。

## 为什么要做（而非靠直觉）

- Demo 阶段能靠直觉，系统 MVP 或即将投产时已十分复杂，"到底是哪一环节出了问题、要不要拆出来单独跑、要不要 Mock 数据"——**靠直觉就对直觉准度提出了极大考验**；若系统还需经常更换底层 LLM，风险更大
- 从一开始纳入计划，可在项目复杂化/工程化后仍良好管理，并**锻炼 Agent 直觉**（识别哪些组件稳定、哪些易受模型或输入格式影响）

## 机制/原理：两步动作

### 1. 检查追踪（Traces）与中间输出

- Agent 运行时每步产生的中间输出整体称为**追踪（trace）**；单个步骤的输出称为 **span**
- 先通读 trace 观察每步质量，笼统判断哪个组件有问题
- 示例（科研查询 Agent）：① 生成搜索词 → 请人判断是否合理；② 网页搜索结果 → 看 URL 与文章质量，若多为非科学博客则问题在搜索引擎；③ 信息筛选 → 若 LLM 选了耸动水文而非严肃论文，则问题在 **LLM 型号或提示词**

### 2. 聚焦错误案例并量化

- 聚焦**最终输出不令人满意**的少数案例，不看运行良好的
- 建电子表格统计各组件"出错"频率
  - **错误的定义**：某一步的输出明显差于人类专家在相同输入下会给出的结果
- 用频率排序决定优先级：若"搜索结果不满意"占 45%、"搜索词不满意"占 5%，就改搜索引擎/参数，而非搜索词生成逻辑

## 例子

| 案例 | 候选病灶 | 结论与优先级 |
|------|----------|-------------|
| 发票到期日提取 | ① PDF 转文本太差 ② LLM 拉错日期（发票日期 vs 到期日） | 若 LLM 提取占比更高 → 改提示词，**别花数周改 PDF 转文本** |
| 客服邮件回复不令人满意 | ① LLM 写错 SQL ② 数据库数据错误 ③ LLM 邮件语气不妥 | 若写查询占 75%、写邮件占 30% → 先改查询，再改撰写提示词 |

> 注意：同一坏 case 可归因到多个组件，统计口径是"错误案例中各组件被判定有问题的占比"，而非互斥划分。

## 与组件级评估的衔接

错误分析定出病灶后，用**组件级评估**做针对性调优（→ 关系类比：组件级评估 : 端到端评估 = 单元测试 : 集成测试）：

1. 错误分析确定问题组件（如网页搜索）
2. 建组件级评估（黄金标准网页列表 + **F1 分数**衡量重叠度）快速调参
3. 调优后跑最终端到端评估，验证组件改进确实提升了整体性能

> 组件级评估的价值：**避免端到端评估的噪声掩盖微小增量收益**，并支持团队分工各自维护指标。

## 改进手段清单

| 组件类型 | 手段 |
|----------|------|
| 非 LLM 组件 | 调参（搜索结果数/日期范围、相似度阈值/分块大小、检测阈值）；替换服务商（国内查财报用百度优于 Bing/Google，查学术资源则相反） |
| LLM 组件 | ① 改进提示词（明确指令 + 少样本）② 换模型（用评估选型）③ 任务分解 ④ 微调（最后手段） |

## 在开发流程中的位置

四阶段模型中，错误分析是第 3 阶段（→ [[01-Wiki/summaries/Agentic AI 课程 4.8 开发过程总结]]）：

1. 快速原型——手查输出、读 trace、凭直觉
2. 初步评估——端到端评估（10-20 例）
3. **严谨分析——错误分析量化各组件出错频率**
4. 高效调优——组件级评估

## 边界与常见误区

- 新手通病：**太多时间构建、太少时间分析**，导致重点不集中、效率低下
- 矛盾信号：系统改进了但评估分数没涨 → **该改进评估本身**了
- 归因依赖人工判断，规模化困难（自动化归因仍是开放问题）
