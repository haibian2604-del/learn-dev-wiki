# Agent 安全与对齐（Safety & Alignment）

## 定义

- 让 Agent 的行为**安全、可控、符合人类意图**的一整套技术与工程约束。
- 核心立场：**不信任 LLM 本身**。模型可以被说服、被注入、会幻觉，因此安全**不能靠提示词保证，必须落在系统层**——纵深防御（defense in depth）+ 最小权限 + 人在回路。

## 机制/原理

### 一、按 Agent 生命周期的分层防御

| 层 | 手段 |
|----|------|
| **目标 / 规划层** | 约束与禁止项显式写入 system prompt；高风险任务先做 **plan review**；关键步骤人机协同（HITL）审批 |
| **输入层** | prompt 注入检测、内容审核、PII 识别与脱敏、意图风险分级 |
| **执行层** | **最小权限**（工具级 ACL / RBAC）、**沙箱隔离**、出口白名单、限额与熔断、幂等与可回滚、高风险操作二次确认 |
| **监督层** | guardrail 模型（如 Llama Guard）审核输入输出、规则引擎、异常检测、自我批判 / verifier agent |
| **训练 / 对齐层** | RLHF / DPO 对齐价值观、Constitutional AI、**学会拒答与表达不确定性** |
| **验证层** | 结果校验（dry-run / 模拟执行 / 形式化约束） |
| **治理层** | 红队测试、注入与越权基准、全链路审计日志、持续监控与回滚 |

### 二、三条底线（面试可直接用）

> **能拦住**（guardrail + ACL）· **能看见**（全链路 trace + 审计）· **能撤销**（幂等 + 补偿事务 + 回滚）

自主性越高，越要在这三条上投资。

### 三、隐私与越权（Q46 的解法）

- **算法层**：PII 识别与脱敏 ← 输入侧；输出侧 DLP + guardrail 审核；把用户身份与权限注入上下文，模型只应请求被授权的操作
- **系统层**：
  - 认证鉴权（用户级 + 服务级）、**最小权限（RBAC / ABAC）**
  - **多租户数据隔离**：检索时按 `user_id` **强制过滤**，防跨用户召回
  - 传输/存储加密 + 密钥管理
  - 代码沙箱、出口白名单、只读优先
  - **支付/删除等高危操作强制人工确认 + 二次验证**
  - 全链路操作审计，可溯源可回滚

### 四、Prompt 注入的特殊性

工具返回内容（网页、文档、API 响应）是**不可信数据**，必须与指令**严格隔离**——否则一条藏在文档里的"忽略之前的指令"就能劫持 Agent。这被称为**间接注入**，是 Agent 相比 Chatbot 新增的攻击面。

## 例子

**行程规划 Agent 的权限设计**：
- 查询天气/景点 → 只读工具，无限额
- 预订酒店 → 写工具，需**用户确认 + 金额上限 + 幂等 key**
- 支付 → 最高风险，**二次验证 + 人工确认节点**，且操作全量审计
- 用户 A 的历史订单绝不出现在用户 B 的检索结果里（user_id 硬过滤）

## 边界与常见误区

- ⚠️ **"把规则写进 system prompt"不是安全机制**：提示层可被覆盖，只有系统层的 ACL 与沙箱是硬的
- ⚠️ **对齐 ≠ 只做 RLHF**：训练侧对齐管"倾向"，系统侧管"能力边界"，二者缺一不可
- ⚠️ **审核模型不是银弹**：guardrail 自身有误杀与漏检，需要阈值调优 + 人工抽检
- **过度限制的代价**：权限收得太紧会让 Agent 变得无用（大量任务卡在确认环节），需按风险分级而非一刀切
- **失败也要安全（fail safe）**：能力不足时应**明确告知并降级**，而不是静默编造或崩溃
