# 向量数据库

## 定义

专门用于存储、索引和检索**高维向量数据**的数据库系统，靠语义相似度（而非精确匹配）做检索；是 RAG / Agent Memory / 语义搜索的底层存储。

## 机制/原理

1. **向量嵌入**：AI 模型（text-embedding-3-small、BGE 等）把文本/图/音转成浮点数组，捕捉语义（如 1536 维）
2. **相似性搜索**：查询内容先转向量，再在库中找"距离最近"的向量（距离越近语义越相似）
3. **ANN 近似最近邻**：高维精确搜索太慢，牺牲少量精度换巨大速度提升，工程可接受
   - **HNSW**：召回最高、查询快、内存大，大部分场景首选
   - **IVF-PQ / IVF_FLAT**：省内存，百万级+（Milvus 用 IVF_FLAT+ COSINE，见 [[01-Wiki/entities/Milvus]]）
   - **Flat**：暴力搜索，精度 100%，数据 <10 万且精度敏感
   - **DiskANN**：磁盘索引、内存友好，千万级+

对比传统关系库：数据类型（结构化 vs 高维向量）、查询（精确 WHERE vs 相似最近邻）、典型场景（CRUD/事务 vs RAG/推荐/语义搜索）、索引（B-Tree/Hash vs HNSW/IVF/PQ/DiskANN）。

## 例子

- RAG：`collection.query(query_texts=[...], n_results=3)` 取 top-k 文档拼进 prompt（→ [[01-Wiki/concepts/RAG]]）
- Agent Memory：Qdrant 用 `query_filter` 做"语义相似 + 元数据(user_id/timestamp)过滤"
- 选型：数据 <10 万用 Flat；100 万-1000 万用 Qdrant/Milvus；>1000 万用 Milvus（DiskANN/分片 HNSW）

## 边界与常见误区

- 与 [[01-Wiki/entities/Redis向量库]] 同理：**RAG 本质不绑定某一库**，换 Chroma/FAISS/Milvus/pgVector 思路不变
- 坑：小数据量上 Milvus 全套（过度工程）；入库/查询用不同 embedding 模型（向量空间不一致）；索引选错（<100K 用 IVF-PQ 召回差）
- Embedding 模型比数据库选择更关键——数据库只是存储工具
