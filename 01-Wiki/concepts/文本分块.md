# 文本分块（Chunking）

> RAG 索引阶段的核心步骤：把长文档切成便于检索与向量化的小片段。

## 定义

切块（chunking）是把大文档拆成多个更容易参与检索的小段。**切块策略直接影响 RAG 最终效果**，是质量的重要一环。

## 为什么必须切块

- **检索效果差**：整篇文档向量表达粗糙，难以精确定位相关小段
- **生成成本高**：整篇塞不进上下文，或大量无关内容稀释关键信息
- 即使模型支持长上下文，也不意味着直接塞整篇更好——切块+检索本质是**帮模型先做一轮信息筛选**

## 常见分割器

| 分割器 | 作用 |
|--------|------|
| **RecursiveCharacterTextSplitter** | 通用首选，优先保持大语义单位，必要时递归切细 |
| CharacterTextSplitter | 按指定分隔符切，简单直接 |
| MarkdownHeaderTextSplitter | 按标题层级切分 |
| TokenTextSplitter | 按 token 数控制块大小 |
| 语义切分（Semantic Chunking） | 按语义变化切分，更保完整但成本高 |

## 关键参数

| 参数 | 含义 | 实践理解 |
|------|------|----------|
| `chunk_size` | 单块最大长度 | 太大不利检索，太小语义碎片化 |
| `chunk_overlap` | 相邻块重叠长度 | 防句子被截断，常见取 10%~20% |
| `length_function` | 长度计算方式 | 默认 `len`（字符数），也可按 token |
| `separators` | 优先切分分隔符 | 决定按段落/换行/句号切分的优先级 |

> overlap 会使相邻块重复，总字符数大于原文——这是设计使然（保证语义完整），非 bug。

## 边界与常见误区

- 不存在"永远最优"的块大小：与文档类型、语言、问答粒度、模型上下文长度都有关
- 切分策略不是越高级越好：语义切分成本高，入门先用好 RecursiveCharacterTextSplitter
- 三种切分入口：`split_text`（字符串→列表）、`create_documents`（字符串列表→Document）、`split_documents`（Document 列表→更小 Document，真实项目最常用）
