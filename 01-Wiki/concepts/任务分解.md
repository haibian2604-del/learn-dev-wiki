# 任务分解（Task Decomposition）

## 定义

构建 Agentic 工作流的第一技能：**把复杂任务拆成多个独立、清晰的子步骤，使每步都能由 LLM 或某个工具（API / 函数调用）承担**。它是"多步迭代换质量"的前提。

## 机制/原理：四步方法

1. **观察人类行为**——"如果一个人来做，他会怎么做？"
2. **拆解步骤**——拆成独立的、清晰的子步骤
3. **评估可行性**——每步自问"能否用 LLM 或某个工具实现？"
4. **迭代优化**——效果不理想就把该步继续细分

> 核心方法论：**"如果某一步骤效果不好，就把它再拆成更小的子步骤。"**

## 例子：写深度文章的三种拆法

| 拆法 | 步骤 | 效果 |
|------|------|------|
| 1 步 | 一个 prompt → 文档 | 表面化、缺乏深度与一致性 |
| 3 步 | 大纲 → 搜索 → 写论文 | 有外部信息，但首中尾风格可能脱节 |
| **5 步** | 大纲 → 搜索 → 初稿 → **考虑哪些部分需修订** → 修订 | 模拟"写作-反思-修改"循环，质量显著提高 |

其他实例：回复客户邮件（提取信息 → 查订单库 → 撰写并发送）；发票提取（查找字段 → 写入数据库）。

## 拆完之后：基本构件

| 构件 | 内容 | 用途 |
|------|------|------|
| **模型** | LLM | 文本生成、工具使用决策、信息提取 |
| **模型** | 其他 AI 模型 | PDF 转文本、TTS、图像分析等非文本模态 |
| **工具** | API | 网页搜索、天气、发邮件、日历 |
| **工具** | 信息检索 | 数据库/大文本库检索（→ [[01-Wiki/concepts/RAG]]） |
| **工具** | 代码执行 | 让 LLM 写并运行代码做计算（→ [[01-Wiki/concepts/代码执行]]） |

## 工作流设计原则

1. **从简单开始**：先做 1-3 步原型，再逐步扩展
2. **模块化设计**：每步尽量独立、可复用
3. **容错与反馈**：加入"检查""评审"步骤，避免错误累积
4. **持续迭代**：没有一步到位的完美工作流

## 工程用法：作为一种改进手段

在 [[01-Wiki/concepts/错误分析]] 的改进清单中，"任务分解"是 LLM 组件的第三种改进手段：**当单个步骤的指令过于复杂导致 LLM 难以准确执行时，拆成更小步骤**（如"生成 + 反思"两步，或连续多次调用）——注意此处是为**修 bug** 而拆，而非一开始就拆。

## 边界与常见误区

- 拆得越细不等于越好：步骤增多会累加延迟与调用成本（→ [[01-Wiki/concepts/延迟与成本优化]]），且每步都可能引入新错误
- "迭代到满意"缺乏量化停止判据——实践中应配合 [[01-Wiki/concepts/Agent 评估]] 的数据决定拆到几档
- 与 [[01-Wiki/concepts/规划模式]] 的区别：**任务分解是人（或人指定 LLM）静态拆好的结构，规划模式是模型运行时动态决定步骤顺序**
