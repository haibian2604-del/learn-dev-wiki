# 延迟与成本优化（Latency & Cost Optimization）

## 定义

在系统**输出质量达标之后**才启动的优化阶段，目标是用基准测试定位工作流的延迟与成本瓶颈并针对性削减。

## 核心原则：优化顺序不可颠倒

1. **先质量**——早期团队的高质量输出比延迟与价格重要得多，不应首先把时间花在延迟/价格优化上
2. **再延迟**——系统运行良好后才转向延迟优化
3. **最后成本**——只有当系统有了大量用户、成本成了问题时，才是集中优化成本的理想时机

## 一、优化延迟：计时基准测试

- **计时分析**：详细记录每步耗时（如 LLM 1 耗时 7 秒，LLM 3 耗时 18 秒）
- **定位瓶颈**：通过时间线分析找出耗时最长的组件，确定最大提速空间
- **优化手段**：
  - **并行化**：把可独立进行的步骤（如网页抓取）并行执行
  - **更换 LLM**：用更小更快的模型（可能稍不智能），或测试不同提供商以找返回 token 最快的服务

## 二、优化成本：成本基准测试

- **成本计算**：算每步平均成本
  - LLM：按输入与输出 Token 长度收费
  - API：按调用次数收费
  - 计算/服务：按服务器容量、服务费计算
- **定位瓶颈**：确定成本贡献最大的组件
- **优化手段**：寻找更便宜的组件或 LLM 替代高成本组件

## 多智能体是隐性的成本杠杆

拆成多 Agent 后：每个 Agent 上下文较短 → 更省 Token 费用；上下文越短回复越快、延迟越低；多个 Agent 可并行处理任务 → 时间成本进一步下降（→ [[01-Wiki/concepts/单 Agent 与多 Agent]]）。

## 边界与常见误区

- 误区：**过早优化成本**——在质量未达标时省 token，等于把问题从"贵"换成"不可用"
- 误区：把"并行化"当万能——并行会放大成本（同时发起多路调用），且受限于步骤间依赖
- 基准测试是一次性的：应做成持续监控才能发现退化（→ [[01-Wiki/concepts/Agent 可观测性]]）
