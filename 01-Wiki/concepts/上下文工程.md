# 上下文工程（Context Engineering）

> 在推理阶段策划与维护"最优信息集合（tokens）"的系统方法，是提示工程的自然演进。关心每次模型调用前如何以可复用、可度量、可演进的方式拼装并优化输入上下文。

## 定义

- 提示工程：如何编写与组织 LLM 指令（系统提示写法、结构化策略）
- **上下文工程**：如何策划进入上下文窗口的**一切信息**——系统指令、工具、MCP、外部数据、消息历史，目标是最大化期望行为概率

## 机制/原理

### 为什么要做：上下文腐蚀（Context Rot）

- needle-in-a-haystack 基准显示：上下文 tokens 增加 → 模型回忆准确率下降
- 原因：Transformer 注意力是 n² 级两两关联，上下文越长被"拉薄"；训练分布偏好短序列
- 结论：**上下文是有限资源，边际收益递减**——每个 token 都要谨慎筛选

### 有效上下文三组件

- **系统提示**：最小必要信息集（"最小"≠"最短"），分区组织（XML/Markdown），不过度硬编码、不空泛
- **工具集**：最小可行工具集（MVTS）——功能边界模糊会让"选哪个工具"本身变难
- **示例**：精选多样典型 few-shot，好的示例胜过千言万语

### JIT 上下文（Just-in-time）

- 从"推理前一次性检索"→"维护轻量化引用（路径/查询/URL）+ 运行时动态加载"
- 认知模式贴近人类：用文件系统、书签等外部索引按需提取，而非死记硬背
- 混合策略更有效：前置高价值上下文保证速度 + 允许按需自主探索

### 长时程任务三手段

| 手段 | 定义 | 适用 |
|------|------|------|
| 压缩整合 Compaction | 接近上限时高保真总结，摘要重启新窗口 | 长对话连续性 |
| 结构化笔记 | 固定频率写入上下文外持久化存储，按需拉回 | 迭代式开发/研究 |
| 子代理架构 | 主代理规划+子代理干净上下文深挖，回传 1-2k token 摘要 | 复杂研究与并行探索 |

### GSSC 流水线（ContextBuilder 实现）

1. **Gather**：多源汇集（系统指令高优先级、记忆、RAG、历史、自定义），容错
2. **Select**：综合分 = 相关性权重×相关性 + 新近性权重×新近性，贪心填充 token 预算
3. **Structure**：分区模板 `[Role & Policies]/[Task]/[Evidence]/[Context]/[Output]`
4. **Compress**：超限时兜底压缩（分区截断/LLM 摘要）

## 边界与常见误区

- 上下文工程不是把提示写得更好，而是管理整个上下文状态（含工具/MCP/历史）
- 无限增大上下文窗口不能根治污染与退化
- 简单评分（相关性+新近性）在多数场景已足够；复杂维度（来源/优先级）反而增加复杂度

## 补充视角：Context / State / Memory 区分（zero2Agent 06）

> 来自 [[01-Wiki/summaries/Context、State 与 Memory]]

- **messages**（一次请求的协议化消息）≠ **Context**（本次推理可见工作集）≠ **State**（应用维护的结构化执行状态）≠ **Memory**（选择保留/更新/取回的信息）≠ **RAG**（外部知识检索）
- **Context = 静态前缀 + 动态执行轨迹 + 本轮补充信息**：静态前缀（系统指令/工具定义/固定输出规范）跨请求稳定；动态轨迹（用户消息/工具调用结果/阶段结论）随任务推进变化
- **很多 Memory 问题本质是 State 没设计好**；设计顺序：先结构化 State → 再管理会话 Context → 最后验证是否需要长期 Memory
- **工具调用因果配对是裁剪底线**：未完成的 tool_call/tool_result 配对不能切开，不能留"孤儿结果"
- **KV Cache（单次推理内注意力优化）≠ Provider Prompt Cache（跨请求前缀复用）**：只有服务端明确返回 cached input tokens 等字段才能作观测数据；正确性始终优先于缓存

## 补充视角：系统化 Context Engineering（zero2Agent 13）

> 来自 [[01-Wiki/summaries/Context Engineering：系统化设计模型输入]]

- **Context 五组成部分**：System Prompt / Tool Definitions / Conversation Trajectory / Dynamic Metadata（状态栏、时间、环境）/ Retrieved Content（RAG、Skills 文档）
- **Agent Skills 三层加载架构**：Metadata（始终在 Context，几百 token，能力发现）→ Core Workflow（按需加载，完整执行指令）→ Detailed Docs（深度按需经工具读取）。平衡 token 与能力发现，避免"全注入爆 token"或"全工具读取不知有该能力"
- **Status Bar**：结构化执行元数据（task_plan 勾选、剩余工具调用、token 预算、时间、警告）显性注入——模型上下文学习更接近"检索"而非"推理"，显性化状态减少推断负担；但 Status Bar 被无条件信任，只能从可靠程序状态派生
- **三设计原则**：稳定内容在前动态在后（前缀缓存命中 + 注意力位置偏差）、不在 Context 重复信息、正确性优先于缓存
- **Prompt Engineering 五维度**：语气风格 / 结构化组织（XML 分区）/ 流程驱动（SOP 而非规则堆砌）/ 业务规则精炼 / Few-shot（2-3 精选覆盖标准+边界+应拒绝）
