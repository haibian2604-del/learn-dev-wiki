# 单 Agent 与多 Agent（Single vs Multi Agent）

## 定义与核心判断

多 Agent 的价值前提不是"角色名漂亮"，而是**任务是否真的存在明确的职责分离**。大多数项目第一版应优先从单 Agent 做起——单 Agent 做稳之前，多 Agent 大概率只会把问题复制并放大。

## 单 Agent 更合适的场景

目标单一、状态可集中管理、工具集不复杂、不需多独立视角长期博弈、系统优先稳定。例：风险初筛、文档问答、单任务研究分析、工单分类处理。

## 多 Agent 真正有意义的四类场景

1. 职责确实不同（收集 vs 审查裁决，输入/输出/关注点真不同）
2. 上下文压力太大（不同子任务需不同上下文，硬塞一个 Agent 又长又乱）
3. 任务可并行（多独立方向同时搜集再汇总）
4. 需要对抗/复核机制（生成方案 + 找漏洞 + 最终裁决）

## 三种协作模式

1. **分发-汇总（Fan-out/Fan-in）**：协调者拆任务并行分发执行最后汇总。适合子任务独立。
2. **流水线（Pipeline）**：串行传递（收集→结构化分析→输出审核）。适合有明确阶段。
3. **对抗式（Adversarial）**：Generator → Critic → Judge。适合正确性极重要、避免单一视角盲区。

## 上下文共享 vs 隔离（核心架构决策）

- 完全共享：信息不丢失但上下文爆炸、职责边界模糊
- 完全隔离：不干扰但传递成本高、可能重复工作
- **选择性共享（推荐）**：只传结构化中间结果，需设计接口协议——大多数生产系统选此

子 Agent 上下文注入：最小化（只给任务描述+参数）/ 手动选择 / 自动裁剪（按相关度过滤）。注意：子 Agent 上下文可能含不可信外部数据（其他 Agent 输出、工具返回），仍需独立权限与约束。

## 涌现行为与成本

多 Agent 交互可能出现单独测试观察不到的行为：回音室效应（互相确认结论越来越极端）、资源竞争死锁/活锁、隐含协议（换模型版本就崩溃）。应对：长时间集成测试、监控交互模式、全局轮次上限与成本预算、保留人工介入点。

被低估的成本：Agent 间通信、全局状态归属、最终决策权、冲突解决、协作停止条件、成本延迟控制。

## 常见误区

同一模型 + 同一上下文 + 同一执行循环，只换几个 system prompt 名字 = **"多角色提示词"而非多 Agent**。真正值得拆的系统有清晰的角色/状态/输入输出边界与协作协议。

## 演进路径

单 Agent 做扎实 → 找真正瓶颈 → 只在必要处拆子 Agent → 让多 Agent 服务问题而非演示效果。
