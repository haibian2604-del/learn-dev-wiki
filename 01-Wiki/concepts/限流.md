# 限流（Rate Limiting）

> 控制单位时间内请求/操作速率的技术，保护系统不被突发流量打垮。与熔断、降级构成高可用三件套。

## 定义

限流 = 对访问速率的**主动控制**（超过阈值拒绝或排队）；熔断 = 对依赖故障的**被动保护**（下游不可用就快速失败）；降级 = 对功能的**主动取舍**（保核心丢次要）。

## 四种经典算法

| 算法 | 机制 | 优点 | 缺点 |
|------|------|------|------|
| 固定窗口 | 单位时间窗口内计数，超限拒绝 | 实现最简单 | 临界突刺（窗口边界双倍流量） |
| 滑动窗口 | 按粒度细分小窗口，滑动统计 | 缓解临界问题 | 精度取决于粒度（粒度细则成本高） |
| 令牌桶 | 匀速生成令牌，请求取令牌 | 允许一定突发，平滑 | 实现略复杂 |
| 漏桶 | 请求入桶，恒定速率流出 | 强制平滑，保护下游 | 无法应对突发（全部排队） |

**选型**：允许突发 → 令牌桶；要求恒定平滑 → 漏桶；简单场景 → 固定/滑动窗口。

## 落地实现

- **单机**：Guava RateLimiter（令牌桶）、Bucket4j（滑动窗口）
- **分布式**：Redis + Lua 原子计数（固定/滑动窗口，Lua 保证原子性避免竞态）；Sentinel（规则配置 + 流控效果：快速失败 / Warm Up / 排队等待）；Redisson RateLimiter
- **网关层**：Nginx limit_req / Kong / API 网关统一限流

## 边界与常见误区

- 固定窗口的临界突刺：窗口重置瞬间可放行 2 倍阈值——生产应至少用滑动窗口
- 分布式限流有网络开销：单机可行时优先单机；精确一致性需求才上 Redis/Sentinel
- 限流 ≠ 熔断：限流防自己被打垮，熔断防依赖故障传染
- 限流阈值需要压测标定，拍脑袋设值会导致误杀或失效
