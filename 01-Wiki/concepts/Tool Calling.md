# Tool Calling（工具调用）

## 定义

Tool Calling 是 Agent 与大模型 API 交互、获得“外部行动能力”的核心机制：**模型在响应中声明要调用的工具与参数，宿主程序负责真正执行并把结果按协议回传，模型据此继续决策或组织答案**。它让系统从“只会说”变成“能行动”。

> Tool Calling 的意义不是“让模型更聪明”，而是“让系统更有手”。

## 关键机制

### 1. 大模型 API 通常无状态

一次 HTTP 请求结束，下一次不天然继承上一次的用户问题、模型回复或工具结果。“对话记忆”首先是 Agent **Harness 的状态管理能力**，而非模型参数变化。生产系统不应把唯一状态只托管在厂商侧——任务进度、工具执行记录、可恢复检查点仍由应用管理。

### 2. 角色（非跨厂商通用枚举）

- `system`：系统级规则（部分接口放顶层字段）
- `developer`：开发者指令（部分 OpenAI 接口区分应用规则与用户输入）
- `user`：用户目标与内容
- `assistant`：模型文本 / 工具请求 / 其他输出
- `tool`：工具执行结果（非模型生成事实）

跨厂商不变量：**工具结果必须与产生它的工具请求保持可验证的因果关联**。

### 3. 客户端工具闭环：通常至少两次模型请求

请求（问题+工具定义）→ 模型返回 `tool_calls` → 程序校验/执行/取结果 → 回传（原 user + assistant 工具请求 + tool 结果，模型需见完整因果链）→ 模型生成最终答案。若又含工具请求则继续下一轮，直到最终输出或结束条件。

### 4. 调用 ID 是工具轨迹的外键

带显式 `call_id` 时：原样保存模型返回的 ID 不改写；每个结果精确引用对应 ID；不按数组顺序猜归属；工具失败也返回结构化错误并绑定原 ID。调用 ID 解决协议内配对，**不等于业务幂等键**——支付/发信/下单等副作用工具还需独立业务幂等键与执行台账。

### 5. 并行调用

独立、只读调用可在校验后并行；写操作（如创建订单 + 扣减库存）有顺序/事务/补偿要求，应由业务工作流控制，不按模型返回数组直接同时执行。某并行调用失败也不丢其他结果。

### 6. 流式响应是状态机

打开 stream 后响应拆成事件序列（`response_started` → `tool_call_started` → `tool_arguments_delta` → `tool_call_completed` → `response_completed`）。工具参数可能分多段到达，任一中间片段不可独立解析——应按 item/调用索引/调用 ID 累积，等完成事件再拼接、JSON 解析与 Schema 校验。中断传输应丢弃未完成调用，不猜剩余字段、不执行半截参数。

## Tool Calling vs Structured Output

二者都可能用 JSON Schema，但解决问题不同：

| 能力 | Structured Output | Tool Calling |
|------|-------------------|-------------|
| 核心目的 | 约束模型**输出**的数据结构 | 让模型请求宿主**执行**能力 |
| 是否访问外部世界 | 通常否 | 可能（由客户端/托管工具执行） |
| 典型用途 | 信息抽取、分类、固定字段 | 查询、搜索、发邮件、写文件 |
| 结果由谁产生 | 模型 | 外部系统 / 托管工具 |
| 是否需回传再调模型 | 通常不需 | 客户端函数工具通常需 |

可组合：先调工具取外部数据，再让模型按 Schema 生成结构化结果。参数符合 Schema 只说明格式合法，不代表有权限执行、不代表业务语义正确。

## 好工具的五个清晰

职责清晰（一个工具只做一件事）/ 输入清晰（结构化字段 + 格式单位限制）/ 输出清晰（区分成功数据与错误对象，不塞几百 KB 原始日志）/ 权限清晰（只读写入分开，高风险加审批沙箱）/ 错误可处理（区分参数/权限/网络/空/超时限流/部分成功）。第一原则不是“越多越强”，而是“越清晰越稳”。

## 工具设计八原则（实现视角）

> 来自 [[01-Wiki/summaries/架构师AI杜 Day21 MCP工具开发]]，是上方"五个清晰"的工程化展开。

单一职责 / 明确接口 / 错误处理 / 安全优先 / 性能优化 / 可测试性 / 可扩展性 / 用户友好。

其中**可测试性**与**用户友好（错误信息清晰可读）**最易被忽略，却直接决定 Agent 能否自我纠偏——模型要靠错误信息判断"该换参数重试还是换工具"（→ [[01-Wiki/concepts/Loop Engineering]]）。

### 参数验证的五道闸门

类型 / 范围 / 格式 / 依赖 / **安全**。第五道最常被漏掉：文件类工具必须拒绝含 `../` 或 `..\` 的路径，这是**路径遍历**这一最常见致命漏洞的入口。声明式验证（Pydantic `Field` + validator）能同时产出验证逻辑与供模型阅读的参数 schema。

### 工具错误是返回值，不是异常

执行层必须用 try-except 包裹一切，把任何失败变成结构化返回值：

```python
{"success": True,  "timestamp": ts, "data": {...}}    # 成功
{"success": False, "timestamp": ts, "error": "..."}   # 失败，供模型读懂并重试
```

**一致性比丰富性重要**——模型依赖稳定结构做解析，返回格式漂移会直接导致 Agent 崩溃。七类常见错误：参数 / 权限 / 资源 / 执行 / 超时 / 安全 / 系统。

### 执行统计是工具治理的最小数据集

在管理器层记录每工具的调用总数、成功数、失败数、累计耗时、最后调用时间。**失败率与耗时是判断"哪个工具该重写或下线"的唯一硬依据**（→ [[01-Wiki/concepts/Agent 评估]]）。

### 执行前三查

```
is_safe_path（白名单前缀）→ has_permission（权限位）→ is_too_large（体积上限）
```

⚠️ 白名单前缀匹配的经典绕过：`"/tmp_evil/x".startswith("/tmp") == True`，应改用 `os.path.commonpath()`。

## 常见坑

- 模型假装调用过工具（编结果而非发真实请求）→ 按响应类型显式区分文本/工具请求/程序执行结果。
- 工具接口过宽、返回结果太脏（外部内容可能含提示注入，工具结果是“不可信数据”）。
- 没有调用预算 → 循环里不断再搜再调，成本失控。
- 把 HTTP 200（传输成功）当成任务成功。
