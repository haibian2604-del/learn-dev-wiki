# RAG 评估（RAG Evaluation）

## 定义

- 对 RAG 系统**检索**与**生成**两个阶段分别度量质量的方法体系。
- 与 [[01-Wiki/concepts/Agent 评估]] 的分工：Agent 评估关注**自主决策与工具调用**的质量；RAG 评估关注**把正确知识找出来、并据实作答**的能力。二者互补，Agent 式 RAG 需要两套指标并用。

## 机制/原理

### 一、为什么要分阶段

RAG 出错时最忌讳"看端到端分数猜原因"。**分阶段拆解的唯一目的是定位瓶颈**：

| 观察 | 结论 |
|------|------|
| Recall@k 低 | 检索有问题（切块/嵌入/召回策略） |
| Recall@k 高但 faithfulness 低 | 生成有问题（prompt 未约束 / 模型爱编） |
| 两者都高但用户不满 | 问题定义或答案形式不匹配需求 |

### 二、检索阶段指标

| 指标 | 含义 |
|------|------|
| **Recall@k / Hit Rate** | 正确证据有没有被召回——**最关键**，召不回后面全废 |
| **Precision@k** | 召回的 k 条里有多少相关（影响噪声与 token 成本） |
| **MRR** | 第一个正确结果的排名倒数均值 |
| **NDCG** | 考虑排序位置的相关性加权得分 |
| **上下文相关性 Context Relevance** | 召回内容与问题是否真的相关（RAGAS 类框架内置） |

### 三、生成阶段指标

| 指标 | 含义 |
|------|------|
| **忠实度 Faithfulness / Groundedness** | 答案是否**只依据**给定材料——**幻觉率的直接度量** |
| **答案相关性 Answer Relevance** | 有没有答非所问 |
| **答案正确性 Correctness** | 与标准答案比对（需标注） |
| **引用准确率** | 引用是否真的支持该句论断（防"引用对了但内容无关"） |

### 四、评估方法（四选多组合）

1. **有标注集**：人工标注 `(query, 正确文档, 标准答案)` → 自动计算指标（最可靠）
2. **LLM-as-Judge**：强模型按 rubric 打分——需**人工抽检校准**（长度/格式/自我偏好等系统性偏差）
3. **A/B 测试**：线上分流对比，看业务指标
4. **人工评审**：抽样盲评 + 评分卡

### 五、工程落地

- **接入 CI 回归**：每次改 prompt / 切块 / 嵌入模型都跑同一评测集，防版本退化
- **分层评测集**：冒烟集（20 条，每次跑）/ 回归集（300 条）/ 全量集
- **防泄露**：评测集与训练/调参数据严格隔离，发布后冻结
- **无标注时**：先用 LLM-as-Judge 建基线，再逐步人工标注补齐

## 例子

**一次典型的定位过程**：
1. 用户反馈"答非所问" → 先跑评测集
2. Recall@5 = 0.62（偏低）→ 检索是主因
3. 检查发现 BM25 未开启、纯向量检索在含型号的问题上召回差
4. 开混合检索 + RRF → Recall@5 升到 0.91
5. faithfulness 仍 0.7 → 进一步收紧 prompt（"仅依据材料"）并加引用校验 → 0.92

## 边界与常见误区

- ⚠️ **只看端到端准确率**：无法定位问题，也无法验证单个改动是否真的有用
- ⚠️ **LLM-as-Judge 当真理**：Judge 自身有偏差，必须有**人工抽检一致性**校准
- ⚠️ **评测集与调参集重叠**：会得出虚高的进步（典型的自欺）
- ⚠️ **只看平均分**：必须**分层看**（按问题类型/语言/难度），平均值会掩盖某个切片严重退化
- ⚠️ **只测检索或只测生成**：两者必须同时看，否则会"修好一个坏掉另一个"
- **指标不是目标**：最终准绳是用户是否采纳答案
