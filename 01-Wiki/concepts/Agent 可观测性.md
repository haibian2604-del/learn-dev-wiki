# Agent 可观测性（Agent Observability）

## 定义

- 让 Agent 系统的**内部执行过程**可被观察、可被回溯、可被归因的能力体系，由 **Trace / Metrics / Logs** 三支柱构成。
- 与 [[01-Wiki/concepts/Agent 评估]] 的区别：**评估回答"好不好"（离线、抽样），可观测回答"哪里出问题了"（在线、全量）**。二者配合——评估发现问题，可观测定位原因。

## 机制/原理

### 一、三支柱

| 支柱 | 内容 | 用途 |
|------|------|------|
| **Trace** | 一次 run 的 **span 树**：根=整个请求，子 span=LLM 调用 / 工具调用 / 检索 / rerank | **定位"哪一步错了"——最重要** |
| **Metrics** | 延迟 / 成本 / 质量 / 系统四类指标 | 趋势、告警、容量规划 |
| **Logs** | 结构化日志（JSON）+ `trace_id` | 排查细节 |

每个 span 记录：输入、输出、耗时、token、成本、状态、错误、**使用的版本号（prompt/模型/索引）**。

### 二、核心指标

- **延迟**：TTFT（首 token）、端到端 P50/P95/P99、**各阶段耗时占比**（不拆开就不知道优化哪里）
- **成本**：每 run token 成本，按租户/场景聚合
- **质量**：任务成功率、工具失败率、重试率、缓存命中率、幻觉率
- **系统**：QPS、并发数、GPU 利用率、错误率

### 三、三个关键能力（区分"有日志"和"真可观测"）

1. **回放（Replay）**：用相同输入重跑 → 判断是否为随机性问题
2. **Diff**：两个版本同输入输出对比 → **调 prompt 的必备工具**
3. **失败归因**：自动聚类失败模式，输出 top 失败原因（而非让工程师逐条翻日志）

### 四、告警设计

- 基于**阈值 + 变化率**（如 P99 环比涨 50%），而非只看绝对值
- 分层：P0 电话 / P1 邮件 / P2 日报
- **抑制与聚合**：同根因合并，避免告警风暴
- 每条告警必须配 **Runbook**，否则等于噪声

### 五、工具选型

| 方案 | 监控对象 | 部署 |
|------|----------|------|
| Prometheus + Grafana | 系统与业务指标 | 自建 |
| **LangFuse** | LLM 链路（trace + 评测 + 成本） | **开源自部署** |
| LangSmith | LLM 链路 | SaaS（数据出域） |
| OpenTelemetry | 统一埋点标准 | 自建 |

**结论：不是三选一，而是组合**——Prometheus 看系统层，LangFuse/LangSmith 看 LLM 层，用 `trace_id` 关联，才能从"指标异常"下钻到"具体哪条请求哪一步出错"。

## 例子

**一次线上故障定位**：
1. Grafana 告警：P99 从 800ms 涨到 2.3s
2. 下钻 LangFuse：发现某类查询的 **rerank span** 耗时异常
3. 用 `trace_id` 拉出具体请求 trace → 看到 rerank 输入候选数从 50 涨到 500
4. 归因：检索侧改了 top-k 配置但 rerank 未同步调整
5. 回滚配置 → 恢复；把"候选数上限"加入 CI 检查

## 边界与常见误区

- ⚠️ **只有日志没有 trace**：多步 Agent 的日志是散的，无法还原一次执行的因果链
- ⚠️ **指标与 trace 割裂**：两个系统不关联，看到指标异常却无法下钻到具体请求
- ⚠️ **采样过度**：全量存 trace 成本爆炸，但采样率过低会漏掉长尾故障——按错误/慢请求**偏置采样**
- ⚠️ **隐私盲区**：trace 里含用户原文（**常见泄露点**），必须脱敏 + 设留存期 + 租户隔离查询权限
- **可观测不是监控的替代**：监控告诉你"坏了"，可观测告诉你"为什么坏"，二者都需要
- **埋点成本要前置设计**：事后补埋点往往补不全（缺版本号、缺中间变量）
