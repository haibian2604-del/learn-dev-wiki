# 从 SFT 到部署：Agent 模型上线全流程（learn-agent-training 06）

> Agent 模型从训练完成到生产上线的工程全流程与关键决策——从"训练好的模型权重"到"线上稳定运行的 Agent 服务"之间还有一段不短的路，部署阶段踩的坑往往比训练更多。

## 1. 模型选择：不一定是最后一个 Checkpoint

考量维度：Agent 任务完成率（核心）/ 通用 benchmark（确保没崩）/ 工具调用格式正确率（格式崩了上线是灾难）/ 安全评测得分（硬约束）/ 推理效率（平均步骤数，影响延迟成本）。

选择策略：综合最优（五维加权，默认）/ 安全优先（安全通过里选 Agent 最强，金融医疗）/ 效率优先（达标里选步骤最少，延迟敏感）/ 集成多个（不同 checkpoint 路由分发，任务类型差异大）。

**反直觉经验**：RL 后期 checkpoint 往往 Reward 最高但不一定最好上线——可能过拟合训练任务分布，分布外任务退化。中期某 checkpoint 综合更好。

## 2. 模型压缩

**量化**：FP16（不量化）/ **INT8（大多数场景默认，显存 ~50% 精度 ~99%）** / INT4 GPTQ/AWQ（显存 ~25% 精度 ~95-96%）/ FP8（H100+ 支持，精度 ~99.5%）。

**Agent 量化特殊注意点**：tool call JSON 格式对 token 精度敏感——量化后可能少闭合大括号、函数名拼错。**必须跑完整 Agent 评测而非只看 perplexity**：工具调用 JSON 格式正确率（下降 >2% 警惕）、参数填充准确率、复杂轨迹（8+ 步）完成率。

**蒸馏**：Teacher（70B）沙箱生成轨迹 → 筛选成功轨迹 → Student（7B-13B）SFT（可选再 RL）。7B 达到 70B 的 70-85% Agent 能力。适用：推理成本硬约束、延迟 <2s、GPU 有限。天花板取决于 Teacher 质量。

## 3. 推理优化：Agent 对延迟更敏感

**端到端延迟 = 模型推理延迟 × 步骤数 + 工具调用延迟 × 步骤数**（8 步任务每步推理 2s+工具 1s = 24s，用户不会等）。

- **KV Cache 优化**：Agent 上下文单调递增（每步追加几百上千 token）但前面不变——缓存命中率高、显存压力大（8 步后 8K+）、需管理多并发请求争抢
- **推理并行化**：独立工具调用并行执行（同时查天气+航班，串行 6s → 并行 2s）。实现：模型原生支持（训练教输出多个并行 tool call）/ 系统层面调度
- **推理框架选型**：vLLM（PagedAttention 高吞吐，默认选择）/ TensorRT-LLM（NVIDIA 极致性能）/ **SGLang（支持结构化生成，对 tool call JSON 友好，Agent 场景特别推荐）** / Ollama（小模型简单部署）。**Agent 特殊需求：Structured Output/JSON Mode** 确保 tool call 合法 JSON

## 4. 服务架构：Agent Runtime

职责：对话管理（多轮状态/上下文拼接）、工具调度（解析 tool call → 路由 → 收集返回）、循环控制、错误处理（超时/报错重试降级）、并发管理、日志记录。

请求链路：API Gateway（鉴权限流）→ Runtime（拼上下文 → 调模型 → 解析输出 → tool_call 则执行工具返回追加再调模型 / 文本则返回 → 异步写日志）。

**循环控制硬限制（必设，否则上线等出事故）**：最大步骤数 15-20 步、最大 Token 数（窗口 80%）、单步超时 30-60s、总超时 2-5 分钟、重复检测（连续 N 次同工具同参数判定循环）。

## 5. 工具层：注册、鉴权、编排

**工具注册**：名称描述（给模型看）、参数 schema（JSON Schema）、端点、鉴权方式、超时、限流、版本号、是否启用。

**版本管理重要性**：工具接口变更直接改 Agent 行为。安全升级：新旧并行 → 灰度切流量 → 监控调用成功率 → 确认后下线旧版 → 需重新训练适配则先训练再切。

**参数校验与补全**：类型转换（"123"→int）、默认值补全、格式修复（日期）、越界检查（返回错误让模型重试）、注入防护（清洗或拒绝）。

## 6. 安全层：上线前最后一道关

- **输入过滤**：Prompt 注入检测、PII 过滤、频率限制、内容分类
- **输出过滤**：工具调用合法性检查（允许列表）、参数安全检查（rm -rf/DROP TABLE）、返回内容过滤、敏感信息脱敏
- **操作确认机制**：黑名单（绝对拦截：删系统文件/执行未知代码/大量外部请求）/ 需确认（删用户文件/发邮件/改数据库/支付）/ 白名单（只读查询/检索/文本生成直接执行）

## 7. 灰度发布与监控

**灰度流程**：第 1 天内部测试 → 2-3 天 1% 流量（错误率/完成率/延迟）→ 4-7 天 5-10%（新旧 A/B）→ 第 2 周 30-50%（长尾 edge case）→ 第 3 周 100%（旧模型保留 1 周回滚备份）。

**监控分级**：P0 严格告警（请求成功率 <95%、工具调用格式正确率 <98%、循环终止率 >5%、端到端延迟 P99 超 SLA、安全拦截率突变）；P1 每日（任务完成率按类型、平均步骤数、Token/请求、用户反馈、工具调用分布）；P2 每周（失败轨迹分析、高 token 轨迹、新 pattern、安全事件回顾）。

**回滚方案**：旧模型保持在线 ≥1 周、5 分钟内完成回滚、回滚后自动告警通知、不影响对话状态。

## 上线前 Checklist 要点

模型层（checkpoint 有依据/量化后指标降 <3%/格式正确率 >98%/安全拒绝率 >95%/8K+ 长文本通过）；推理层（框架压力测试/结构化输出验证/KV Cache 策略/GPU 扩缩容）；服务层（Runtime/循环限制/工具注册鉴权/参数校验）；安全层（输入输出过滤/高危确认/安全日志）；发布层（灰度方案/监控告警/回滚验证/旧模型可用/值班）。
