# 一个 Agent 系统的核心组成（zero2Agent 基础 03）

> 从系统视角拆开 Agent 的关键模块——先想清楚模块边界，再选框架。

## 为什么先讲模块而非框架

很多教程直接上框架代码，导致能跑 Demo 却说不清：哪部分决策、哪部分存状态、哪部分调工具、哪部分限制乱跑。边界不清，系统一复杂就难维护。

## 7 个核心模块

1. **Goal（目标）**：要解决什么问题、输出长什么样、何时算完成。目标不清 → 做无关动作、无限探索、看起来努力却没完成任务。很多 Agent 问题本质是目标定义问题。
2. **State（状态）**：最易被忽略却最关键。含当前输入、已完成步骤、已获信息、中间结论、下一步待办、结束条件。无明确状态 → 上下文混乱、重复调工具、无法恢复、难调试。现代框架强调“状态驱动”是为可维护，非为高级。
3. **Model（模型）**：理解、推理、生成、决定下一步、生成结构化结果。**模型只是 Agent 中的一个核心组件**，不是整个 Agent；能力全堆给 Prompt 会变脆弱。
4. **Context（上下文）**：模型每步“能看到什么”即 Context（系统指令、工具定义、用户输入、历史轨迹、检索资料、结构化状态）。**Agent 能力天花板往往不是模型参数量，而是 Context 的组织质量**——约束是否在、历史是否裁剪、检索是否相关、工具描述是否让模型选对。
5. **Tools（工具）**：让 Agent 获得外部能力。三类及对应安全策略：
   - **感知类（Perception）**：搜索/查询/读文件/拉 API → 无副作用，可放心重试
   - **执行类（Execution）**：写库/发消息/建资源/执行代码 → 需幂等保护与审批
   - **协作类（Collaboration）**：与其他 Agent 或人类交互 → 需明确协议与超时
6. **Memory（记忆）**：会话内（当前任务状态延续）/ 跨会话（长期偏好、历史、画像）。多数 Agent 至少需会话内状态记忆。
7. **Planner / Policy（规划与策略）**：决定下一步是否需工具、用哪个、是否继续收集、何时停止。简单系统是 Prompt，复杂系统是显式状态机/策略函数/图结构。
8. **Evaluator / Guardrails（评估与护栏）**：检查输出格式、证据是否充足、是否越权、控制成本/延迟/调用次数、必要时触发人工接管。缺失 → 一本正经地出错、为完成任务耗爆成本与时间。

## 典型流程

```
Goal → State 初始化 → Planner 判断 → Model 生成动作/参数
     → Tools 执行 → State 更新 → Evaluator/Guardrails 检查
     → 继续循环或结束
```

## 务实建议

动手前先拿一张纸写清：目标是什么 / 状态里放什么 / 哪些能力必须经工具 / 哪些决策交模型哪些交程序 / 何时结束、失败、人工介入。答不清，再高级框架也救不了设计。
