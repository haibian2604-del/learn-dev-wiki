# 单 Agent 和多 Agent 的边界（zero2Agent 基础 08）

> 判断什么时候需要多 Agent，而不是盲目拆角色——大多数项目第一版应优先从单 Agent 做起。

## 先说结论

多 Agent 真正有价值的前提不是"角色名起得漂亮"，而是"任务是否真的存在明确的职责分离"。

## 单 Agent 更合适的场景

目标单一、状态可集中管理、工具集不复杂、不需要多独立视角长期博弈、系统首先追求稳定。例：风险初筛、文档问答、单任务研究分析、工单分类处理。

## 多 Agent 真正有意义的四类场景

1. **职责确实不同**：一个负责信息收集、另一个负责审查裁决，输入/输出/关注点真不同
2. **上下文压力太大**：不同子任务需要不同上下文，硬塞一个 Agent 又长又乱
3. **任务可以并行**：多个独立方向同时搜集信息再汇总到中心节点
4. **需要明确对抗或复核机制**：一个生成方案、一个找漏洞、一个最终裁决

## 多 Agent 最容易被低估的成本

一旦进入多 Agent 就要处理：Agent 间怎么通信、谁维护全局状态、谁有最终决策权、冲突结论怎么解决、多轮协作何时停止、成本延迟怎么控制。不是"把单 Agent 复制几份"。

## 三种协作模式

1. **分发-汇总（Fan-out/Fan-in）**：协调者拆任务分发并行执行，最后汇总。适合子任务独立。
2. **流水线（Pipeline）**：A 收集 → B 结构化分析 → C 输出审核，串行传递。适合有明确阶段。
3. **对抗式（Adversarial）**：Generator 生成 → Critic 找漏洞 → Judge 裁决。适合正确性极重要。

## 核心架构决策：共享多少上下文

| 策略 | 优势 | 风险 |
|------|------|------|
| 完全共享 | 信息不丢失、协作顺畅 | 上下文爆炸、职责边界模糊 |
| 完全隔离 | 各自独立不干扰 | 信息传递成本高、可能重复工作 |
| **选择性共享** | 只传结构化中间结果 | 需设计接口协议 |

大多数生产系统选第三种：Agent 间通过结构化消息通信而非共享完整对话历史。

**子 Agent 上下文注入**：最小化（只给任务描述+参数）/ 手动选择 / 自动裁剪。注意子 Agent 的上下文可能含不可信外部数据（其他 Agent 输出、工具返回），不能"因为是自己的系统"就自动信任——子 Agent 仍需独立权限与约束。

## 涌现行为：多 Agent 的不可预测性

单独测试任一 Agent 观察不到，需大量交互才暴露：回音室效应（互相确认、结论越来越极端）、资源竞争死锁/活锁、隐含协议崩溃（换模型版本就坏）。应对：长时间集成测试、监控交互模式、全局轮次上限与成本预算、保留人工介入点。

## 常见误区

同一个模型 + 同一个上下文 + 同一个执行循环，只是换几个 system prompt 名字 → 这是"多角色提示词"，不是多 Agent。真正值得拆的系统有清晰的角色/状态/输入输出边界与协作协议。

## 务实判断标准与演进路径

判断：单 Agent 真做不好还是觉得多 Agent 更高级 / 职责边界是否明确稳定 / 拆分后复杂度增加是否值得 / 是否真需并行复核对抗。

演进路径：先做状态清晰的单 Agent → 找真正瓶颈 → 只在必要处拆子 Agent → 让多 Agent 服务问题而非演示效果。

> 如果单 Agent 还没做稳，多 Agent 大概率只会把问题复制并放大。
