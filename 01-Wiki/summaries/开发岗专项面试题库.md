**JD 三层考察点**：
- **Layer 1 后端系统功底**：分布式、高并发、K8s（核心判断：**Agent 系统本质是复杂分布式服务**）
- **Layer 2 Agent 核心技术**：混合架构、上下文工程、工具编排、Memory（Mem0/Zep）、编排、评估
- **Layer 3 模型理解**（加分）：模型长短板、Function Call 微调、Agent RL/DPO

## 高频考点与标准答法

### 1. 系统设计题要"先算账，再分层"（Q1 是模板）
- **第一步永远是把需求翻译成容量数字**：日均 100 万 / 峰值 QPS 3000 → **峰均比 250×**，说明按峰值设计容量、按均值设计成本
- 成本倒推：10 万元/月 ÷ 3000 万次 ≈ **0.0033 元/次** → **必须靠缓存 + 模型分层**，不能全靠大模型
- 然后才是分层架构 + 延迟预算表 + 可用性 + 监控
- **面试官最想看的不是架构图，是"你怎么把数字算出来"**

### 2. Multi-Agent 设计题要"先划职责边界"（Q2）
- Supervisor 只做路由与汇总，**不干具体活**；每个子 Agent 的**工具集互不重叠**（否则会出现"两个 Agent 都能退款"）
- 高危写操作（退款）必须：**人工确认 + 幂等 key + Saga 补偿**
- 会话级串行化（同 session 排队）解决并发写冲突（→ [[01-Wiki/concepts/单 Agent 与多 Agent]]）

### 3. 流式题要"点破一个伪命题"（Q3）
- "检索与生成并行"不严谨——生成必须以检索结果为输入
- 真正能做的是：**检索内部并行** + **预取** + **立即推送进度**；传输优先 **SSE**（单向自动重连），需打断才用 WebSocket
- 必踩的坑：**Nginx `proxy_buffering` 会把流攒起来**

### 4. 延迟与成本题是"同一套动作的两个方向"（二-Q1/Q2）
- 延迟：拆指标定位 → 检索并行/索引调优/预过滤 → 生成靠**流式（感知延迟）+ 小模型路由 + prompt 压缩**
- 成本：**语义缓存（单项收益最大）+ 模型分层 + prompt 压缩 + 减少调用次数 + 批处理 + 输出控制**
- 共同前提：**先做成本/延迟归因，找到头部 20%**

### 5. 框架选型题统一用"定位 + 场景"作答（三-Q1~Q10）
- 判据永远是**"我的核心难点是什么"**：检索深 → LlamaIndex；编排复杂 → LangGraph；多角色协作 → CrewAI/AutoGen
- 选型要查的是**可靠性、隔离、可观测、可删除**这些工程属性，而不是 star 数

### 6. 业务落地题禁止"只报好数字"（四-Q1/Q8）
- Q1 的正确答案是**分层结论**："在 X 类问题上替代 Y% 人工"，而不是"比人更好"；方法是**影子模式 + A/B + 分层分析**
- Q8 的 ROI 可信度**取决于对照组设计**——没有对照的 ROI 只是故事；且要算全成本（研发运维/兜底人力常被低估）

### 7. 幻觉与隐私题要"给边界认知"（四-Q4/Q6）
- **幻觉不能根除，只能降低 + 让用户可识别**；设计目标是"可发现的幻觉"，关键是**答案-证据一致性校验 + 强制引用 + 拒答合法化**
- 隐私要**按生命周期逐段施策**：采集最小化 → 存储加密隔离 → 使用脱敏 → 传输评估出域 → 留存与**删除权** → 治理合规

## 亮点与不足

**亮点**
- **按真实 JD 三层组织**，自带岗位定位与核心考察点，可直接当复习路线图
- **系统设计题给足了数字**（Q1 的需求约束、延迟预算分配），这类"带约束的设计题"比开放式设计题更难也更能区分候选
- **业务落地部分（第四部分）是很多题库的盲区**：如何证明优于人工、如何算 ROI、如何做灰度——这些是开发岗晋升与面试的关键
- **Q10 的监控选型给出了"不是三选一而是组合"的正确答案**，避免候选人踩坑

**不足**
- ⚠️ **原文只有题面与要点标题**（如"优化方向：检索优化/生成优化/缓存策略/并行处理"），无展开答案；第四部分 Q5/Q6/Q7 原文的"设计要点/保护措施/实现方式"甚至是**空标题**，答案均为本次补写

- **题目编号分部分重复**（四个部分各从 Q1 开始），引用时必须带部分前缀
