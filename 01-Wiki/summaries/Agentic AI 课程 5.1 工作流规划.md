# Agentic AI 课程 5.1 工作流规划

> 规划模式 = 给 LLM 一套工具集，让它**在运行时自己决定调用顺序**，开发者不再硬编码流程。灵活度大涨，代价是结果不可预知。

## 核心观点

- 类比：复杂软件系统需要工厂模式、单例模式、依赖倒置等设计模式；Agent 系统要兼顾复杂度与效率，也需要设计模式
- **规划模式（Planning）** 的 Agent 系统**高度自主**，能自行决定执行复杂任务所需的工具调用序列，而无需事先硬编码（→ [[01-Wiki/concepts/规划模式]]）

## 真实案例：客服助理 Agent

- **目标**：回答广泛、复杂的查询，运行时灵活决定行动。示例："你们有没有库存中售价低于 100 美元的圆形太阳眼镜？"
- **方法（四步）**：
  1. **提供工具集**

     | 工具名 | 功能 | 示例用途 |
     |--------|------|----------|
     | `get_item_descriptions` | 获取商品文字描述/元数据（名称、款式、材质、颜色、形状） | 用户说 "round sunglasses" 时查出所有圆形特征太阳镜 |
     | `get_item_price` | 查询指定商品价格 | 找到商品后判断哪些低于 $100 |
     | `check_inventory` | 检查库存与数量 | 查圆形眼镜是否在库 |
     | `check_past_transactions` | 查看用户历史交易（买过什么、是否退换） | 客服场景"我上周买的眼镜有问题" |
     | `process_item_sale` | 处理购买，创建销售订单 | 用户确认购买时 |
     | `process_item_return` | 处理退货 | 用户想退货时 |

  2. **LLM 编写计划**：要求 LLM 返回逐步执行计划，说明按什么顺序调用哪些工具——本例：调 `get_item_descriptions` 找 round sunglasses → 据 Step 1 输出（找到的产品）→ 调 `check_inventory` 查库存 → 对库存有货的结果 → 调 `get_item_price` 筛出低于 $100 → 输出最终结果
  3. **逐步执行**：按计划把每步指令与上一步输出/上下文依次喂给 LLM，让它调用相应工具并执行
  4. **最终输出**：把所有步骤结果反馈给 LLM 生成最终答案

## 收益与风险

- **收益**：Agent 能力强、任务范围广；开发者无需事先编排工具调用序列，灵活性与自主性提高
- **风险**：运行时无法预知 LLM 会生成什么计划，带来**结果不稳定 / 出错 / 越权**的风险
- **现状**：规划模式在 **AI Coding 应用中非常成功**，但在其他领域仍处尝试阶段

## 工具设计的经验（笔记作者补充）

- 随基础模型智能程度提高，完全由 Agent 控制流程的场景越来越多，作者自己开发时也常用；**难点在于工具设计与流程设计**
- 同一个场景：经验丰富的开发者可能抽象出 3 个封装好复杂逻辑的核心工具即可；经验不足者容易**过度抽象出十几种工具**，或索性只提供一两个最基础的工具（如直接把商品系统后台的数据库 session 交给模型——**极其不安全！**）让 AI 自己写业务
- 推荐框架：HuggingFace 社区的 **smolagents**，代码简洁、抽象少、工具开发只要一个 `@tool` 装饰器、自由度高、有流程跟踪（→ [[01-Wiki/entities/smolagents]]）

## 亮点与不足

- 亮点：完整演示"工具集 + LLM 出计划 + 逐步执行"的落地路径，并诚实指出规划模式目前只在 AI Coding 领域成功；工具粒度（3 个 vs 十几种 vs 裸数据库）的经验判断很实用
- 不足：未给出"何时该用规划模式而非固定工作流"的判据；越权风险的缓解手段缺失
