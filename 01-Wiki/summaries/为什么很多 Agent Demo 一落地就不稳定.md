# 为什么很多 Agent Demo 一落地就不稳定（zero2Agent 基础 04）

> 从工程视角看 Agent 从 Demo 到生产的断层——差别不在“规模更大”，而在“约束更多”。

## Demo 关注“能不能动”

Demo 只需证明：模型能理解任务、工具链能接通、能完成一个示例流程。它只证明“有可能可行”，不能证明“长期可用”。

## 真实系统关注“会不会坏”

进入真实场景后关注：用户输入是否稳定、外部数据是否可靠、工具是否会失败、系统是否重复无效动作、出错能否恢复、成本延迟是否可接受。真实系统追求“多数情况下都别坏”，而非“最聪明的一次”。

## 六大断层

1. **目标定义太模糊**：如“自主研究并给出结论”。→ 不知道何时结束、探索膨胀、输出标准不稳。第一步不是换更强模型，而是“把目标写窄”。
2. **状态没有设计**：所有信息塞进 Prompt 不断续写。长任务 → 中间结果无结构化保存、忘记已做、重复调用、中断无法恢复。
3. **工具调用被过度乐观**：默认 API 可用/格式稳/延迟可接受/无权限问题。真实中 API 超时、格式变、权限失败、返回空或部分缺失 → 需重试/降级/兜底/错误处理。
4. **把“会思考”误当“会执行”**：模型擅长生成看似合理的解释 ≠ 真完成任务。要看实际执行了什么、用了哪些数据、每步是否可验证。
5. **没有结束条件和预算控制**：无约束就可能不断再查、再搜、再试。需：最多调多少次工具、最多跑多少轮、超时必退出、证据不足转人工。
6. **没有可观测性**：出错只见“任务失败”一句无法维护。至少应见每轮状态、每步决定、每次工具调用、错误原因、最终退出条件。

## 更现实的做法（顺序）

1. 先把目标缩窄
2. 明确状态结构
3. 给工具调用加异常处理
4. 定义结束条件和预算上限
5. 增加日志、追踪、人工接管点

而不是：先换更强模型 → 堆更多 Prompt → 希望系统自己变稳（通常没用）。
