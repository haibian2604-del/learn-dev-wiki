# Agent 评估：怎么知道你的 Agent 好不好（zero2Agent 基础 11）

> 从指标设计到评测方法，建立 Agent 质量的工程判断标准——"能跑"和"好用"之间的距离远比想象中大。

## 为什么 Agent 评估比传统软件更难

传统软件测试假设相同输入产生相同输出；Agent 打破假设：模型输出有随机性、工具调用路径可能不同、同一任务多种"正确"完成方式、中间过程和最终结果都要评估。不能只套单元测试思路。

## 评估的四个维度

1. **任务完成率（Task Success Rate）**：是否真正完成任务。"完成"= 可被外部验证的结果（测试通过/包含关键事实/格式规范），而非模型说"我完成了"。关键是**定义明确的验收条件**。
2. **效率（Efficiency）**：迭代次数、token 消耗、工具调用次数（无效/重复）、端到端延迟、费用。完成率相同，3 轮完成与 12 轮完成质量差距很大。
3. **安全与合规（Safety）**：是否调用越权工具、泄露信息、生成不合规内容、信息不足时编造事实。Demo 阶段几乎不测，生产中可能最重要。
4. **鲁棒性（Robustness）**：模糊/恶意输入、工具报错/超时、上下文极长极短、中断恢复。鲁棒性不是"永远不出错"而是"出错时行为可预测且可恢复"。

## 四种评测方法

1. **固定测试集 + 自动验证**：有明确预期结果的用例自动比对。可重复/可回归；局限是只覆盖有限场景。
2. **LLM-as-Judge**：用另一模型评估输出质量（准确/完整/相关打分）。可评估开放式任务；但评判模型有偏差、评分标准需校准。原则：给明确评分标准与示例、多次取平均、定期人工校准、**不要同一模型既当运动员又当裁判**。
3. **A/B 对比**：同批任务两版本分别处理比较各维度指标。回答：新 Prompt 好多少 / 换模型是否降质 / Reflection 是否值得成本。
4. **对抗性测试（Red Teaming）**：专门设计让系统出错的输入（prompt 注入、边界极端输入、误导矛盾指令、越权请求）。追求"最差情况下系统会不会失控"。

## 评测设计实用建议

- 从小测试集开始：20-50 个代表性用例 + 自动化脚本已远超"人工试几个"。
- 区分**能力评测**（固定上下文、Mock 工具、控制变量，验基本逻辑）与**集成评测**（真实工具/延迟/端到端，验生产可行性）。
- 注意统计显著性：同用例至少 3-5 次；比较版本样本量要够。
- **持续监控 > 一次性评测**：追踪成功率趋势、平均迭代次数、token 异常增长、用户反馈、工具失败率；突变往往意味着外部依赖或数据分布漂移。

## 常见评测陷阱

只测 happy path（≥30% 覆盖异常边界）/ 把"模型说完成了"当真（须基于可验证外部标准）/ 忽略成本维度（10 轮 vs 3 轮成本差 3 倍）/ 过度依赖 Benchmark（任务分布/工具环境/成功标准不同，Benchmark 用于选模型定基线，业务评测用于验证系统）。

## 与 Loop Engineering 的关系

相互支撑：Loop 退出条件需评估结果触发（Verification Loop 验证器本质是实时评估器）；评估指标驱动 Loop 策略调优（迭代次数太高→调 Reflection 条件）；持续监控发现退化→触发评测分析根因。
