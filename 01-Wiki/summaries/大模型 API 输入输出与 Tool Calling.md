# 大模型 API 输入输出与 Tool Calling（zero2Agent 基础 05）

> 从消息协议到完整工具调用循环，理解 Agent 如何与大模型 API 交互——模型返回的不是一段文本，而是一组带类型、来源与控制状态的输出。

## 为什么需要工具

单靠模型做不到：实时数据、私有库查询、文件读写、内部系统调用、代码执行、外部 API 交互。Tool Calling 的意义不是“让模型更聪明”，而是“让系统更有手”。

## 心智模型：分工

- **模型负责**：决定是否调工具、选工具并生成参数、根据结果继续决策或组织答案。
- **程序（宿主）负责**：校验工具名与参数、真正执行、处理权限/超时/重试/异常、按协议回传结果。
- 模型输出“我要调某工具”≠ 工具已执行，只有宿主完成调用并得结果，外部动作才真发生。

## 大模型 API 通常无状态

一次 HTTP 请求结束，下一次不天然继承上一次的用户问题/回复/工具结果。“对话记忆”首先是 Agent Harness 的状态管理能力，而非模型参数变化。生产系统不应把唯一状态只托管在厂商侧——任务进度、工具执行记录、可恢复检查点仍由应用管理。

## 一次请求的组成

连接与鉴权 / 模型与推理配置 / 指令与输入（system/developer/用户/历史/文件）/ 工具定义 / 输出约束 / 追踪元数据。示例用 OpenAI-compatible Chat Completions 风格展示（非各厂商统一格式）。

## 角色不是跨厂商通用枚举

- `system`：系统级规则（部分接口放顶层字段）
- `developer`：开发者指令（部分 OpenAI 接口区分应用规则与用户输入）
- `user`：用户目标与内容
- `assistant`：模型文本/工具请求/其他输出
- `tool`：工具执行结果（非模型生成事实）

跨厂商不变量：**工具结果必须与产生它的工具请求保持可验证的因果关联**（显式 call ID 是常见实现，但非所有协议强制，如 Gemini 可无显式 ID，应按该协议结构/名称/顺序关联）。迁移厂商不能只换字段名，还要查指令位置、工具请求与结果是否须相邻、是否须回传原始 output item、并行时如何配对、多模态与流式如何编码。

## 响应不只是一个字符串

只读 `content` 是很多 Agent Bug 起点。成功响应还可能含：文本 / 一个或多个工具调用 / 结构化或多模态 output / 停止原因（`finish_reason`：正常结束、请求工具、截断、安全拦截）/ token 用量 / 响应 ID 与 provider request ID / 警告拒答等。注意：`content` 为空不代表失败（可能正在请求工具）；`arguments` 是 JSON 字符串需解析校验；字段名取值因厂商而异不能写死。生产应记录 provider request ID 用于排查。

## 客户端工具闭环：通常至少两次模型请求

“上海现在几点，天气如何？”示例：第一次请求把问题+工具交给模型 → 模型返回两个 `tool_calls`（含 `call_time_01`/`call_weather_01`）→ 程序校验、执行、取得结果 → 第二次请求必须让模型看见完整因果链（原 user + assistant 工具请求 + 两个 tool 结果回传）→ 模型生成最终答案。不能只发工具结果，也不能省略第一次的 assistant 工具请求（多数协议校验配对）。若第二次又含工具请求，继续下一轮直到最终输出或结束条件。

## 因果关联是工具轨迹的外键

带显式 call ID 时，每次调用至少含：工具名、参数、调用 ID（结果归属哪次请求）。处理规则：原样保存模型返回的 ID 不改写；每个结果精确引用对应 ID；不按数组顺序猜归属；同轮同名调用分别配对；工具失败也返回结构化错误并绑定原 ID（如 `{ok:false, error:{code, message, retryable}}`），不伪装成普通 user 消息。调用 ID 解决协议内配对，≠ 业务幂等键——支付/发信/下单等副作用工具还需独立业务幂等键与执行台账。无显式 ID 时用官方结构/顺序维持关联，并在适配层生成稳定内部事件 ID。

## 并行工具调用

时间查询与天气查询互不依赖可并行。Harness 应：先解析校验整组调用 → 判断数据依赖/写冲突 → 对独立只读调用设并发上限并行 → 为每个调用单独记录成功/错误/耗时/结果 → 按协议关联机制组装结果再发下次请求。不要盲目并行写操作（“创建订单”与“扣减库存”有顺序/事务/补偿要求，由业务工作流控制）。某并行调用失败也不要丢其他结果。

## 最小 Agent Loop（伪代码要点）

核心是 `for step in range(MAX_STEPS)` 的循环：调模型 → 记录 usage/request_id → 解析 assistant item → 分类 stop reason → 校验 → 入 history → 若 completed 且无 tool_calls 返回文本 → 否则校验 tool_calls、按 policy 执行、按 call_id 配对回传。真正困难在周围工程约束：输入输出校验、权限与审批、超时重试幂等、上下文长度与成本、结束条件与调用预算、日志追踪与故障恢复。

## Structured Output vs Tool Calling

二者都可能用 JSON Schema 但解决问题不同：Structured Output 约束模型**输出**的数据结构（信息抽取/分类/固定字段，结果由模型产生，通常不需回传）；Tool Calling 让模型请求宿主**执行**能力（查询/搜索/发邮件/写文件，结果由外部产生，客户端函数工具通常需回传再调模型）。可组合：先调工具取外部数据，再让模型按 Schema 生成结构化结果。注意参数符合 Schema 只说明格式合法，不代表有权限执行、不代表业务语义正确，程序仍需业务校验。

## 流式响应是状态机，不是随时可解析的 JSON

打开 stream 后响应拆成事件序列（`response_started` → `text_delta`/`tool_call_started` → `tool_arguments_delta` → `tool_call_completed` → `response_completed`，事件名因厂商而异）。工具参数可能分多段到达，任一中间片段不可独立解析——应按 output item/调用索引/调用 ID 累积增量、等完成事件、拼接完整、再 JSON 解析与校验。连接在参数传输一半时中断，应丢弃未完成调用，不猜剩余字段、不执行半截参数；恢复/重试要考虑重复副作用。

## 不要把原始思维链当成系统接口

可观测性 ≠ 保存模型原始 Chain of Thought。不同模型对 reasoning 处理差异大（只返最终答案 / 可展示 summary / 不透明或加密 reasoning / 要求后续请求原样回传某些块）。**不要让业务逻辑依赖“读取模型内心独白”，也不要主动索取/持久化/分析原始隐藏思维链**——非稳定跨模型合同，且有隐私安全风险。调试应记录可验证执行轨迹：输入与指令版本（敏感脱敏）、模型输出文本或 typed item、工具名/校验后参数/协议关联信息、工具结果摘要/错误码/耗时、停止原因/token/provider request ID、预算/审批/退出状态。reasoning summary 可作可选解释性输出，不可作真实执行证据；协议要求回传的不透明 reasoning 应作受控临时协议状态原样传递，不解析不写业务日志。

## 工具调用不等于随便开放能力

新手易把搜索/文件系统/shell/数据库/浏览器/写入接口一次性暴露给模型 → 模型选错工具、参数乱填、调用失控、权限过大、难调试。工具系统设计第一原则不是“越多越强”，而是“越清晰越稳”。

## 好工具的五个清晰

1. **职责清晰**：一个工具只做一件事，不兼搜索+总结+打分+写入。
2. **输入清晰**：结构化字段、明确格式/单位/限制，Schema 校验后再做路径/资源/业务权限校验。
3. **输出清晰**：返回稳定，区分成功数据与错误对象，保留来源/时间戳/版本，不把几百 KB 原始日志直接塞回上下文（存原文、返摘要与可追溯引用）。
4. **权限清晰**：只读与写入分开，高风险副作用加白名单/人工确认/沙箱/审批，不只靠 Prompt。
5. **错误可处理**：区分参数/权限/网络/空数据/超时限流/部分成功，才能决定重试/换工具/降级/停止。

## 最容易踩的坑

- 模型假装调用过工具（编结果而非发真实请求）→ 按响应类型显式区分文本/工具请求/程序执行结果，实时数据或副作用操作最终文本不能代替可验证执行记录。
- 工具接口设计过宽（一个搜索支持十几种模式无明确字段）→ 模型难稳定生成正确参数。
- 工具返回结果太脏（超长原始文本/混乱 JSON/不稳定结构）→ 模型后续也处理差；外部网页/邮件/文档可能含提示注入，工具结果是“不可信数据”，进入 tool item 不自动获得指令权限。
- 没有调用预算 → 循环里不断再搜/再调，成本失控。
- 把传输成功（HTTP 200）当成任务成功 → 还需检查 typed output、停止原因、工具状态、业务验收。

## 务实建议

先做“可控工具”再做“强大工具”：围绕具体任务列真正需要的能力 → 每个做成边界清晰的小工具 → 优先保证输入输出稳定 → 再补权限/异常/预算控制 → 用失败样例测错参/超时/中断/重复调用/越权。
