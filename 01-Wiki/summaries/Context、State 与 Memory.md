# Context、State 与 Memory（zero2Agent 基础 06）

> 从大模型 API 的消息轨迹出发，理清上下文、状态、短期记忆和长期记忆——"模型记得我们刚才说过什么"是产品感受，不是工程描述。

## 五个常被混用的概念

- `messages`：一次 API 请求的协议化消息
- `Context`：本次推理时模型实际可见的工作集
- `State`：应用维护的结构化执行状态
- `Memory`：系统选择保留、更新并在以后取回的信息
- `RAG`：从外部知识源检索当前任务所需资料的方法

它们相互传递信息，但职责不同。

## messages 不是模型的记忆

大模型 API 无状态：第二次请求能继续，是因为应用把必要消息轨迹再次提交，而非模型"想起"了第一次。对话记忆首先是 **Agent Harness 的状态管理能力**。

**工具调用必须保持因果配对**：保留模型发出的工具调用、协议关联信息（call ID）、程序返回的工具结果、调用与结果的先后顺序。裁剪历史时**一个尚未完成的工具调用及其结果不能被切开**，不能留下"孤儿结果"。

## Context = 静态前缀 + 动态执行轨迹 + 本轮补充信息

- **静态前缀**：系统指令、工具定义、固定输出规范、长期背景（跨请求稳定）
- **动态执行轨迹**：用户新消息、工具调用/结果、阶段结论、当前任务状态

messages 最终还要经过 **Chat Template** 序列化成 token：`system/user/assistant/tool` 是协议的一部分而非普通文本标签；不同模型消息格式不可原样互换；手工拼字符串会丢角色边界与调用 ID。

## Context / State / Memory / RAG 对比

| 概念 | 主要职责 | 是否一定进入当前 Context |
|------|---------|------------------------|
| Context | 为本次推理提供可见信息 | 是，它就是当前输入工作集 |
| State | 记录任务执行到哪里（步骤、预算、中间结果、完成条件） | 否，只注入当前决策所需部分 |
| 短期记忆 | 保持当前会话/任务连续性 | 不一定，可裁剪/摘要/结构化 |
| 长期记忆 | 跨会话保留主体相关信息（偏好、约束、历史决策） | 否，通常按需召回 |
| RAG | 从外部知识源补充事实 | 只有被检索选中的内容进入 |

**很多所谓 Memory 问题本质是 State 没设计好**。设计顺序建议：先结构化 State → 再管理会话 Context → 最后验证是否真需要长期 Memory（过早加长期记忆易召回不相关信息、旧事实污染、冲突、敏感信息过度保存）。

## 四种 Memory 设计模式

1. **对话窗口保留**：只留最近 N 轮。实现简单、原始细节保真；但长任务超预算、早期关键约束被挤出、裁剪须按完整 API 轮次。
2. **摘要式记忆**：较早内容压缩成滚动摘要。省 token 适合长会话；但可能遗漏/改写事实、早期错误持续传播、需保留来源回查。
3. **结构化状态存储**：任务进度/中间结果放进明确字段（goal/constraints/completed_steps/open_questions/tool_budget_remaining）。可校验可调试可恢复，适合工作流与 Agent。
4. **检索式长期记忆**：长期信息存数据库/向量库按需召回。跨会话积累；但召回不保证相关、需处理权限/过期/冲突/删除。

## Memory 和 RAG 不是一回事

- RAG：从外部知识源取回当前问题需要的资料
- Memory：系统应为某个用户/任务/主体保留什么、以后什么条件下取回

判断标准不是"是否用了向量数据库"，而是**信息为什么被保存、归属于谁、何时应被召回**。

## KV Cache vs Prompt Cache

- **KV Cache**：一次推理内部、逐 token 生成时的注意力优化，运行时层面机制
- **Provider Prompt/Prefix Cache**：不同请求之间复用匹配前缀计算，条件/生命周期/计费由供应商决定

不要假设前缀相同一定命中缓存、命中一定有收益。只有服务端明确返回 cached input tokens 等字段才能作为观测数据。**稳定前缀原则**：稳定内容在前（系统指令→工具 Schema→固定背景）、动态内容在后（历史轨迹→检索结果→用户输入），避免在稳定前缀中插时间戳/随机 ID。**正确性始终优先于缓存**。

## 上下文压缩：压什么，保什么

优先顺序：删重复日志/冗余格式 → 大文件移外部存储只留引用 → 进度提取到结构化 State → 较早轮次滚动摘要 → 需要时检索取回 → 超长任务检查点开新 Context。

压缩边界：不切断未完成 tool_call/tool_result 配对、不改协议关联、不把推测摘要成既定事实、保留硬约束/关键决定/未解问题及来源、原始证据可回查。压缩是有损变换，压缩器也要测试。

## 上下文消融实验

agent-api-lab 用可观察请求/响应/工具事件检验上下文策略，比较 A 完整轨迹基线 / B 窗口裁剪 / C 摘要+结构化 State / D 删除关键事实 / E 孤立工具结果或错配 call ID（协议负例）。记录：任务成功率、重复调用数、token 用量、事实保留率。

## 设计 Memory 最该问的问题

1. 这条信息是 State、会话 Context 还是跨会话 Memory？
2. 完整保留、摘要保留还是按需检索？
3. 来源是什么，能否验证？
4. 何时过期，冲突以谁为准？
5. 是否含不应长期保存的敏感信息？
6. 写入/读取/更正/删除由谁控制？
