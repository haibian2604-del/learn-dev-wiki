# 图数据建模与准备（LLM 抽取 + Neo4j 导入）

> 用 LLM 把 Markdown 菜谱转为图数据（nodes/relationships CSV），经 Cypher 导入 [[01-Wiki/entities/Neo4j]]，并实现"图→结构化文档"转换与图感知分块。（Datawhale all-in-rag 第 9 章 §2）

## 核心观点

- **转换流程**：读取 Markdown → LLM 解析抽取实体/关系 → 输出 nodes.csv + relationships.csv → Cypher 脚本导入 Neo4j（→ [[01-Wiki/concepts/实体关系抽取]]）
- **实体类型**：Recipe、Ingredient、CookingStep、CookingMethod、CookingTool、DifficultyLevel、RecipeCategory（统一 `nodeId` 编码、多语言、层次化）
- **关系类型**：`REQUIRES`（菜谱-食材，含 amount/unit）、`CONTAINS_STEP`（含 step_order）、`HAS_DIFFICULTY_LEVEL`、`BELONGS_TO_CATEGORY`
- **图→文档转换**：`build_recipe_documents` 把图记录拼成结构化 Document，metadata 保留 `node_id` 关联；图数据提供关系信息、结构化查询、动态推荐、语义增强、查询优化等额外价值
- **图 RAG 分块策略**：每个 chunk 通过 `parent_id` 关联图节点；优先按 `##` 章节语义分块，必要时长度分块（chunk_size 500 / overlap 50）；元数据直接来自图节点

## 关键数据

| 项 | 值 | 出处 |
|----|----|------|
| nodes.csv 字段数 | 21 列（含 nodeId/labels/name/.../stepNumber/methods/tools） | 本文 §3.2 |
| relationships.csv 字段 | startNodeId,endNodeId,relationshipType,relationshipId,amount,unit,step_order | 本文 §3.2 |
| 分块参数 | chunk_size=500, chunk_overlap=50 | 本文 §5.3 |

## 亮点与不足

- 亮点：图结构让"包含鸡肉的所有菜谱"类查询比全文检索更高效；chunk 保留双层上下文（文本 + 图关系）
- 不足：依赖 LLM 抽取质量，需抽检；图谱维护成本未深入
